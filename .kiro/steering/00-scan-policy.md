# 扫描策略：先看图，别扫源码

这个仓库里**小程序源码（示例）是「已固化的输入」，不是待改的代码**。它们只是用来驱动和验证渲染引擎的素材。默认不要读、不要遍历、不要全文搜索它们 —— 那是纯粹的 token 浪费，而且会把上下文挤掉。

## 默认不扫的路径

```
sample/**          # 全部示例小程序（wxml / wxss / js / json / 图片）
dist-html/**       # 编译产物
dist-news/**       # 编译产物
doc/gallery/**     # 画廊截图
target/**          # 构建产物
assets/**          # 字体等二进制素材
*.png *.jpg *.ttf *.otf *.zip
```

## 什么时候才允许定向读小程序源码

只有在**已经确认问题出在某个具体页面**之后，才去读**那一个文件的相关片段**：

1. 先用现象定位：截图/像素比对、`MINI_FPS=1` 的整帧归因、`MINI_LAYOUT_LOG=1` 的失效范围、compare 报告里的 diff 区域。
2. 由现象推出可疑的页面与元素（例如「首页 y=464~680 每帧重绘」）。
3. **只读那个页面的对应片段**，或只 grep 一个具体属性名。

反面做法（禁止）：一上手就 `ls -R sample/`、把整页 wxml/wxss 读进来通读、为了「了解一下」而遍历所有页面。

## 优先走「功能可用图」而不是读代码

排查顺序固定为：**先看现成的诊断产物 → 再看引擎侧代码 → 最后才定向看一眼小程序源码**。

- 渲染不对 → 先看 `target/*-compare/<page>/side-by-side.png` 与 `diff.png`，diff 会直接圈出位置
- 卡顿/掉帧 → 先看 `MINI_FPS=1` 的「整帧归因」，它会指出是谁触发的整屏重绘
- 布局重建慢 → 先看 `MINI_LAYOUT_LOG=1` 的分段耗时
- 滚动异常 → 先看 `MINI_SCROLL_LOG=1`
- 局部重绘可疑 → 跑 `bash tools/damage-check.sh`

这几个开关的存在意义就是**替代"把源码读一遍再猜"**。先拿数据，再动手。

## 已固化、不要主动改的东西

- `sample/` 下的示例小程序：除用户明确要求外不修改。它们是双端一致性的**基准输入**，改了会让历史像素基线失效。
- 已通过逐字节基线验证过的渲染路径：不要"顺手清理"。重构与改行为必须分开做，且要用快照逐字节对照证明等价。
