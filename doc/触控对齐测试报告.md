# tea-app 触控对齐测试报告

**被测对象**：`sample/tea-app`（uni-app 编译产物，35 个页面）
**测试方式**：全部走无头 CLI，与交互窗体**同一条输入链路**（`on_pointer_press/move/release`）——
`--touch`（完整触摸序列）、`--swipe`（按下→逐步移动→抬起）、`--swipe-hold`（停在终点不抬手）、
`--click`（命中/冒泡/导航）、`--drag`（逐帧计时）。诊断开关 `MINI_SCROLL_LOG=1` 打印手势归属与滚动状态。
事件对象的观察通过 `sample/touch-probe`（把所有触摸绑定写全的探针页）与在 tea-app 上劫持
`__dispatchEvent` 两种方式取得。

**结论**：上下滑动、点击、长按、侧滑返回、方向锁定、`catchtouchmove` 锁滚、触摸事件对象
共 25 项与微信语义一致；发现并修掉 1 个真实缺口（`onPageScroll` 宿主从未派发）；
遗留 2 项已知差距（scroll-view 自身的滚动事件、多指手势），文末列出。
**后续**：实机反馈又暴露 6 个缺陷（组件事件被派发到页面、覆盖层命中失灵、
`e.detail.value` 被强转类型、`checkbox-group` 的 change 语义、惯性撞边界不回弹、
scroll-view 可滚内容漏算），逐条修复与实测见第六之二节。

## 六、本轮修复

**`onPageScroll` 从未被宿主派发**（A8）。逻辑层一直有派发入口
（`__dispatchPage('onPageScroll', arg)`，甚至有单测），但宿主没有任何调用点 ——
「滚动到一定位置显示回到顶部按钮」「吸顶导航变色」这类写法在引擎里完全不生效。

现在在每帧的滚动收尾处统一判断：位置变化超过 0.5px 就派发一次
（`src/bin/app_window/event_handler.rs::dispatch_page_scroll`）。放在这一处而不是各条输入路径里 ——
拖动、惯性、回弹、滚轮、脚本设位置最终都会经过这一帧检查，不会漏。

代价实测为零：tea-app 首页拖动 60 帧平均 0.38ms（改动前 0.44ms，在噪声内），
sample-app 15 页快照逐字节不变，damage-check 全绿。

## 六之二、实机反馈修复轮（点击 tab / 底部回弹 / 输入框）

用户在交互窗体上报三条：① 点底部 tab 切换不对；② 滑到底部内容被底部条遮住、回弹不像微信；
③ 输入框差距大、点发送没反应且报 `TypeError: not a function`。逐条定位到 5 个引擎缺陷。

### 1. 组件模板里的事件被派发到了页面上（问题①）

`__dispatchHandler(name)` 无条件先查 `__currentPage[name]`，找不到才去组件实例里找。
而 uni-app 给**页面和每个组件各自**生成 `e0_0`、`e1_1` 这种短名字 —— tea-app 的
`pages/choose/choose` 和它用的 `tab-bar` 组件都有 `e0_0`…`e4_4`（实测
`page has: e0_0=function e1_1=function …`），于是点任何一个 tab 都执行到**页面**的同名方法：

```
修复前：tab x=37/112/187/262/337 → 全部 [Navigate] navigateTo: /pages/ai-result/ai-result
修复后：x=37 → switchTab /pages/index/index    x=112 → 当前页（不导航）
        x=187 → /pages/gift/gift   x=262 → /pages/origin/origin   x=337 → /pages/mine/mine
```

做法：模板引擎展开自定义组件时给子树打归属标记（`parser::template::COMPONENT_OWNER_ATTR`），
标记随 `EventBind` → `EventBinding` 传到宿主，派发时作为 `__dispatchEvent(handler, event, ownerTag)`
的第三个实参；JS 侧先在该组件实例上找，找不到再退回原来的「页面 → 任意组件」顺序。
5 个 tab 页 × 5 个 tab = **25 种组合全部落到正确页面**。

### 2. 覆盖层里的元素点不出反应（问题①③共因）

`handle_click_scoped(fixed_only)` 写的是「全局 `hit_test` 之后再判 `is_fixed`」。
元素表里覆盖层的元素排在**前面**（正常流每帧重建、追加在后），而命中是从后往前找 ——
于是先撞上正常流的元素、再被 `is_fixed` 过滤掉，返回 `None`。
表现是覆盖层里的输入框点不出焦点、开关拨不动，而且**只在「这一帧没重绘覆盖层」时才犯**
（重绘那一帧覆盖层元素刚好被追加到最后），所以偶发得像随机失灵。
改为用 `hit_test_fixed`；`pointer_input` 的按压分支、滚轮命中滚动区的分支是同一个反模式，一并改掉。

```
修复前：--click 100,537（底部输入条）→ 无任何输出，--type 报「当前没有聚焦的输入框」
修复后：📝 Focus: input_25_520 at (25, 520, 272x36) fixed=true
```

### 3. `e.detail.value` 被当成 dataset 强转了类型（问题③根因）

输入事件走的是 `__callPageMethod(handler, {value})`，而 `__callPageMethod` 会对整包数据做
`__coerceDataset`（`data-id="12"` → 数字 12，这对 dataset 是对的）。于是输入 `1212121`
到页面里变成 **number**，`e.detail.value.trim()` 直接 `TypeError: not a function` ——
就是用户日志里 `sendText (eval_script:90:35)` 那一行。

改为原生侧构造完整事件对象走 `__dispatchEvent`，`detail` 不过 `__coerceDataset`：
`input` → `{value:<字符串>, cursor, keyCode}`、`focus` → `{value, height}`、
`blur`/`confirm` → `{value}`。同时补上此前**完全没有派发过**的 `bindfocus`。

```
--click 100,537 --type 1212121 --click 344,538
📝 Focus: input_25_520 …
📝 Input input_25_520: 1 / 12 / 121 / 1212 / 12121 / 121212 / 1212121   ← 每字符一次，与微信一致
👆 tap → [Navigate] navigateTo: /pages/ai-result/ai-result              ← 不再报错
```

顺带修掉同一处的第二个 bug：绑定匹配是「遍历绑定表取第一条 `event_type=="input"` 就 break」，
一个页面有两个输入框时所有输入都打到第一个。现在按**焦点输入框的 `component_id`** 精确匹配。

### 4. `checkbox-group` 的 change 事件发的是布尔值

命中有状态组件后，旧实现用 `renderer.hit_test` 取该点最上层的**任意一条**绑定，
再 `__callPageMethod(handler, dataset)`：不分事件类型、不冒泡、事件对象是 dataset 拼的。
按微信语义重写成：`change` 走 change 链（`checkbox-group` 的 `detail.value` 是**组内选中项的
value 数组**）、tap 走统一的 tap 链，两者可同时发生（把开关包在带 `bindtap` 的 view 里就是）。

```
修复前：点「运动」→ [Error] onHobby: not a function（e.detail.value 是 true，没有 .indexOf）
修复后：已选爱好：阅读、运动、音乐
```

### 5. 惯性滚到边界当场停死 + 回弹是固定时长缓动（问题②的「回弹」）

两处都不是微信/iOS 的做法：

- 惯性撞到边界原来是 `position.clamp()` + `velocity = 0`，**只有「手指拖过界再松手」才有回弹**，
  甩一下滑到底是「咔」一下停住。现在把剩余动量交给弹簧（先冲出去一点再弹回）。
- 回弹原来是 0.3s 的 `cubic ease-out` 且把速度清零。现在换成**带初速度的临界阻尼弹簧**
  `x(t) = (x₀ + (v₀ + ω·x₀)·t)·e^(−ω·t)`（ω=20，落位约 0.35~0.45s，单调收敛不振荡），
  松手速度先经橡皮筋斜率 `c·(1−r/dim)²` 衰减 —— 测到的是手指速度，越界区里内容走得更慢。

```
修复前：pages/mine/mine 甩动 → 滚动 317.0/317.0（直接停死，无过冲）
修复后：滚动 342.2/317.0（冲出 25px）→ 317.0/317.0（弹回精确落位）
```

单测 4 个：`fling_into_bottom_overshoots_then_springs_back`、
`slow_arrival_at_bottom_does_not_overshoot`、`bounce_is_critically_damped_no_oscillation`、
`fling_into_bottom_still_fires_reach_bottom_once`。

### 6. scroll-view 的可滚内容只算了直接子元素

`content_height` 取的是直接子节点盒子的并集。uni-app 的页面结构是
`<scroll-view class="page">` 里放一个 `flex:1` 的容器，那个容器的高度**等于视口**
（它就是用来吃掉剩余空间的），真正超出去的是它里面的内容 —— 于是算出 content == viewport、
`max_scroll == 0`，手势被判成「这个 scroll-view 不可滚」交给页面。
改为按 CSS 的可滚溢出区语义递归求子树并集（自己裁剪的子树、`position:fixed` 子树不计入）。
新增诊断 `MINI_SCROLL_LOG=1 MINI_SCROLL_TREE=1` 打印滚动容器子树的逻辑几何。

### 7. 无头动作脚本：多步交互可脚本化

`--press/--click/--touch/--swipe[-hold]/--drag` 原来是 `snapshot_all` 的六个独立参数、
按代码里写死的顺序各执行一次，「先点 A 再点 B」表达不出来 —— 而输入框相关的回归全是多步的。
现在收敛成一条**按书写顺序执行**的动作队列（`app_window::headless_script`），
并补上 `--type <文本>`（逐字符走真机键盘链路）、`--key <按键>`、`--wait <秒>`：

```bash
./target/release/mini-app-window sample/tea-app --route pages/choose/choose --settle 0.8 --time 2 \
    --click 100,537 --type 1212121 --click 344,538 --wait 0.5 --snapshot target/t
```

### 未复现的一项

「滑动到底部会把底部的遮挡住」在 `pages/choose/choose` 上定位为**小程序自身的留白不足**，
不是引擎问题：页面尾部的 `.bottom-space` 只留 `240rpx = 120px`，而固定输入条
（`bottom: safeAreaInsets.bottom + 108px`、高 `84rpx = 42px`）从视口底往上占到 517px，
需要 150px 才不压住内容 —— 差的 30px 正是 `.direction-card`（370..551）被盖住的那一截。
逐层核对过该页布局与 WXSS 声明一致（`nav 44 + hero 4+125 + chat-area 379 + bottom-space 120 = 672`，
视口 667）。带 `.bar-space`（`150rpx`，够用）的 `pages/shop/detail` 滑到底部实测不遮挡。
底部 tabBar 被内容覆盖的现象未能复现：固定层每帧都在页面之上合成，首页滑到上限截图 tabBar 完整。

## 六之三、实机反馈第二轮（协议弹窗 / 触控板双指）

用户再报三条：① 点「用户协议」弹出的模态框内容溢出、按钮被顶出去；② 协议不能滚动；
③ 触控板双指滑动不像微信那么顺手。定位到 3 个引擎缺陷。

### 1. 弹窗里 `flex:1` 的滚动区被内容撑破（问题①②同因）

登录页协议弹窗是 `.sheet{height:78%}` 里放 `.sheet-head` + `.sheet-body{flex:1}` + `.sheet-ok`。
CSS 里滚动容器的**自动最小尺寸为 0**，所以 `flex:1` 的正文区被压到分配给它的空间、内容自己滚。
我们给 `scroll-view` 保留 `Overflow::Visible`（换成 `Overflow::Scroll` 会让整页画布高塌掉，
见 `layout.rs` 注释），代价是它的自动最小高度仍按内容算 —— 于是正文区被 924px 的协议正文
撑成 732px，把「我已阅读并同意」按钮顶到弹窗外面，而且完全不可滚。

在第二遍布局修正里加了一条（`reflow.rs::release_scroll_min_size`）：**布局算完后**看滚动区
有没有真的溢出父级内容区，溢出就把 `min_size.height` 解除为 0、再跑一遍布局让弹性布局把它
压回去。只看实际几何、不做建树期推断，所以整页那层 `<scroll-view class="page">`（自己 ==
父级、不溢出）不受影响，页面级滚动行为逐字节不变。

```
修复前：scroll-view .sheet-body h=732（撑破）  sheet-ok y=860（在 667 视口外，点不到）
        内容 718 == 视口 732 → max_scroll≈0，不可滚
修复后：scroll-view .sheet-body h=408（被压回）  sheet-ok y=535（弹窗内）
        内容 938 > 视口 407 → 上滑 📦 视口 407.5 内容 938.0，正常滚动
```

### 2. 弹窗正文只有一行、横向冲出（问题①的「内容溢出」）

协议正文是靠内容定宽的文本盒（`text.rs` 里 `max-content` + `flex_shrink=0` 那条路径），
在纵向排布的父级里会一路横向溢出 —— 实测协议正文 674px 宽、只有 1 行，品牌页「品牌故事」
正文更是 1414px 宽。浏览器里这段文字的宽度来自交叉轴（`align-items:stretch`），到容器边折行。

`reflow.rs::fix_text_box`：布局后发现文本盒比父级内容区还宽，就收到父级宽度并按新宽度重算
行数补高。只收拾「确实比父级还宽」的定宽文本盒，带背景/边框的短标签、徽章不受影响
（它们本来就没超过父级）。tea-app 仅 `brand`、`subscribe` 两页变化，都是长正文从「一行冲出去」
变成「按容器宽正常折行」的改进。

### 3. 触控板双指滑动不顺手（问题③）

滚轮/触控板路径此前是「命中点最内层的 scroll-view 无条件接管」，与拖动路径的仲裁完全脱节，
三个后果在触控板上尤其明显：

- **不可滚也接管**：tea-app 整页套一层 `<scroll-view class="page">`（`max_scroll==0`），
  双指滑动全被它吞掉，只在原地橡皮筋、60ms 后弹回，**页面一动不动** —— 这就是「不顺手」的主因；
- **主轴不锁**：光标停在横向卡片列表上时纵向滑动被那条列表按 `delta_x` 吃掉，页面不动、列表还横向抖；
- **到边界不传递**：内层滚到底后继续推不接着滚页面。

把滚轮路径抽成 `events::wheel`，与拖动用**同一套仲裁**：按本次事件的主轴锁定方向、由内到外
找第一个「轴匹配且没顶在边界」的滚动区、都吃不下就落到页面；精密位移（触控板）1:1 跟手。
5 个单测覆盖：不可滚壳交给页面、纵滑不驱动横向列表、横滑只滚列表不滚页面、内层到头链式传给页面、
遮罩上页面锁定但覆盖层内 scroll-view 仍可滚。

```
修复前：tea 首页双指纵滑 → scroll-view_0_0 接管，页面滚动 0.0/202.0（不动）
修复后：🖱 scroll-view_0_0 吃不下这次滚动（max_scroll=0）→ 交给外层，页面 0→202
```

无头复跑加了 `--wheel x,y,dx,dy[,步数]`（触控板）与 `--wheel-lines`（普通滚轮），
走与交互窗体完全相同的 `MouseWheel` 分支。
