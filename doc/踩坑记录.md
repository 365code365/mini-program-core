## 远程图片必须异步加载

`<image src="https://…">` 曾经是在**绘制期同步** `ureq::get` 的 —— 渲染线程直接卡在 HTTP
往返上。实测 tea-app 首屏背景图 276KB / 3.2s，也就是那一帧卡 3.2 秒；长列表里每滚出
一张新图就再卡一次。**这是「很多页面滑动很卡」的直接原因**，跟布局、光栅化都无关。

而且失败结果被永久缓存成 `None`：网络抖一下，那张图这辈子都不会再出现（「图片没展示」）。

`src/renderer/components/image_net.rs` 改成和浏览器一致的三段式：

- 绘制期**只查表**，没有就登记「下载中」并立刻返回（本帧画占位），永不阻塞；
- 后台线程下载 + **解码**（解码大图同样贵，不能放回渲染线程），完成后置脏，宿主重绘一帧；
- 失败带**退避重试**（2s 起翻倍，上限 30s，最多 4 次），不再一次失败终身失败；
- **磁盘缓存**（`target/mini-imgcache/`，URL 哈希命名 + 先写临时文件再重命名）：
  同一张图第二次打开 6132ms → **11ms**。没有它，tea-app 那张 6 秒才下完的闪屏背景
  永远来不及在 5 秒的闪屏里出现。

有个配套细节容易漏：宿主必须在「有图在下载」时保持出帧、在「图下载完」时置脏重绘，
否则图片下完了也要等下一次别的原因触发重绘才显示。

## page 选择器与绝对定位的包含块

两个让 tea-app「差距有点大」的渲染语义缺口：

- **`page` 选择器之前完全被忽略**。页面底色写死 `#F5F5F5`，文字继承从内置默认值起步。
  于是在 `page` 上定义暖米色底（`#f7f3ec`）+ 宋体 + 字号的应用，整体色调与字形全对不上。
  现在 `page` 的 `background-color` 作为清屏色与画布外填充色，`color / font-size /
  font-weight / line-height / letter-spacing / text-align` 作为继承链的起点。
- **`position:absolute` 且没有定位祖先时，百分比高度按视口折算**。CSS 规则是「包含块为
  最近的定位祖先，没有则是初始包含块（视口）」，而布局引擎只按父节点解析百分比 ——
  父节点是 auto 高度时 `height:100%` 直接塌成 0，整屏铺底的背景图就此消失。

> 这两条里第二条我先做过头了：一开始把**宽度**也按视口折算，结果 canvas 页与组件页
> 与 H5 的差异从 5.4%/3.8% 恶化到 12.5%/10.2%。原因是元素的 `left/top` 偏移仍然相对父
> 节点，只改尺寸不改偏移，窄父节点里的绝对定位元素就会「变宽但不移位」。
> 还试过补一趟「根高度换成确定值」的布局来给百分比提供参照物，那会改变 flex 的分配规则，
> 同样两页整页错位。两次都靠**逐字节快照基线**当场发现并回退了 —— 最终只保留
> 「无定位祖先时按视口折算高度」这一条最小改动，15 页快照与基线逐字节一致、双端差异不变。

## 网络与缓存：让「拉数据 → 存起来 → 下次走缓存」真的成立

`wx.request` 之前是**完全没有实现**的（`ureq` 只用在图片加载上）。现在补齐：

- `src/net.rs`：请求切成「提交 → 后台线程跑 → 宿主按帧取回」三段，**不阻塞 JS 线程**。
  响应回来后由 `MiniApp::update()` 喂给 `__resolveRequest`，所以 `Promise` 链、
  `async/await` 都能正常推进（它们靠微任务队列，宿主每帧 pump 一次）。
- 微信语义逐条对齐：**4xx/5xx 仍走 `success`**（只是 `statusCode` 不是 2xx）、
  GET 的 `data` 拼进 query、`dataType` 缺省 `json` 且解析失败就原样给字符串、
  `header` 原样透出、`RequestTask.abort()` 之后不再回 `success` 但仍调 `complete`。
- `wx.setStorageSync` **跨启动持久化**（`src/storage_file.rs`，写到
  `target/mini-storage/<小程序名>.json`，按小程序隔离且**不写进 `sample/`**）。
  之前只有进程内的 HashMap，于是每次启动都是空的 ——
  任何「首次拉取存起来、之后走缓存」的逻辑永远只走首次分支，缓存代码等于从没执行过。
- `getSystemInfoSync` 补全 `safeArea` / `safeAreaInsets` / `statusBarHeight` 等字段
  （以及拆分出来的 `getWindowInfo` / `getDeviceInfo` / `getAppBaseInfo`）：
  这些是布局算式的输入，少一个就是一个 `cannot read property 'bottom' of undefined`。

网络语义有 6 个**离线**回归测试（`src/tests/network_tests.rs`）—— 直接调
`__resolveRequest` 模拟原生回调，不依赖外网，所以能进 CI。诊断开关
`MINI_NET_LOG=1` 打印每条请求的方法/URL/状态码/耗时，`MINI_STORAGE_LOG=1` 打印缓存读写。

补上这两块之后 tea-app 的表现变化很直接：首屏倒计时会真的走到 0 并
`switchTab` 进首页，首页从 3384 色（占位方块）变成 85860 色（真实照片）。

> 顺带修掉一个「排查时会把人带偏」的问题：`--frames` 跑帧时不冲 JS 输出缓冲，
> 也不处理导航请求。于是定时器/网络回调里的 `console.log` 全攒在缓冲里看不到，
> 靠时间驱动的跳转也只在日志里出现、页面其实没换 —— 看起来就像「回调没跑」。

**当前边界**：tea-app 是 uni-app x(UTS) 的产物，它的资源缓存工具在**首次运行**
（storage 为空）时会对 `''` 调 `.toMap()` 而抛异常 —— 那是 UTS 的 API，
微信的 `getStorageSync` 读不到时返回 `''`。按「对齐 Skyline」的原则这里不迁就：
**引擎不为偏离微信语义的写法让路**。所以它的首次运行仍会命中这个应用侧的问题，
第二次运行起（缓存已落盘，`getStorageSync` 返回 uni 包装过的 `UTSJSONObject`）一切正常。

## 页面内的自定义组件（`usingComponents`）

`<tab-bar/>` 这种页面 json 里声明的自定义组件，以前落到「未知标签」的兜底分支被当成空
`view` —— **整条底部导航（图标 + 文字）在原生端凭空消失**。而 uni-app / Taro 编译出来的
产物普遍把 tabBar 做成页面内组件（Skyline 下 tabBar 也推荐自绘），所以这不是个别写法。

打通它需要四段：

- **加载**（`src/using_components.rs`）：按页面 json 递归读组件三件套（组件自己也可以再
  声明组件）。样式做**单向隔离** —— 组件 WXSS 的每条选择器前缀成 `<标签名> …`，
  `:host` 改写成标签本身。`.icon` / `.label` 这类通名不做隔离会直接污染页面。
- **展开**（`TemplateEngine::render_with_components`）：保留一个以组件标签命名的宿主节点
  （承载使用方写在标签上的 class/style，也让 `:host` 与作用域前缀有落点），
  子树用**组件实例自己的 data** 求值 —— 组件的 `{{a}}` 与页面的 `{{a}}` 是两套东西。
- **实例**（`src/host/component_mount.rs` + `__mountPageComponent`）：以「组件路径」为键执行
  组件 js（`Component()` 借此注册到该路径，而不是把当前页面顶掉），再建实例。实例必须真的
  建出来：框架型产物是在 `attached` 里挂载自己的组件树并触发首次 `setData` 的，
  没有实例的话组件模板里全是空值。使用处的属性按微信规则转成组件属性
  （`u-p` → `uP`、`u-i` → `uI`，dashed → camelCase），uni-app 的 props 就是这么传的。
- **事件**：处理函数可能挂在页面上，也可能挂在组件实例上，`__callPageMethod` 两边都找。
  只找页面的话点了没反应 —— 底部导航点不动就是这个原因。

> 一个连带的大坑：`class="{{['tabbar', d]}}"` 是 uni-app **每个组件/页面根节点**的固定写法
> （`d` 是虚拟宿主类名）。通用插值会把它渲染成字面量 `['tabbar','']`，于是
> `.tabbar` / `.root` / `.page` 这些根节点样式**一条都命中不了** —— 底部导航既没有
> `position:fixed` 也没有背景，整页配色也对不上。现在 `class` / `style` 绑定到数组或对象时
> 按 CSS 语义拼接（空格 / 分号）。

## `font-family` 曾经被整条忽略

全局只有一个系统主字体（macOS 上是黑体系的 PingFang / Hiragino Sans GB），
于是所有声明宋体/衬线的文字都画成黑体。对以「书卷感」为设计语言的应用来说，
这是第一眼就能看出来的差别（tea-app 的品牌名、导航文字、正文全都指定
`"Songti SC","STSong",serif`）。

`src/text_family.rs` 按浏览器的规则解析：**字体栈从左到右取第一个「本机存在」的字族**，
通用族兜底（`serif` → 宋体、`monospace` → Menlo、`sans-serif` / `system-ui` → 默认字体）。
`"Playfair Display","Times New Roman",serif` 在 macOS 上就落到 Times New Roman ——
与浏览器一致，因为 Playfair 确实没装。

- 每个字族一份 `TextRenderer`（自带字形缓存），按规范化后的字体栈字符串缓存，
  同一条 `font-family` 只解析、只加载一次；
- 缺字形时**逐字回退**到系统默认字体：`"Times New Roman"` 没有汉字，
  不回退的话中文全是豆腐块；
- `font-family` 是继承属性，`page { font-family }` 作为整页基线；
- **度量与绘制必须用同一族**：字形宽度、自然行高都随字体变，
  用默认字体量、用宋体画的话盒子和文字对不上，还会误换行。
  所以 `TextMeasure` 带上字体栈，taffy 的度量闭包、二次换行修正、裸文本节点全部按它取字体。

诊断：`MINI_FONT_LOG=1` 打印每条 `font-family` 解析到了哪个字体文件。
另见[架构文档里的「字体按文件缓存」](架构与实现原理.md#触控与事件按-skyline-对齐)一条 ——
同一个 63.8MB 的 `Songti.ttc` 曾被解析多遍，首帧白付 2 秒多。

## 绝对定位的包含块高度塌成 0

```text
.page { flex: 1; position: relative }   /* 子节点全是绝对定位 → 没有在流内容 → 高 0 */
.background { position: absolute; inset: 0; width: 100%; height: 100% }
```

微信/Skyline 里页面根节点就是视口高，`.page` 因此是满屏的；而我们的布局根是
`height: auto`（内容高驱动滚动），于是这类「整屏铺底」的写法整屏塌掉：
闪屏页的背景照片不见了、文案全挤在顶部。

建树期已经处理了「一个定位祖先都没有」的情况，现在补上「有定位祖先、但它的使用高度是 0」：
`correct_absolute_heights` 在**布局之后**按实际使用高度判断，塌成 0 就退回视口高度，
并顺带处理 `top`/`bottom` 都给了而高度 auto 的情况。放在布局之后是必须的 ——
「包含块的使用高度」只有布局算完才知道。

## 页面根缺一条 `min-height: 100vh`

上面那条补的是「绝对定位」的包含块，还有一半没补：`flex: 1` 的容器。页面根是
`height: auto`，`.page{flex:1}`（框架产物的标准结构）于是只有内容高，写了
`justify-content: center` 也没得可居中。表现分三档：

- 内容比一屏矮一点 → 底下漏出 `page` 的背景色（tea-app 登录页底部露出 12px 浅米色）；
- 空状态页 → 「购物车还是空的」「下单成功」这类本该垂直居中的内容全贴在顶部；
- 整页只有绝对定位/`flex:1` 子节点 → **整页空白**（tea-app 的认养成功页就是白屏）。

编译出的 H5 端一直是对的（`#app{min-height:100vh}`），原生端漏了。现在布局根加上
`min_size.height = 视口高`：内容比一屏高时照旧由内容驱动（要能滚），矮时至少一屏。
sample-app 15 页与 news-app 6 页零像素变化（它们本来就比一屏高），tea-app 修好 7 个页面。

## 子节点的样式必须算它自己的

三个「样式被父节点吞掉」的 bug，是拿 tea-app 登录页对着微信截图一格一格量出来的：

| 问题 | 现象 | 原因 |
|------|------|------|
| `page{font-size}` 继承时被乘了一次 `scale_factor` | @2x 真机上所有靠继承的文字**大一倍**（登录页「微信一键登录」28px vs 设计稿 15px） | `InheritedText` 里的文字度量是逻辑像素，而 `page_style.rs` 写成了 `v * sf`。当年的单测用 `scale_factor=1` 建渲染器，正好把它盖住 —— 现在那条用例改成 @2x |
| `<button>` 被当成叶子 | 里面 `<text class="wx-btn-t">` 写的 `color:#fff; font-size:30rpx` 全失效，按钮用继承来的深色画了一遍文字 | 微信里 `button` 是普通容器。现在「带元素子节点」的按钮按容器建树，文字交给子节点画；`<button>纯文字</button>` 仍走叶子那条成熟路径 |
| `<text>` 里嵌套 `<text>` 被拍平 | 优惠券的 `¥<text class="c-num">10</text>` 整段都是 32rpx，而 `.c-num` 写的是 64rpx（应该 ¥ 小、数字大） | 现在按 `rich-text` 同一套做法：容器改成「行内排列 + 允许换行 + 基线对齐」，混排内容切成 run（裸文字用外层样式、嵌套 `<text>` 用自己的 CSS），每个 run 再按可换行单元细分。子元素里有 `<image>` 这类非文本时退回拍平 —— 本引擎没有真正的行内流，硬拆会把图文拆成上下两行 |

顺带修掉两个更小的：`<input>`/`<textarea>` 自己画盒子，从来没画过**逐边边框**，
于是「下划线式输入框」（`border-bottom: 2rpx solid …`，表单最常见的写法）在引擎里完全看不见；
以及 HTML 编译器的漂亮打印会在 `<text>` 内部插入缩进换行，而 `.wx-text` 带
`white-space: pre-line` —— 浏览器把它当**真实换行**渲染，优惠券的「¥10」在 Chrome 里被拆成两行。
后者还会污染双端对比的基线（参照物自己先错了），修完 coupon 页差异 4.91% → 4.49%。

## 异步图片到位时必须整帧重绘

远程图片下载完成属于「内容变了但数据没变」，`setData` 的失效范围算不出它。
于是在**每秒都有 setData** 的页面上（闪屏倒计时、首页秒杀），增量范围只覆盖那一小块文字，
刚到位的图片永远不会被重画 —— 表现就是图片一直停在占位图。现在
`image_net::take_dirty()` 会把这一帧标记成强制整帧。

> 同一个问题在快照工具里还有一层：`--settle` 从前只 `update` 不出帧，
> 而**异步资源是绘制期才发起的**（绘制到 `<image src="http…">` 才知道要下载它），
> 等待的那几秒里根本没人发起下载。现在 `--settle` 跑的是完整的一帧（与交互窗体同一套闸门），
> 截图前再补一帧。`MINI_IMG_LOG=1` 下画占位会打印 src，
> 用来区分「还在下载 / 下载失败 / src 为空」这三种完全不同的原因。

## 颜色的 alpha 曾经被整条丢掉

`rgba(…, .55)` 一律画成不透明色 —— 半透明遮罩、淡出、发丝描边全糊成实色块。
tea-app 首页 banner 上那道横线就是这么来的：`.hero-wash-fade` 是
「顶部 55% → 底部 0%」的淡出，解析成两个不透明色标之后变成一块实色，
在它结束的地方留下一条硬边。

根因是**同一份颜色语法有四个入口各写一份实现**：WXSS 声明、内联 `style`、
渐变色标、canvas `fillStyle`。其中两份把第四个分量直接扔了。现在统一到
`components::color_parse` 一处（`#rgb`/`#rgba`/`#rrggbb`/`#rrggbbaa`、
`rgb()/rgba()` 的逗号式与 `r g b / a` 新语法、百分比通道、常用命名色），
WXSS 解析器改成薄封装调它。

同一批修的还有两个「值被空白切碎」的问题：`border: 2rpx solid rgba(0, 0, 0, .04)`
和 `box-shadow: 0 8rpx 24rpx rgba(76, 52, 29, .06)` 以前直接 `split_whitespace()`，
`rgba(0,` `0,` `0,` `.04)` 四段残片全都解析失败 —— 边框退回默认灰、阴影退回
50% 纯黑。现在按**括号感知**的空白切分（`split_top_ws`）。tea-app 里这类声明有 83 条。

## `letter-spacing` 会让文字凭空少一行

盒子宽度按内容宽定，断行算法却用另一把尺子量：`measure_text_weighted` 按
`(n-1)` 份字间距算，断行按 `n` 份算。于是「刚好装下」被判成「装不下」，
最后一个字掉到第二行，**盒子高一倍**。

Chrome 实测 `letter-spacing:10px` 的 4 字符 inline-block 正好宽 40px（不是 30px）——
CSS 把字间距加进每个字形的前进宽度，末字符也算。按这个口径统一之后：
tea-app 首页 `.brand-cn` 不再变成两行，被它挤出定高导航栏的 `PHOENIX YUNXIU`
也回来了。（sample/news 两个示例不用 letter-spacing，15 页快照逐字节不变。）

## 滑动帧成本：先量出来，再改

滑动手感只有**连续拖动**才测得出来，而快照永远只出一帧。所以先加了两件工具：

```bash
# 模拟手指拖动并逐帧计时（每帧上移 8px，共 60 帧）
./target/release/mini-app-window tea-app --route pages/category/category \
    --settle 2 --drag 8x60 --snapshot target/drag
# 🖐  pages/category/category：60 帧，单帧耗时 平均 5.32ms  p50 5.49ms  p95 8.89ms  最慢 9.94ms
#    ↳ 最慢一帧 9.94ms 的渲染构成：页面 9.71ms  覆盖层 0.32ms  tabBar 0.00ms

MINI_DRAW_LOG=1 ...   # 再按组件类型/绘制阶段摊开耗时
#    ↳ 绘制归因（合计 523.9ms）：view 188.2ms/2346次  image 121.0ms/832次
#      背景:圆角填充 102.8ms/460次  背景:边框环 79.3ms/646次  text 19.5ms/1620次
```

有了归因，三个热点一目了然（也说明**先量再改**为什么值得）：

- **`box-shadow` 用 12 层半透明圆角矩形叠出模糊**：`0 8rpx 24rpx` 在 2 倍屏上
  blur=24px → 12 层，每层都要把整张卡片面积做一遍带抗锯齿的路径填充，
  一张卡一帧 140 万次像素混合。改成 CSS 的做法：把阴影形状画成 8 位覆盖率掩膜、
  可分离盒式模糊三遍逼近高斯（σ = blur/2），**掩膜按几何尺寸缓存**，
  每帧只剩一趟乘加合成（`components::shadow`）。与 Chrome 的剖面差在 3~10/255 之间。
- **抗锯齿路径填充横扫整个包围盒**：`border` 的圆角描边是「外圈套内圈」的环形路径，
  中间是空的，而填充器逐像素扫过 662px 宽的卡片，其中 650+ 个像素算出覆盖率 0。
  改成**按扫描线区间遍历**（合并各子扫描线的区间，同一像素只访问一次），
  输出逐像素不变 —— 分类页这一项 354ms → 79ms。
- **渐变逐像素投影 + 查色标**：实际用到的渐变几乎全是轴对齐的，垂直方向同一行同色
  （整行一次填充）、水平方向所有行同色序列（只算一行，其余行整行复用），
  只有圆角波及的那几行退回逐像素（`components::gradient`）。
- scroll-view 从离屏缓存上屏是逐像素 `set_pixel`（一屏一百万次带边界+裁剪判断），
  改成按行成片拷贝、整行不透明时退化成 memcpy。

tea-app 十个页面的拖动帧（60 帧一次，取平均/最慢）：

| 页面 | 改前 | 改后 |
| --- | --- | --- |
| 首页 | 7.17ms / 最慢 11.6ms | **3.74ms / 10.0ms** |
| 产区选茶 | 9.76ms / 最慢 14.0ms | **5.32ms / 9.9ms** |
| 我的 | 8.95ms / 最慢 11.4ms | **2.49ms / 6.9ms** |

其余页面 0.09~5.74ms。全部落进 60Hz 预算，多数落进 120Hz 预算；
最慢帧仍会碰到 144Hz 的 6.94ms 上限 —— 因为拖动时整屏内容仍在逐帧重新光栅化，
而 Skyline 那边滑动是纯合成。下一步是把 scroll-view 的内容也纳入离屏缓存复用。

## 导出的 HTML 每次编译都不一样

`WxmlNode::attributes` 是 `HashMap`，转译时直接 `for (k, v) in &node.attributes` 往
标签上拼 `data-ds-*`。`HashMap` 每个实例的哈希种子不同，于是**同一个二进制连跑两次**，
属性先后就会变 —— 实测 `sample-app` 有 5 个页面文件在两次编译之间不一致。

浏览器不在乎属性顺序，所以功能上看不出来；代价是**导出产物没法做逐字节回归**：
拆 `transpile.rs` 时我想拿「导出结果一模一样」当搬迁的证据，结果发现基准自己就在抖。

修法是给节点加一个排序遍历入口 `WxmlNode::attrs_sorted()`，凡是遍历顺序会进输出的
地方都走它（转译的事件/dataset、组件挂载拼属性、事件绑定列表）。往 `HashMap` 里插入
的场景不受影响，那些本来与顺序无关。

守这条的测试：同一份 WXML 解析 8 遍（8 套独立的 HashMap、8 个种子）转成 HTML，
结果必须只有一种。把 `attrs_sorted()` 换回原来的写法，这条立刻红。

## Flutter 宿主改尺寸时，旧画面被拉伸一帧
现象：Flutter 例子里从普通页面进 `navigationStyle: custom` 的页面，整页先放大一下再弹回来（「抖」）。
录屏逐帧看（Android 模拟器，`adb shell screenrecord` + `ffmpeg -fps_mode passthrough`）：AppBar 消失、
视图从 786 变高到 866 之后，有一帧是**旧的 786 高画面被拉伸到 866**（卡片位置整体 ×1.1），下一帧才是
新尺寸的画面。引擎每一帧都是对的，问题在插件的时序：`resize` 先把新尺寸回给 Dart，Dart 按新尺寸重建
`Texture`，而新尺寸的那一帧要等下一个 vsync 才写进纹理 —— 中间那一帧 Flutter 只能拿旧纹理去填新盒子。
修法：先把新尺寸的那一帧写进纹理（Android 写进 Surface 但不通知 Flutter；iOS 换上新 buffer 但先不发
`textureFrameAvailable`），再回尺寸，让「盒子变大」与「换上新画面」落在同一个 Flutter 帧里。修完再录：没有拉伸帧。

还剩一个**插件修不了**的（已知差距 G-24，后来改成引擎画导航栏解决：Flutter 宿主默认 `navigationBar: true`，切页不再改尺寸）：引擎先按旧尺寸把新页面画出来，宿主看到 `page` 事件才知道
这页不要导航栏、才去改尺寸，于是 position:fixed 的底部按钮栏有约 90ms 停在离底边 80px 处，然后落下去；
这一页 `onLoad` 里读到的 `windowHeight` / `safeArea.top` 也还是改尺寸之前的值。

## 侧滑返回露出一片黑、返回后回到顶部
同一轮在模拟器上发现的两条，都与「宿主改了尺寸」或「回到上一页」有关：
- **侧滑露黑**：上一页的视口图是它被盖住那一刻留的（786 高，AppBar 下面）；进 custom 页后视图变成 866，
  `edge_back::compose` 见图和帧尺寸对不上就整条画暗底。修法：`resize` 时把留着的图按**底边对齐**改高
  （高度变化来自顶上的 AppBar，上一页在屏幕上正好是下面那一截），多出来的顶上一条填那一页的导航栏颜色，
  变矮就从顶上裁；宽或像素比变了（转屏）才丢图。见 `engine_resize.rs::refit_back_shots`。
- **返回回到顶部**：`pop_page` 无条件新建 `ScrollController`。微信里上一页的实例一直活着，滚到哪停在哪。
  修法：页面被盖住时把（位置, 内容高）记在 `PageInstance::saved_scroll`，返回时按它恢复（内容高先按存下的给，
  `max_scroll` 才不会把位置夹成 0）。SDK 与桌面窗体同一个 `PageInstance::restored_scroll`。
判据：`tests/page_return_e2e.rs`（滚到 600 → 进下一页 → 返回仍是 600；改高之后侧滑，露出来的是压暗的上一页、顶上是它的导航栏色）。

## 快速滑动时一条底色横线（局部重画清多一行）

现象：荣耀真机（dpr 3）上快速来回滑，绿按钮、横幅中间一闪一条 1px 的浅灰线；白卡片上看不出来。
录屏逐帧（`screenrecord` + ffmpeg）对比：滚动本身没有撕裂，线是页面底色 `#f5f5f5`，横穿整块内容、线上下颜色一样。
原因：局部重画（补条带、动画损伤区、setData 损伤区）是「`clear_area` 清掉这块 → 裁剪到这块重画」两步。
`clear_area` 按 `pixel_rect` 向外取整（上沿 floor、下沿 ceil），`Canvas::clip_rect` 的下沿却是截断的。
矩形边落在半个像素上时，最后一行被清成底色、又不在裁剪区里，没人重画。dpr 3 加上松手惯性的小数滚动位置，
补条带的边几乎每帧都落在小数上。dpr 2 + `scroll_to` 整数滚动的旧用例永远测不出来。
修法：`geometry::snap_out` 先把矩形扩到整像素，清屏与裁剪用同一个矩形（SDK `engine_frame.rs`、桌面 `frame_render.rs`）。
判据：`tests/sdk_damage_equivalence.rs` 的 dpr 3 小数滚动用例（修之前第 55 帧屏幕第 93 行局部 #f5f5f5、整帧 #ffffff）。

## 120Hz 真机上「触控卡、不跟手」：点击态逼出的整页重画

现象：一加 PLY110（120Hz、中端 SoC）上每次手指按上去、每次松手，页面都顿一下；桌面基准一切正常。
真机 `debug.mini.damage_log` 一看：一次滑动测试 97 帧 `整帧·结构`，每帧 20~30ms。
原因：点击态（`hover-class` / `:active`）一律走 `needs_redraw`。按下那一帧整页画一次；`hover-start-time`
等出现的那几十毫秒里 `press_feedback_pending` 让**每一帧**整页画；松手后 `hover-stay-time` 里又是每帧整页 ——
正好压在惯性的头几帧上。拖页面时内容跟着手指走，手指一直在那一行里，点击态也一直不撤。
桌面基准测不出来：基准的拖动第一步就超过手势阈值，点击态还没出现就被取消了；真机 `input swipe` 按下后要隔几帧才开始动。
修法：`engine_press.rs` 每帧比对「画成点击态的元素」，变了只重画它们自己的盒子；被滚动接管时 `cancel_press()`。
普通 bindtap 的点击也不再整页重画（setData 走失效分析，弹层只重新合成）。
排查方法留下来了：`MiniEngine::mark_full` 记调用位置，`MINI_DAMAGE_LOG` 的 `整帧·结构` 行末尾就是源码行号。

同一轮还有两处「逐像素算完再被裁剪拒掉」：斜向渐变（首页横幅）与圆角边框整张元素逐像素算，补条带只裁一条，
一趟 10~17ms。改成先收窄到 `Canvas::draw_bounds()` 再循环，结果逐字节不变。

## GPU 选上了，弹层反而比 CPU 慢
现象：一加 PLY110 上 GPU 自动选上后滚动、转场都快了，ActionSheet 弹出却一帧 10~20ms（CPU 后端 6.8ms）。
原因：Toast / Modal / 操作菜单 / picker 是直接画进输出缓冲的（读目标像素、带浮点），GPU 复刻不了逐字节，
这些帧走「直通」：CPU 整帧合成 + 整帧 10MB 上传。比 CPU 后端多出一次上传，还少不了一次合成。
修法：覆盖层画的时候报出自己写了哪几行、遮罩用的哪张表（`compositor::Footprint`）；行区间外 = 基础帧逐分量查表，
着色器自己算（表由 CPU 用同一个算式算好，着色器不做浮点）。只有那一截要 CPU 合成、上传。
两个坑：① 操作菜单按墙上时钟动画，「先算范围、再画」两次各取 `Instant::now()` 会对不上 —— `reach` 定住那一刻，
紧接着的 `render` 按同一刻画；② Modal / picker 的遮罩画在操作菜单**之后**，要连菜单白底一起压暗，
这时不能只给「要底图的行」压暗（GPU 单测第一次就抓到：@0,333 CPU #666666 / GPU #ffffff）。
## 慢慢拖页面一顿一顿（帧率是满的）
现象：120Hz 上快甩很顺，慢拖反而一顿一顿；`MINI_FPS` 显示每帧都按时出了。
原因：Flutter 的触摸要过 Dart → 平台线程 → 引擎线程，一帧里到几个移动事件是碰运气，页面按「最后到的那个」走：
这一帧挪两格、下一帧挪零格。慢拖每帧只挪一两个像素，这点不均匀肉眼就看得出来。
修法：移动事件带上它自己的时间戳（与 `pump` 同一个单调钟），每帧取「现在 − (一帧 + 5ms)」那一刻在前后两个采样之间插值
（`engine_resample.rs`）。往回取一帧换来的是这一刻前后的采样几乎一定都到了。松手速度仍按原始事件算。
帧间隔估计要「往小立刻跟、往大慢慢跟」：拖起来之前常是隔帧 pump，按 16ms 估的话一开头多落后一帧。
## 回归脚本「全绿」但一张也没比
`tools/sdk-parity.sh` 在基线目录不存在时 `find` 一张也找不到，打出 `一致 0 / 不一致 0 / 缺图 0` 和绿勾。
清理完 `target/` 直接跑就是这样。现在 0 张时直接失败，并提示先跑 `snapshot-all.sh`。
另：`interaction-check` 的 `slider_hold` / `slider_drag` 两条落在 showcase 页的 GIF 上（包围盒 x[616,698] y[465,548]），
GIF 按墙上时钟换帧，同一个二进制连跑几次就有 0.22% 的差异 —— 与 gallery 的 `35_gif_frame4` 同一类噪声，看包围盒判断。
## 帧耗时全达标，屏上照样一顿一顿（Flutter 外部纹理）
现象：`MINI_FPS` / `MINI_DAMAGE_LOG` 里每帧都在预算内、每帧位移也均匀，真机慢拖还是一顿一顿。
原因：引擎画进 Flutter 的外部纹理（SurfaceProducer），屏上那一帧是「Flutter 光栅线程取纹理那一刻队列里的那张」。
引擎线程每个 vsync 都按时交了，可 Flutter 自己的帧跑在主线程上（3.29 起 UI 线程与平台线程合并），主线程一忙，
Flutter 这个 vsync 不出帧，屏上重复一张。一加上 vsync 后 10~13ms 才开始光栅的帧不少见。
怎么看出来的：引擎打 `🎞`（交帧时刻）、Dart 打 `🎞F`（`FrameTiming` 的光栅开始），`tools/pace-check.py` 对起来；
再用 `dumpsys SurfaceFlinger --latency '<层名>'` 看屏上那一层每次上屏的时刻 —— 后者不靠 App 内日志，最可信。
修法：Android 上引擎画到自己的 SurfaceView（平台视图，hybrid composition），系统合成器直接取引擎交的每一帧。
## 动画按「画的那一刻」取样
操作菜单、picker 面板、`@keyframes` 从前在画的时候取 `Instant::now()`。画的时刻相对 vsync 忽早忽晚（这一帧 1ms 后、
下一帧 4ms 后），屏幕却按 vsync 匀速换帧：入场头几帧每毫秒挪 7 个物理像素，差 2ms 就是 14px 的抖。
现在 SDK 每帧按宿主给的 vsync 时间取样（`frame_clock.rs`）。两个坑：① 帧时刻要在 pump 结尾清掉 ——
两帧之间的触摸按「此刻」记起点，留着上一帧的时刻，静止十秒再点一下过渡就直接走完；② CSS 动画时钟的起点要钉在
不晚于第一帧的地方，否则 `帧时刻 − 起点` 为负、截成 0，动画定住。另：`tests/embed_host.rs::css_无限动画逐帧出新画面`
有约 15% 的偶发失败，这一轮之前（7a42620）就有、与帧时钟无关，还没查清。
## 松手速度按到达时刻算，慢拖一松手就「飞」出去
事件过两道线程才到引擎，常常几个一批地到：按到达时刻算，最后 100ms 的采样挤在一两毫秒里，速度是真实值的十几倍
（一加慢拖每帧 2.3px，松手第一帧 44.5px）。手势推进改按事件时间记（`engine_resample.rs::gesture_clock`）。
## 真机测试脚本的三个坑
- `while read L; do adb shell …; done < 列表`：adb 会吃掉 stdin，循环只跑一遍。循环里的 adb 一律 `</dev/null`。
- Android 清单的 XML 注释里不能出现两个连续的减号（写了 `simpleperf record` 的命令行参数就整个清单解析失败）。
- ColorOS 上 App 日志量大了之后会整段静默（`logcat` 里一个字都没有），节拍分析别只靠 App 内日志，用 SurfaceFlinger。
## 复杂页面一滑就顿：线程在小核上
- 引擎线程每个 vsync 醒一次、干几毫秒就睡，调度器按利用率把它放在小核（一加 SM7635 抽样 92% 在 0~3 号 A520）。
  桌面 0.3ms 的补条带手机上 5~11ms，越复杂的页面越顿。查法：`cut -d' ' -f39 /proc/<pid>/task/<tid>/stat` 连抽几百次看落在哪个核。
- ADPF（`PerformanceHintManager`）会话建成了（`dumpsys performance_hint` 能看到）也没把线程挪走；`Session.sendHint` 不在公开 SDK 里。
  真正管用的是 `sched_setaffinity` 绑掉最慢一簇（`host/cpu_affinity.rs`）。
## 回桌面再回来白一下
- ColorOS 上 `SurfaceView.setSurfaceLifecycle(FOLLOWS_ATTACHMENT)` 不管用，回桌面照样 `surfaceDestroyed`。
- 从前卸 surface 就扔掉整个 GPU 合成器，回来重开 Vulkan 设备 + 自检要 490ms，`detach` 与 `on_show` 还各要一次整页重画。
  现在合成器只放 surface、停着等下次挂（`gpu_parked`），画布不重画只重新合成。
## 真机测速的两个坑
- **构建和安装不能并行**：引擎库、`flutter build apk`、装包放在同一批里同时跑，gradle 会把旧库打进去、或者装上的是上一个 APK，
  量出来的「对比」其实是同一份代码。`tools/android-jank.sh … install` 现在先比 APK 里的库与 jniLibs 的可执行段。
- **simpleperf 符号化**：`--sort symbol` 给的 `libmini_render.so[+偏移]` 直接对 `llvm-nm -n` 未 strip 库的地址（不加段偏移），
  前提是装上的库就是那一份 —— 对不上时出来的全是 rav1e / png 之类不相干的函数。
- 截屏（`screencap`）截不到引擎那块 SurfaceView（ColorOS），看画面用桌面无头快照或引擎 `dumpFrame`。

## 转场动画开头一顿
- 动画时钟从「开始那一帧的 vsync」起算的话，开始那一帧本身很贵（建页 20ms+），第二帧来时已经过了两三个周期，
  减速曲线起手最快 —— 第一步就是后面的两三倍。页面转场改成按帧推进（`route_anim.rs` `StepClock`）。
  只按「刷新周期估计」补第一步也不行：页面静止时 ColorOS 把屏降到 60Hz，估计还是 17ms。
## 事件回调里的 setData 不要 `mark_full`
- `onPageScroll`、IntersectionObserver、swiper 翻页事件的回调每帧 / 每次翻页都会来，里面的 setData
  与别处一样走失效分析就行。从前 `tick_scroll_views` 一律整页重画：滑「节点与滚动」页每帧 24~31ms。
- 测 swiper 时别在回调里 setData 做 A/B 对照：swiper 的状态和事件队列是进程级的，两个引擎共用一份，
  事件被谁先取走取决于 pump 顺序。
## SurfaceView 闪一下
- 只实现 `SurfaceHolder.Callback` 时，窗口重绘不等 SurfaceView（logcat `handleSyncNoBuffer`），新 Surface
  还没有缓冲就上屏了，露黑底。实现 `Callback2.surfaceRedrawNeededAsync`，在引擎交出第一帧后再回调。
- `setSurfaceLifecycle(FOLLOWS_ATTACHMENT)` 在 ColorOS 上不管用，回桌面照样 `surfaceDestroyed`。
## Gradle 打进旧引擎库
- 引擎库在 Flutter 例子工程外（`sdk/android/src/main/jniLibs`），守护进程开着文件监视时常常当它没变：
  APK 里还是旧库，一次直接 `UnsatisfiedLinkError`。例子工程的 `gradle.properties` 关掉了 `org.gradle.vfs.watch`。
  另外只比可执行段大小不够（小改动段大小不变），要比 md5。
- 编引擎库和 `flutter build apk` 必须**一个跑完再跑另一个**（分两次调用）。放在同一批里并行起跑，
  APK 先打完、装进去的还是旧库，md5 对比也是在库编完之前取的，看着「一致」。
## 测速脚本自己坏了
- `android-jank.sh` 用一个停止标记文件叫停 SurfaceFlinger 轮询，退出时 trap 会留下它。下一次在起轮询之后才删
  的话，轮询一起来就看见、立刻退出，结果只剩最后一次 dump 的 127 帧（≈1.4 秒），「屏上重复」低得好看。
  现在起轮询之前就删；看到「127 帧」这个数要先怀疑量具。
## 真机比桌面慢十倍的那几段
- 同一次 setData 重建，桌面 1ms、一加上 7~9ms：不是算法，是分配。Android 的 jemalloc 带锁，
  「每个节点 × 每条规则」那层循环里一个临时 Vec、级联时把声明逐条深拷进新 HashMap、每个节点克隆整条祖先链，
  在桌面上几乎不要钱，手机上就是一半的时间。看热点要在真机上抓（simpleperf `--call-graph dwarf`，
  符号用 `target/aarch64-linux-android/release/` 里没剥的库对 `llvm-symbolizer`；jniLibs 里那份剥过、也没有 build-id）。
- `vec![Color::TRANSPARENT; n]` 不走 calloc（只有整数这类类型才走），45MB 的页面画布逐个写一遍要十几毫秒。
## 内容变高时的局部重画
- fixed 元素在布局里的位置不是它画的位置（常常就在 (0,0)），配对配错时不能拿它的框当页面上的失效范围，
  否则切线一下到了页面最顶上。
- 失效分析收框要带上阴影那圈：盒子变高 / 挪动时框外的旧阴影没人擦。
- 只看「孩子个数相同」配对的话，列表新条目插在「底部提示」前面（`wx:for` 后面还有兄弟）就全错位；
  内容变高时配到第一个标签对不上为止，剩下的两边各走一遍取最高的顶边。
## 原生 App 一滑就顿，Flutter 示例却很顺
- 同一个引擎库、同一个演示小程序：Flutter 示例「节点与滚动」慢拖屏上重复 2%，原生示例（`MiniProgramView`）19.9%。
  上屏优化（SurfaceView、GPU、高刷投票、Callback2）全在 Flutter 插件的 `EngineHost` 里，原生视图还是最早那版：
  像素拷进 ByteArray → `copyPixelsFromBuffer` → `postInvalidate` → `onDraw` 里 `drawBitmap`，后端写死 CPU。
  每帧三次整帧拷贝 + 一次纹理上传、晚一个 vsync、UI 线程一忙就丢，滚动帧还都是 CPU 整帧合成。
- 修法：`MiniProgramView` 改成 FrameLayout + 一块 SurfaceView，上屏状态机搬进 `EngineSession.kt`（与 `EngineHost` 同一套）。
  改完 2.5~3.3%。两份上屏代码现在是并行的两份（Flutter 那份还管纹理模式与视频），改一边要对照另一边。
- 同一处还漏了两个选项：`navigationBar` / `routeAnimation` 没传，原生示例整页顶进状态栏、没有返回箭头、转场一换就到。
- 原生示例从前也不认 `debug.mini.*` 诊断开关（Flutter 插件的 `DiagProps` 只在插件里），真机上只能靠肉眼 —— 现在 SDK 里有 `MiniDiag.kt`。
- 清单与数字：[滑动顿挫避坑清单](滑动顿挫避坑清单.md)。
## 操作菜单弹出来是白板、底下一截黑（GPU），弹出一顿一顿（CPU）
- 现象（原生示例，auto → GPU）：点 ActionSheet，面板没有文字、只有白底和一道灰缝，屏幕最下面一截是黑的；
  按一下选项才变对。`MINI_DAMAGE_LOG` 里整段弹出每帧都只「传 130KB」（只有圆角那几行），面板那张 2.4MB 的图一次也没传。
- 原因：面板缓存的编号是**线程局部**的、每条线程从 1 数。GPU 自检在预热线程（`mini-gpu-warm`）上画了一张
  1 号缓存（两项、没文字），合成器搬到引擎线程后，第一次真弹出来的菜单也是 1 号 —— 合成器按编号判断「纹理已经是它」，
  不传，屏上贴的是自检那张；自检的面板矮，越界取样是 0，于是底下一截黑。单测都在一条线程上跑，撞不上。
  修法：编号改成进程级（`AtomicU64`），单测 `面板缓存编号跨线程不撞`。凡是「拿编号 / 代数判断要不要重传」的缓存，
  编号必须进程里唯一（`compositor::layer` 的代数发号器同理）。
- 弹出第一帧：画面板缓存 7.5~10ms。整屏草稿第一次用时 `resize` 把 10MB 逐个写零、画完再 `to_vec` 拷出一截。
  现在画布用 `vec![0; n]`（calloc，没碰的页不占也不写）、缓存直接留着这块画布：2~4ms。
- CPU 后端（Flutter 示例 `MINI_BACKEND=cpu`）弹出那 0.3s 每帧合成 10~21ms，90Hz 下掉成 30~45 帧。`MINI_DAMAGE_LOG`
  逐段量出来大头是**整屏查表压暗**：每个分量一次随机读，编译器向量化不了（M3 上 1.7ms，比同尺寸 memcpy 慢 7 倍）。
  三刀：① 压暗表写得成 `(c·m + bias) >> 16` 就按乘法算（`LinearLut`，逐项核对，写不成的退回查表；4 万个随机 keep
  全都写得成，写不成的只有 0.84 这类整齐小数恰好被 f32 舍入推得忽上忽下）；② 面板白底整行盖死的行不合成页面、不压暗；
  ③ 底图（页面 + tabBar + fixed + 导航栏）留一份，各层没变就边读边压暗，不再每帧重拼（`compositor::sheet_base`）。
  一加上稳态一帧合成：改之前 10~21ms（Flutter 示例），①② 之后 3.9~4.5ms，③ 之后 2.5~3.5ms（原生示例）；
  桌面 `sdk_motion_bench`（423×919@2.55、90Hz）弹出 p50 2.4~3.1 → 0.97ms。
- 还剩：CPU 后端在每段动画开头（刚点下去、隔了半秒再点遮罩收起）前几帧照样慢两三倍 —— 大核从空闲里起来还没升频，
  同样的循环 2ms 变 6~9ms，屏上重复 4~30% 看那一刻的频率。GPU 后端每帧只有 1~4ms，不受影响。

## 地图一滑就跟页面错开（盖上去的原生组件）
- 视频当初的病：控件盖在引擎画面上，两条上屏路，晚 2~4 个 vsync 且每帧不一样。视频改了同层渲染，`<map>` 还盖着：
  Flutter 示例慢拖时地图框与页面错开最多 15px（`tools/android-native-align.py`，带逐帧推算），**而且从地图上开始的拖动
  页面根本不动**（控件吃掉了触摸）。SurfaceFlinger 的「屏上重复」是好的 —— 两层各自都按时上屏了，错开的是两层之间。
- 修法：同层渲染推广到任意标签（`components/host_view.rs`、`mr_native_view_frame_rgba`）：宿主把控件画进离屏缓冲、
  内容变了才交帧，引擎当动图那样只重画那一块；点击转成 `nativeViewTap` 交回宿主。错位按构造就是 0（实测 24/24 张）。
- Flutter 的离屏渲染：每个组件一棵自己的 `BuildOwner` / `PipelineOwner` / `RenderView`，`toImage` 读回；点击在离屏树上
  命中测试后用 `GestureBinding.dispatchEvent` 派发按下 / 抬起（命中链最后要加上 GestureBinding 自己，竞技场才会关 / 清）。
  `PipelineOwner.dispose` 之前要 `rootNode = null`；测试里的 `ColoredBox` 放进 `Column` 要 `stretch`，否则宽 0、读回全透明。
## 原生 Android 选完图只剩占位图
- `org.json` 的 `toString()` 把 `/` 写成 `\/`：原生视图的回包原文是 `"file:\/\/\/data\/…"`。引擎「回包里有没有 `file://`」
  按字面量筛，筛不到就整包原样交给小程序，`<image>` 拿到 `file://` 显示不出来。Flutter 那条路的 Dart `jsonEncode` 不转义，
  所以插件一直是好的。改成筛 `file:`（解析之后的字符串照旧按 `file://` 认），`tests/host_media.rs` 补了一条；
  导入失败的那一行改走 `diag::emit`（Android 的 stderr 进不了 logcat，从前失败了也看不见）。
- 选择器给的 `content://` 授权只属于收结果的那个 Activity：代办的 `MiniMediaActivity` 先 `finish()` 再在后台拷文件，
  拷的时候授权已经收回（`Calling uid … does not have permission to access picker uri`）。现在拷完才关它。
