# 滑动顿挫避坑清单

「顿挫」= **屏上重复了一帧**：相邻两次上屏隔了一个以上的显示器周期。平均帧率、引擎自己的帧耗时都可能全达标而屏上照样顿，
所以判据只认两样：

1. **屏上**：SurfaceFlinger `--latency` 量引擎那一层每次上屏的时刻（不靠 App 内日志）；
2. **引擎**：`debug.mini.damage_log` 里每一帧重画了多少、花了多久（`整帧·…` 行末尾带 `← 源码文件:行号`）。

两样一条命令都给（宿主承载的原生组件——地图、视频——跟不跟页面是第三样，见下面「原生组件」那一节）：

```bash
bash tools/android-jank.sh query-slow                # Flutter 示例（sdk/flutter/example）
MINI_APP=native bash tools/android-jank.sh query-slow # 原生示例（sdk/android/example，MiniProgramView）
```

每一条坑的来龙去脉在 [踩坑记录](踩坑记录.md)，这里只列「改之前先对一遍」的清单与当前数字。

**转一下屏，之后一直是 CPU（2026-10-24，Flutter 示例上传的诊断日志 20261024-143852）**：GPU 设备建的时候只要了

上下滑一顿一顿。改成建设备时直接要适配器的上限（`compositor/gpu/device.rs`）；真机复测横屏 → 竖屏后仍是 GPU、
`writePixels` 0 次。**看诊断日志先看「[后端]」那一行**：auto 落到 CPU 的原因写在括号里。

停住再拖的第一下：重采样在拖动起步时多回取一帧（取样时刻落在第一个采样之前，页面原地不动），已改成起步时
正好落在第一个采样上、120ms 内退回正常回取量（`engine_resample.rs`）。但关掉重采样（`debug.mini.no_resample 1`）
同一场景也是 33~44ms，剩下的是方向锁定阈值（4px）加上 `adb input swipe` 从静止起步的事件节奏，不是绘制。

## 宿主侧（上屏与帧调度）

| # | 别这么做 | 为什么 | 应该 |
|---|---|---|---|
| 1 | 像素拷进 ByteArray → `Bitmap.copyPixelsFromBuffer` → `postInvalidate` → `onDraw` 里 `drawBitmap` | 每帧三次整帧拷贝（约 10MB）+ HWUI 再上传一次纹理；晚一个 vsync；UI 线程一忙就丢；只能走 CPU。原生示例实测 19.9% | 画到自己的 **SurfaceView**，引擎线程直接交帧（`EngineSession.kt` / Flutter `EngineHost.kt`） |
| 2 | Flutter 外部纹理（SurfaceProducer） | 屏上那一帧取决于 Flutter 自己这一帧有没有按时出，主线程一忙就重复 | 独立图层（`androidSurfaceView: true`，默认） |
| 3 | 后端固定 CPU | 滚动每帧都要 CPU 整帧合成 + 整帧写进缓冲区；GPU 下是「只合成」约 2ms | 偏好 `auto`，失败逐级回退（GPU → CPU 直写 Surface → Bitmap），回退有日志 |
| 4 | 不给 Surface 投帧率票 | ColorOS 没人要高刷就把整个屏降到 60Hz | `Surface.setFrameRate(最高刷新率)`（`surfaceChanged` 里） |
| 5 | SurfaceView 只实现 `Callback`、一建出来就显示 | 回前台时窗口不等它，露黑底一闪；第一次打开时黑块 | `Callback2.surfaceRedrawNeededAsync` 等引擎首帧（250ms 兜底，第一次打开不等）；首帧前 `alpha = 0` |
| 6 | SurfaceView `MATCH_PARENT` | 视图 1080、引擎 1079 像素时整帧被横向拉伸 1 像素，全屏发虚 | 缓冲区与布局都按引擎像素尺寸（`setFixedSize` + 同尺寸 LayoutParams） |
| 7 | 只在「这一帧有新画面」时续帧 | `setTimeout` / 网络回包在静止页面上停住 | 认 `FRAME_WANTS_MORE`，否则停下等输入 |
| 8 | `pump(此刻)` | 画的时刻相对 vsync 忽早忽晚，动画抖 | 传 Choreographer 的 `frameTimeNanos` |
| 9 | 移动事件不带时间、抽稀 | 一帧到几个事件是碰运气，慢拖一顿一顿；松手速度暴涨 | `nativePointerMoveAt(x, y, eventTime)`，历史点逐个送 |
| 10 | 在 UI 线程上建 / 驱动引擎；不管线程跑在哪个核 | 小核上补条带 5~11ms | 专用引擎线程（引擎自己绑大核）+ ADPF（`FrameBoost.kt`） |
| 11 | 导航栏关着（原生视图从前的默认） | 不是顿，但整页顶进状态栏、没有返回箭头、转场「一换就到」 | `navigationBar` / `routeAnimation` 默认开（与 Flutter 插件一致） |
| 12 | 把原生控件（地图、视频）**盖**在引擎画面上 | 两条上屏路：引擎画面系统合成器直接取，控件要等事件 → 主线程 → 宿主下一帧，晚 2~4 个 vsync 且每帧不一样；按 vsync 推算只推得准惯性。还会吃掉从它上面开始的拖动（页面拖不动） | **同层渲染**：宿主解码 / 画好帧交给引擎画进页面（视频 `sameLayerVideo`，地图这类 `sameLayerViews`），见下一节 |
| 13 | 同层组件每个滚动帧都重画、重交 | 白白占主线程与上传带宽；滚动时画面本来就在引擎画布里跟着走 | 只在内容变了时交帧（`invalidate` / Flutter 离屏树要重画时），引擎只重画那一块 |
| 14 | iOS：主线程 `CADisplayLink` 里 pump + `CGImage` 交给 `CALayer.contents` | 一帧几毫秒压在主线程上；子图层改 contents 默认带 0.25s 隐式动画（每帧都在淡入淡出）；只能 CPU | 引擎线程 + `CADisplayLink`，画面画进自己的 `CAMetalLayer`（GPU），CPU 退路关掉隐式动画（`actions` 全给 `NSNull`） |
| 15 | iOS：触摸不带时间、不要高刷 | 慢拖一顿一顿（同第 9 条）；ProMotion 机型默认被限在 60Hz | `mr_app_pointer_move_at(…, UITouch.timestamp × 1000)`；`preferredFrameRateRange` 要 120 + Info.plist `CADisableMinimumFrameDurationOnPhone = YES` |
| 16 | tick **最后**才 `postFrameCallback` 挂下一帧 | 这一帧一超过一个周期（setData + 覆盖层 11~13ms），下一个 vsync 已经过去，Choreographer 只能排到再下一个。一加 `query-slow` 屏上 21 次重复里 20 次就是它（`🎞` 日志：tick 间隔 22ms，前一帧 vsync→交出 11~13ms）。而 BufferQueue 本来有余量（入队到上屏约 25ms），晚 1~2ms 交上去赶得上 | 上一帧回报 `WANTS_MORE` 就在 tick **开头**预约，这一帧回报没活了再撤掉（静止页面照旧零耗电）。两份 Android 宿主都改了；iOS 的 CADisplayLink 一直挂着，不受这一条影响。`🎞` 第三列是 tick 开始时刻，分得清「pump 慢」还是「线程上前面压着别的活」 |
| 17 | 分栏（frameset）时挪图层与换图分在两次 Core Animation 提交里（macOS，2026-10-26） | 点会话打开聊天时两栏对调着显示一帧（左栏是聊天页、右栏是会话列表）。`applyFrameset` 自己 `CATransaction.begin/commit` 在最外层立刻提交了挪层，换图跟着 RunLoop 末尾的隐式事务晚一帧。另有：GPU 直画 Metal 层时宿主挪层晚一拍；hover-class 点击态冻进左栏留图 | 事件、另一栏的图、主画面包在**同一个显式事务**里（`EngineSession.swift`）；分栏期间整段走 CPU 合成（`frameset_holds_gpu`）；留图前撤点击态。**判据用真录屏**：`python3 tools/mac-split-flicker.py`（ffmpeg 60fps 录窗口 + cliclick 真点击，数 A→B→A 回跳）。轻聊连点会话：改前左栏 3 下 2 次回跳，改后 6 下 × 2 轮 0 次。`MINI_SPLIT_TRACE` 只记交出去的图，量不到这一类 |
| 18 | 小游戏每帧工作 20~30ms 时照旧按 60 请求 rAF（2026-10-29） | 帧率在 30~45 之间跳，帧间隔 16.7 / 33.3ms 交替，手上就是一顿一顿。一加 farm001（手机内存吃紧时）每帧 25ms：10 秒 390 帧、间隔不匀 | 创建选项 `adaptiveFps: true`（`game/fps_governor.rs`）：30 帧里 20 帧超过 15ms 降到 30，30 档 90 帧 p90 < 11.7ms 回 60。同一场景开着它 10 秒 307 帧、稳在 30。默认关（微信语义），两个示例 App 开着；`fixed_clock` 下不生效 |
| 19 | 小游戏 2D 主画布走 CPU 上屏（每帧整张后备缓冲转 BGRA 交给 CALayer / 锁 ANativeWindow 拷贝，2026-10-31） | iPhone 16 Pro Max 物理分辨率 1320×2868 上屏一步 5.7~6.3ms，与游戏自己的工作叠在一起 | `MINI_2D=auto`（默认）：移动端主画布走 GPU（`game/canvas/gpu2d`），EGL 窗口 surface 直接上屏，0.2~0.4ms。g-bench-rects 2000 个矩形一帧合计 12.8 → 7.4ms，精灵 2000 个 10.0 → 6.2ms（都 60fps、0 掉帧，game-doc/14）。Android 走同一个 `nativeBlit` 入口，真机未量 |
| 20 | 小游戏 GPU 2D 帧末为了 flush 无条件切到 2D 的 EGL 上下文（2026-10-31） | 主画布是 WebGL 时每帧多切两次上下文；ANGLE-Metal 切走一个上下文要等它的命令缓冲排进队列，这一下落进 WebGL 的 swap：iPhone present 0.1 → 6ms，发热后 10~14ms，farm001 掉到 50fps（40 秒 203 次掉帧） | 帧末只在 2D 上下文正好是 current 时 flush（`Gpu2d::end_frame`），用 2D 像素的路都先 flush。改后 farm001 auto 60 / 60fps、0 掉帧、present 0.1ms（game-doc/14） |
| 21 | iOS 宿主在小程序每一页都挂 `UIScreenEdgePanGestureRecognizer`（2026-10-26 起，原生示例） | 它一认出手势，UIKit 就 cancel 交给引擎视图的触摸：引擎的侧滑返回推出几个像素就收回，之后页面不跟手、半路松手不回弹，划过 60pt 直接 `goBack` 跳回上一页（「侧滑返回回弹没了」） | 宿主的识别器只在栈底那一页接（`gestureRecognizerShouldBegin` 看 page 事件的 depth），二级页及以上交给引擎（host/edge_back.rs）。验收 `EdgeBackUITests`（模拟器真触摸）：划到 20% 松手截图与松手前逐像素相同、划到 70% 回到首页；把判断改回「每页都接」时这条测试失败 |

## 原生组件（地图 / 视频）：别盖在画面上

「顿」也可能是**两层之间错开**：引擎那一层每帧都按时上屏了（SurfaceFlinger 量不出问题），盖在上面的控件晚了几帧。
量法是截屏量「地图上沿 − 卡片标题上沿」的变化（`python3 tools/android-native-align.py flutter <apk…>` / `native`）：

| 一加 PLY110，宿主页慢拖 700px / 2.5s，3 轮 × 8 张 | \|d\| 均值 | 最大 | ≤2px |
|---|---|---|---|
| Flutter 示例·地图盖在画面上（`--dart-define=SAME_LAYER_MAP=false`，带逐帧推算） | 2.8px | 15px | 15/24 |
| Flutter 示例·同层渲染（`sameLayerViews: ['map']`，离屏画成帧） | **0** | 0 | 24/24 |
| 原生示例·同层渲染（`sameLayerViews["map"]`，`MiniSameLayerView`） | **0** | 0 | 24/24 |
| 原生示例·SDK 自带的瓦片地图（`MiniMapView`，卫星图，2026-11-02） | **0** | 0 | 24/24 |

画进页面以后它就是页面画布里的一块像素，错位按构造就是 0，滚动时宿主一帧都不用重画。真地图 SDK 要能把那一帧画出来
（截图 / TextureView 接口），平台视图（google_maps_flutter）离屏画不出来就只能照旧盖着、接受错位。

地图自己的手势（2026-11-02）：SDK 自带的地图（Android `MiniMapView.kt`、iOS `MiniMapView.swift`）在创建选项 `sameLayerGestures`
里点名，按在框里的整串触摸交给宿主（`nativeViewTouch`），拖的是地图、页面不滚；`enable-scroll` / `enable-zoom` 都关的地图
不接手势，拖动照样滚页面（宿主 tab 那张就是这样，`host-slow` 与上面的错位量的就是它）。宿主拖地图时每一帧在主线程上重画、交帧：
- **瓦片解成 sRGB**（`BitmapFactory.Options.inPreferredColorSpace`）：高德的 PNG 带 gAMA，系统给它挂自定义色彩空间，往 sRGB 画布上贴
  就是逐像素做色彩转换 —— 一加 PLY110 上一屏 20 张瓦片 37.5ms，改了 1.7ms；
- 平移时瓦片按屏上像素预先缩好、整像素贴（缩放中那几帧不滤波，停下 120ms 再按缩好的画一遍）；
- 画布 `density = DENSITY_NONE`：不然 `drawBitmap(b, x, y)` 按位图密度悄悄放大。
拖地图时 PLY110 上主线程一帧中位 6.9~7.8ms、最慢 12ms（画 / 读出 / 交给引擎，`adb logcat -s mini-render | grep 🗺` 每秒一行）。
**2026-11-05（WP-F1 之后，演示页加了控件、自定义气泡、彩虹线、虚线多边形、定位蓝点）回退到中位 11.0~11.5ms**、最慢 14.8ms（Flutter）/ 26ms（原生，
那一帧瓦片缓存没命中、`tiles` 22ms）。临时打点（`MapDraw.draw` 分段，量完已删）180 帧的中位：瓦片 3.2、多边形 / 圆 / 折线 1.2（含虚线描边）、
标记 0.4、标签 + 气泡 0.7、控件 + 比例尺 + 版权 0.4，`MapDraw` 合计约 6ms，读出 + 交给引擎约 3.5ms。
A/B（同一天、同一台、同一份新 Kotlin，只把演示页换回 HEAD 的内容）：**中位 8.7ms、最慢 14.6ms** —— 代码本身没变慢多少，多出来的 ~2.5ms 是演示页新加的内容。
页面不受影响：`host-slow` 0.3%、错位 0 / 24/24。下一步：虚线多边形的描边路径在纯平移时可以只平移不重算（`DashPathEffect` 每帧重切）。
`host-slow`（原生示例，2026-11-02，换成真地图后）：584 帧屏上重复 0 次（0.0%），引擎 >8ms 1 帧（只合成 12.1ms）。
Flutter 示例（插件自带地图 + web-view）：屏上重复 0.5%，引擎 >8ms 2 帧；错位 0 / 0 / 24/24。
踩到的坑：插件自带 web-view 让引擎多报了一条（空的）`nativeViews`，**Dart 收到它之后**引擎每帧 GPU 提交从 1ms 涨到 12~13ms，
>8ms 的帧 0 → 150~190（同一个引擎库，`--dart-define=BUILTIN_WEBVIEW=false` 对照就回到 0~1；屏上重复照样 0.3~0.5%，只看重复会漏）。
现在插件摘掉 web-view 之后是空的就不交给 Dart（`NativeComponents.kt`）；Dart 侧为什么会这样还没查清，宿主自己用 `nativeComponents` 盖控件时可能也有。

## 引擎侧（谁逼出了整帧）

- 点击态（`hover-class` / `:active`）、事件回调里的 setData、内容变高、fixed 元素 `wx:if` 出现：都曾逼出 `整帧·结构`，
  现在各自只重画自己的盒子。新加的失效路径先看 `damage_log` 里有没有 `整帧`。

  `STORE_APP=meditate STORE_PATH='pages/course/course?id=c2' ENTER_TAP="540 2230"`）。仍然超预算：剩下的是封面图那 30 万像素
  实打实的双线性，单线程上压不到 8ms 以内。再往下要么多线程分行贴回（结果逐字节相同），要么 GPU 后端把带 transform 动画的子树
  当图层交给合成器（Skyline 的做法），都还没做。同一轮修了 `margin: 0 auto` / `margin: 60rpx auto 0` 这类多值简写里的 `auto`
  被丢掉（封面贴在左边、光晕一半画在屏外）：改前量的区域被屏幕左边裁掉一截，改后居中、整块都在屏内，两次的面积不完全相同。
  **第二轮（2026-11-03）**：贴回分给最多 4 个线程按 16 行一条的行带领活（`compose.rs`，常驻帮手 `renderer/blit_pool.rs`），
  每行再按源画布里有内容的外包框解出要走的 px 区间（离屏四周给旋转留的透明边不再逐点判）。结果逐字节不变：单测拿「单线程、不收窄」
  比 30 组随机变换，gallery 与 HEAD 逐字节一致。同一场景（Flutter 示例）**画 31 → 14.2ms（中位，p90 15.9）、帧间隔 33.2 → 16.6ms**
  （空闲时 ColorOS 是 60Hz，屏上重复 4.5%）；原生示例画 13.5ms、重复 0.8%。踩到两个坑：① 帮手线程不绑核时被排到小核，
  引擎线程领了 40% 的行带、三个帮手各 20%，所以帮手与引擎线程同一套规则绑大核（`cpu_affinity::pin_helper_thread`，`MINI_CPU_PIN=0` 一起关）；
  把帮手加进 ADPF 会话试过，ColorOS 上没用，没留。② 每帧现起线程（`thread::scope`）的 clone / munmap 占引擎线程约 3%，改成常驻。
  仍超 120Hz 的预算：剩下引擎线程上贴回约 7ms（四个线程共 ~20ms CPU，约 100 万个点、每点 ~20ns）、离屏光栅化约 4ms（光晕圆、封面图与描边，
  每帧重画）、上传 4.6MB 约 2ms。下一步按收益排：离屏子树内容不变时缓存离屏（省 ~4ms，失效条件要覆盖 setData / 图片解码完成 / 按压态 /
  子树里的动画）、GPU 后端把带 transform 动画的子树当图层合成（Skyline 的做法）。`MINI_BLIT_THREADS=1`（`debug.mini.blit_threads 1`）退回单线程对照。

  `data.clone()` 一份作用域，而 data 里就装着这个列表，200 项 = 4 万次对象深拷贝。原生示例 `STORE_APP=wx-components STORE_PATH=pages/list/list
  … store-slow`：滚动时 itembuild 回调 setData，**pump 43.5ms（模板 31.9）→ 16.3ms（模板 3.1~4.6），最长一帧 33 → 22ms**。改成作用域只拷一次、
  每项改写 item / index（`parser/template/for_loop.rs`、`builder.rs`），所有 `wx:for` 页面都受益。对齐网格（非 masonry 的 grid-view / grid-builder）
  也进了增量布局（从前整个网格每次重建）。剩下一次重建约 9ms（模板 4.6、布局 2.8，200 行 + 两组网格），**小程序里别在 itembuild / 每帧的
  bindscroll 里 setData**：示例改成攒 300ms 发一次。

  「绘制坐标≠布局坐标」（拉开的那段位移），失效分析不敢局部重画，整帧 15~16ms、pump 最慢 39ms，一次下拉两帧。屏上重复 0.7%。

  但盒子超过视口 0.34 时照旧按整帧画（失效范围太大，整帧反而便宜），这一页的 scroll-view 占屏 37%，真机上仍是整帧。
- **相机 / 推流页每帧都在换画面**（2026-11-05，一加 PLY110，原生示例 `ROUTE=pages/camera/camera … route-slow`）：相机按 30 帧交预览，
  每帧宿主在自己的 GL 线程上按框读回（1270×893 约 4.5MB）、引擎只重画那个框：画 3.3ms（中位，p90 4.1）、合成 4~7ms、上传 4MB，

- **live-pusher 的小窗画在合成那一步**（2026-11-05 F3，`components/pip.rs`）：不进页面画布，宿主每交一帧只重新合成；GPU 后端这时走直通，
  CPU 只合成小窗那几行（`cpu::overlay_reach` 带上它的行区间）。没有小窗时每帧只多一次线程局部判空。美颜 / 滤镜着色器
  （Android `FrameEffects.kt`，16 个邻点）在相机的 GL 线程上，**没单独量**它多花多少；推流页屏上与上面同一档。
- **横竖同时滚的 scroll-view 不走分块缓存**（F3，`scroll_2d_attrs.rs`）：顶层的走 `scroll_live`、嵌套的走逐帧画可见子节点那条路，
  只按纵向剔除子节点（横向靠裁剪）。拖动时只重画它的盒子（两个控制器各记各的位置，`wpd::scroll_2d` 两台引擎逐帧比、不出整帧）。
  单向的 scroll-view 一个像素都没动（偏移算式与从前逐字节相同）。F3 之后首页慢拖 `index-slow`：原生示例 0.4%（565 帧重复 2 次，
  引擎 >8ms 1 帧）、Flutter 示例 0.5%（559 帧重复 3 次，>8ms 6 帧），与上表同一档。

  下一轮全部落空，孩子、孙子一层层重算。`wx-components` 的 list 页（200 行 list-builder）只把列表容器标脏重排：度量回调 5610 次 / 1.38ms → **0 次 / 0.18ms**；

  守着它的是 `src/tests/layout_cache_tests.rs`（改一行、标脏容器都不该再量任何叶子）；**升级 taffy 时它必须照样过**。

  （父宽没变不再重排）。list 页 `setData` 改一个计数 p50 4.41 → **1.46ms**（剩下的大头是整页模板重新展开 0.5ms）。真机没量（手机没授权调试），待补。

  试过「圆角带逐帧画、中间贴块」（与逐帧画逐字节相同），桌面上这页反而慢（拖动 p50 0.65 → 0.91ms）：每行只有一段字，逐帧画比贴块 + 甩动时补块便宜。

  2. **转圈的唱片每帧把底下整层重画**：1022×957 那块里，铺满屏的封面背景（`opacity: .55` 成组透明度）+ 渐变遮罩 + 唱片子树每帧现画，
     桌面 9.5~10ms。三步：动画包围盒按圆角形状算（圆盘转起来占的是圆，不是外包框转出来的大方块，`animation.rs::ink_far`，702×702）；
     旋转子树的离屏按内容缓存（`transform_cache.rs`）；**动画底图**（`backdrop.rs`：这块矩形没碰到别的损伤时，唱片底下那层贴回上一帧留的，
     之前的节点只遍历不画）。稳态每帧 9.5 → **3.8ms**（`MINI_NO_BACKDROP=1` 对照 6.3ms）。判据：`tests/sdk_damage_transform.rs`
     的转圈唱片用例，局部 = 整帧逐字节，且 30 帧里至少贴回 20 次。
  3. **再进播放页那一帧 50ms+**：300×300 的封面拉成 1656×2303 的背景（`aspectFill`），双线性每个像素四次取样十二次插值，一次 35ms；
     返回歌单页时歌单头图（→1368×1368）又要 17~23ms —— 两张加起来超过缩放缓存的 32MB，来回切页互相挤掉。
     改成横向插好的两行按源行复用 + 大图分四段并行（`canvas/images.rs`，算式不变，gallery 逐字节相同）：35 → 6.4ms、17~23 → 2.9ms。
     缩放缓存预算没动（32MB），两页来回切仍会互相挤，只是挤掉之后重算便宜了。
  4. 列表页上的迷你播放条（覆盖层里转的小封面）每帧重画覆盖层那条，桌面 1.3ms：没动（覆盖层没接动画底图）。
- **播放页真机量过之后（云听音乐，一加 PLY110 90Hz，Flutter release，`tools/android-player.py install --rounds 3`，2026-11-06）**：
  脚本按「进入 → 静置 → 拖进度条 2.5s → 拖后 → 返回 → 歌单页」三轮打标记，屏上帧从 SurfaceFlinger 取，🩹 行从 logcat 取。
  起点 → 现在（三轮的范围）：**拖动** 引擎 p50 22 → 10.1~10.5ms、屏上重复 46~47% → 12.6~14.5%；**返回** 最慢一帧 54 → 12.6~28.8ms、
  重复 31% → 0~12%；**歌单页** 引擎 p50 10.5~11 → 6.0ms；**换歌**（背景整张换，该整帧）60~69 → 44~46ms；
  **进入** 第一帧 80~88 → 47~71ms（剩下的见第 8 条）。逐条：
  1. **成组透明度为一条 65 行的条带开整张离屏**：铺满屏的 `.bg`（`opacity:.55`，1948×2710）每补一条带清 21MB，一加 13ms。
     离屏只开裁剪区里那块（按整像素平移，`draw.rs::paint_opacity_group`），gallery / damage-check 逐字节相同。
  2. **按住滑块时唱片每帧重新光栅化**：变换子树的离屏缓存从前「按着任何东西都不用」，拖进度条那 2.5 秒里唱片（圆角 + 阴影 + 封面）每帧重画，
     simpleperf 里 `fill_round_rect` / `blend_mask` / `memset` 占引擎线程两成。改成只有子树里有按压态样式才不用（`transform_cache.rs`），
     拖动 p50 18~19.5 → 10.1~10.5ms。判据：`sdk_damage_transform` 唱片用例拖进度条那 20 帧缓存至少命中 30 次（改回去只有 10 次）。
  3. **一次 setData 的几处变化被并成一块**：暂停 / 播放时顶上的唱片与底下的播放键并起来大半屏，超过视口 0.34 整帧（一加 52~84ms）。
     失效分析把隔得远的几块分开交给宿主（`invalidate.rs::take_damage_parts`，最多 3 块，宿主按块各画一趟）；唱片开 / 停的范围按
     「框心为圆心、子树里最远一点为半径」的圆算（`invalidate_grow.rs::anim_extent`，从前外扩 + 对角线一半两次都算了旋转，2433×2901）；
     播放 / 暂停键里转了 45° 的三角形换成两根竖条（孩子 1 → 2）、歌词「加载中…」换成整首（滚不动的 scroll-view 里结构变了）也不再整帧。
  4. **图下完就整帧**：进播放页时封面、背景、缩略图一张张到，一张一帧整页（45~52ms）。改成只重画用到它的那几块
     （`image_arrival.rs` / `engine_image_arrival.rs`），先让预取线程按框缩好再画（图晚一两帧出现，引擎线程不现缩：歌单头图 1610² 18~22ms、
     封面 560² 4.4ms）；被盖住那一页留着的画布不再因为图到了作废，记下是哪几张，返回时只重画那几块。顺带修了潜在问题：
     **远程 `widthFix` 图下完一直按默认 320×240 的框画**（数据没变、布局缓存照旧命中），现在重排（`sdk_damage_fixed_scroll` 远程那条，去掉修复失败）。
  5. **返回整页重画**：被盖住那一页的页面画布与覆盖层留着（`engine_keep_canvas.rs`，`MINI_NO_KEEP_CANVAS=1` 关），返回只重画盖着时变了的。
  6. **每次 setData 把整页数据 `JSON.stringify`**（2~12ms）：`__getRenderData` 按根键缓存 JSON（`page-components.js`）。
  7. **背景大图每次整页重画都重采样 350 万像素**：目标超过 4M 像素不进缩放缓存。溢出画布的大图只缓存看得见的那块
     （`canvas/image_crop.rs`，单独一张 18MB 的表，不挤缩放缓存里别的图；第一次照旧现画、后台单线程缩好），桌面画一遍 5.2 → 1.2ms。
     成组透明度贴回与铺满屏的竖直渐变按行带分给帮手线程（`canvas/par_rows.rs`），换歌那一帧 60~69 → 44~46ms。
  8. **还剩的：进播放页第一帧 47~71ms**（画 30~56；第一次进时背景图还没下完，所以便宜，到了那一帧只重画背景那块 31~59ms）。一加上大头是唱片第一次光栅化 + 旋转贴回、背景成组透明度的整屏离屏（12MB 缺页 + 拷贝）、
     整屏遮罩；GPU 准备 5~8ms 是新页 14MB + 转场用的旧页截图 13.5MB 上传。下一步可做：单张图的成组透明度不开离屏、直接按透明度贴缓存块。
- **真机上播放页的上一首 / 下一首 / 播放键是白方块，桌面看不出来**：手机装的是商店里的 `music-online`（version 1），与 `sample/` 里的不是同一份
  （样例后来改成了 `overflow:hidden` + 旋转方块）。商店版用 CSS 边框三角形（`width:0; height:0;` 上下透明边 + 一侧白边），
  引擎把每条边画成整条矩形 → 实心方块。改成相邻两边都有宽度且颜色不同时按对角线斜接、每条边画梯形（`box_paint.rs::draw_side_borders`；
  单边分割线、同色边照旧整条矩形，gallery 逐字节不变）。判据 `renderer_tests::css_border_triangle_draws_a_triangle`（改回去失败）。
  **量真机之前先确认装的是哪一版小程序**：`curl $STORE/api/apps/<id>` 看 version，`/package` 下下来与 `sample/` 比一下。
- **量具：静置 / 歌单页「重复 49.5%」是 ColorOS 把屏降到了 60Hz**（`dumpsys SurfaceFlinger` 的 `activeMode vsyncRate=60`），
  按全程的 90Hz 周期算，60Hz 下每一帧都算成「重复一帧」。`android-player.py` 改成每段按自己的 vsync 网格判 60 / 90Hz（行首印出来），
  这几段都是 60Hz、0 重复。别的脚本（`android-jank.sh`）量没有触摸的那段时同样要看一眼刷新率。
## 量具与环境（会让你误判）

- **debug 包**是 DEBUGGABLE，量流畅度装 release（原生示例 `./gradlew assembleRelease`，已配 debug 签名）。
  `adb shell dumpsys package <包名> | grep flags=` 里有 `DEBUGGABLE` 就是 debug 包。
- **引擎库与 APK 并行编**：APK 打进旧库，「对比」其实是同一份代码。一个跑完再跑另一个，比 APK 里那份库的 md5。
- **停止标记**：测速脚本只剩 127 帧（≈1.4s）时先怀疑量具（踩坑记录「测速脚本自己坏了」）。
- **`KEYCODE_BACK`**：没有触摸时 ColorOS 把屏降到 60Hz，退场转场一半是「重复」。返回点导航栏的返回箭头。
- **共用手机**：别的检查（`flutter-android-check` / `android-native-check`）会装包、`force-stop`、转屏。
  量之前看一眼 `lastUpdateTime` 与前台窗口；脚本报「前台不是示例 App」「没进到 …」就是被打断了，重跑，不要拿结果。
- **「滑一会儿才顿」先量前后半段**：`android-jank.sh <页>-long` 打「前半 / 后半」各自的重复率，没变差就不是累积问题，
  去看 `🩹 >8ms` 那几帧是什么（多半是某块大东西被逐出画布窗口后滑回来重画）。
- ColorOS 上 App 日志量大了会整段静默；循环里的 `adb` 会吃掉 stdin（一律 `</dev/null`）。

（详情页）里找不到这个 swiper 的盒子，就退回整页重画：详情页每 3.7s 一个 60~72ms 的整帧，接着 0.5s 换页动画里每帧
21ms 整帧。改成找不到就不画（屏上看不见它）。`STORE_APP=news-app MINI_APP=native ENTER_TAP="540 1500"
bash tools/android-jank.sh detail-fastslow`（从首页点进详情再量）：**屏上重复 7.4% / 6.9% → 1.3~1.8%**（原生），
Flutter 1.4~1.5%，引擎整帧 0。直接深链到详情页量不出来（首页没起来，就没有在后台翻的轮播）——
量「从 A 页点进 B 页」的顿挫要用 `ENTER_TAP`。

**「刚开始不卡、滑着滑着卡起来」的底层原因（2026-10-24，诊断 20261024-153306「原生选茶师也是卡顿」/ 153041）**：
uni-app 产物的页面根是一个 `<scroll-view class="page">`（内容多高它就多高，滚的是页面）。引擎给 scroll-view 做了
整段内容的离屏缓存，可 `layout.rs` 在「数据没变、只换了滚动偏移」时也把这份缓存作废。于是：
- 一开始在预画好的条带（视口 ± 余量）里滑：只合成，2ms，**不卡**；
- 滑出条带后每帧都要补条带，**每次补条带都把这个 scroll-view 的整页内容重新光栅化**（ai-result 3705 行 × 1080，
  外加一块 16MB 新画布）：补 30 行桌面 8ms、PLY110 15~23ms —— **卡起来**。别的页面补条带 0.2ms。
改成只换偏移时不作废 scroll-view 缓存（缓存与页面偏移无关；数据 / 图片 / 字体变化照旧作废）：ai-result 补条带
画 p50 8.3 → 0.6ms，真机 `STORE_APP=tea-app STORE_PATH=pages/ai-result/ai-result … x-fastslow` 引擎 >8ms 的帧 0。
判据 `tests/sdk_damage_root_scroll_view.rs`（根 scroll-view 页面，局部 vs 整帧逐帧逐字节一致）。

同一类页面的第二个坑：根 scroll-view 内容不满一屏（不可滚）时，手指在上面拖，`input.rs` 的 `UpdateArea`
每次移动都置整帧 —— tea-app 分类 / 购物车 / 订单详情等 20 多页拖一下每帧整页重画 9~19ms。改成内层位置没变就不重画。
全量体检（`sdk_scroll_bench` 逐页跑 4 个小程序 65 页）：拖动中「整帧·结构 ← engine_input.rs」从 20 多页降到 0。
剩下的「整帧·动画」（real-sample 分类、tea-app 下单成功、sample-app 订单）是页面上有 CSS 动画，另案。

**Flutter 点胶囊 ⊙ 退出一卡**：① 路由退出动画 250ms 每帧要挪 SurfaceView 平台视图，Flutter 跟着平台线程同步出帧，
实测 45 帧/秒、最后一帧 55ms —— 退出改成不做动画（`reverseTransitionDuration: Duration.zero`）；② 平台视图先没、
销毁后到：引擎没了 Surface 回退 CPU 后照样按 vsync 白画，`dispose` 在主线程等放手时排在这些帧后面，tea-app 首页
等了 102ms —— `EngineCore` 丢了 Surface 就停帧（`surfaceLost`）。改后主线程等 0.3~1.6ms，退出那段上屏无 >15ms 的间隔。

**小游戏在 iPhone 上的零星长帧（2026-10-31，iPhone 16 Pro Max，`tools/ios-game-sweep.sh` + `MINI_GAME_SLOW_MS`）**：
稳态 pump 16ms 左右是 DVFS 把活摊满一帧，不算卡；手上的「顿」是每隔几秒一帧 40~80ms 的长帧。`-gameStats 1` 会顺带开慢帧归因
（`🐢 慢帧` 一行说清 JS 各段、最贵的 GL / 2D 调用、画布传纹理整张 / 部分 / 跳过）。萌宠小岛（UI 画在 2x 离屏画布上）这轮找到、改掉的：
- **渐变 / 阴影 / 合成模式的 fill 每次整画布做蒙版**：`paint_with_fx` 每次新建一张画布大小的蒙版、整张取覆盖率、整张浮点合成。
  改成蒙版按尺寸缓存在线程里、填充给外接框（画蒙版裁剪到框里、只在框里找写过的范围）、只在框里合成；竖直 / 水平线性渐变按行 / 列取样，
  覆盖率、源色、目标色与上一个像素相同时复用结果（`fx_mask.rs` / `fx_composite.rs`）。逐字节不变（gallery 65 张、damage-check、
  新加的两条单测）。真机上同一界面 `〔fx蒙版〕×5` 17.4ms → 8.7ms，`×8` 18.3ms → 2.2ms。
- **同一张 2D 画布反复 `texSubImage2D` 到同一纹理**：记住上次传的源像素，逐行比，只传首末变化行之间那段，一行没变不调 GL
  （`webgl/upload_cache.rs`；纹理被别的途径改过、挂过帧缓冲、删掉都会忘掉，`wg2b_画布增量上传` 守着）。小岛里这类重传从 952 行降到 65~95 行、
  1.6ms 以内。**没解决的**：每打开一个界面游戏都新建一张纹理，第一次整张传（880×1448 一次 13ms，三分之二在 ANGLE 里、三分之一在 Metal 转 tile 排布）。
- 结果：小岛 40 秒里超过 25ms 的帧中位 55ms → 38ms，p90 72ms → 57ms；最长间隔 83 → 62ms。保龄球 / 跑酷 / farm001 不变（60fps，掉帧 1 / 0 / 0）。
- 还在的长帧来源（按大小）：新纹理整张上传 8~15ms；普通 fill（非 fx）一个界面 8~17ms；`clear` 偶尔等 drawable 8ms；
  着色器第一次链接（`getProgramParameter` 一次 12ms，见过一次 242ms）—— ANGLE 的程序缓存没落盘，每次启动都重编。
- 试过没用的：Mach 时间约束线程（`thread_time_constraint_policy`，farm001 反而掉到 30fps，已删）；Game Mode 的 Info.plist 键（几乎无差别，留着）。
