# 测试场景总表

每一轮测试都按这张表对照：每个功能由哪个测试守着、怎么跑、跑多久、怎么判、这一轮过没过。
没跑的项写原因，不留空格。判据细节与能力矩阵见 [引擎测试说明](引擎测试说明.md)，真机顿挫的坑与当前数字见
[滑动顿挫避坑清单](滑动顿挫避坑清单.md)，固定流程见 [`.kiro/steering/30-test-and-cleanup.md`](../.kiro/steering/30-test-and-cleanup.md)。

## 0. 每轮怎么跑

| 步 | 做什么 | 命令 | 用时 |
|---|---|---|---|
| ① 定向速测 | 只测改到的那块，先把发现的问题修掉 | `cargo test --release --lib <过滤词>`、`python3 tools/test-fast.py --only <文件名>`、对应的真机脚本 | 2~30s |
| ①′ 全部用例 | 只跑 `test` 那一步（全部 Rust 用例，分片并行） | `python3 tools/test-fast.py`（`--quick` 跳过起 Chrome 的小游戏用例，`--changed` 只跑改动相关的） | 60~150s（含编译） |
| ② 全量（后台） | 第一节的 9 步 | `bash tools/regress-async.sh <标签>`，看 `target/test_batches/<批次>/summary.txt` | 3~4 分钟 |
| ③ 真机 / 模拟器 | 按第三节「什么改动必须跑」那一列挑 | 见第三节 | 每项十几秒到两分钟 |
| ④ 对照填表 | 在第五节加一轮：每项 ✅ / ❌（附数字）/ 没跑（附原因） | — | — |

测得快的几条（2026-11-01 实测）：

- **等待一律轮询**：等「🎮 第一帧上屏」、播放器状态、`[事件] page`，条件一到就往下走，不写死 sleep。
  `android-game-exit-audio.sh` 一个游戏从打开到判完 8~10s；按固定 12s 预热算，12 个游戏要多等两分钟多。
- **超时按墙上时钟算，不按次数**：一次 `dumpsys` / `logcat -d` 在一加 PLY110 上要几百毫秒，按次数写的「40 秒」实际等了 122 秒。
- **日志开一条 logcat 流写进本地文件再 grep**，别反复 `logcat -d` 从头翻：PLY110 的 logcat 环只有 256KB，ColorOS 几十秒就冲掉，
  要找的那一行可能已经没了。
- **全量放后台**：跑的时候写文档、跑真机，不改 Rust 源码（跑的就是工作区）。
- **定向用例很快**：lib 单测 1187 个全跑约 9s；示例小程序 e2e 每个文件 0.5~1s（虚拟时钟，见下）；最慢的是 `game_e2e`（起 Chrome 的那批，单个 10~18s）。
- **`tools/test-fast.py` 怎么快的**（2026-11-06，全部用例 707s → 61s，同一台机器）：按上次记下的每个用例耗时（`target/test_timings.json`）
  把每个测试二进制切成约 6s 一片、按 CPU 核数并行；起 Chrome 的用例（`web*_cases::`）放在后半段、最多 `--chrome` 个同时开
  （默认 3，机器空闲时 5）；失败的单独重跑一次，过了记「偶发」。每片的日志在 `target/_fast/`。
  示例小程序与 wpc 用例用**虚拟时钟**（`MiniEngine::use_virtual_clock`：定时器、JS 的 `Date`、动画时钟都跟 pump 给的毫秒走），
  不再真睡：从前一个文件 20 多秒里 CPU 只用了 1 秒。
- **PATH 上的 `python3` 是 x86 的 3.7（跑在 Rosetta 下）**：它起的 Chrome 也在 Rosetta 下，慢约 5 倍。`test-fast.py` 开头会换成
  `arch -arm64` 的原生 Python 重新执行自己（`MINI_FAST_NATIVE` 防重入）；别的脚本要起 Chrome 也照这样做。
- **起 Chrome 的用例跑完不留孤儿**：`game/web/cdp.rs` 经一个 `/bin/sh` 看门狗起 Chrome，测试进程被杀（含 SIGKILL）Chrome 跟着退。
  从前一轮崩掉的全量能留下 275 个 Chrome 吃满内存，下一轮全部超时。
- **真机构建串行**：引擎库 → `flutter build apk` / `./gradlew assembleRelease` → 装包。功能先在模拟器（emulator-5554）上验，手机留给计时、顿挫、GPU。

### 2026-11-06（七）· 青桔骑行首页：地图上的按钮全点不动

**改动**
- 现象：真机上 bike 首页铺满屏的 `<map>` 上，绝对定位的 cover-view（钱包 / 行程 / 报修、计费说明、定位 / 刷新、扫码开锁）一个都点不动；桌面无头点得动。
  示例本身是完整的（处理函数都在），是引擎的 bug。
- 原因：宿主点名 `sameLayerGestures: ["map"]` 后，`engine_host_views::gesture_view_at` 只看「按下点在不在地图框里」，在就整串触摸交给地图，
  盖在上面的按钮收不到 touchstart / tap。桌面不点名手势，所以走不到这条路。
- 修法：新 `wxml_renderer/cover_hit.rs`（`covered_at`）：正常流的绘制顺序 = 树的先序，排在地图之后、不是它祖先的节点（按祖先 overflow 裁过）盖住这一点就算盖住；
  正常流的地图再先问 `fixed_layer_hit`。盖住了：不交给地图（`gesture_view_at`），点击也不再转 `nativeViewTap`（`on_tap`，免得点卡片时地图判成点了下面的标记）。
  没绑事件的卡片同样挡（与浏览器命中一致）。

### 2026-11-06（六）· 车管家门店页：「导航」「去预约」的字贴在按钮上沿
