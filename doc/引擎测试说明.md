# mini-render 引擎测试说明

**对齐目标**：微信小程序 **Skyline** 渲染引擎。所有「期望」列写的都是微信的行为，不是我们自己的约定。

**本文档的用法**：
1. 改动引擎之后，按「第一节 一条命令跑完回归」跑一遍，六项判据全绿才算没回归；
2. 新增能力时，按「第五节 逐项测试清单」的编号追加条目 + 补自动化测试；
3. 发现新的差距时，写进「第六节 已知差距」，不要留在聊天记录里。

---

## 一、一条命令跑完回归

```bash
bash tools/regress.sh            # 下面 0)~6)、8) 全部串起来跑，每步计时
bash tools/regress.sh --no-h5    # 不跑 8) 的 H5 对比（不起 headless Chrome）
bash tools/regress-async.sh <标签>  # 同一套放后台跑，结果进 target/test_batches/<时间>-<标签>/（meta / run.log 每行带时刻 / status / summary / logs）
bash tools/regress-async.sh --status  # 所有批次的时间线（index.tsv）与进行中的批次
bash tools/android-jank.sh <场景> [install]  # 真机定向速测（一个场景几十秒）：index/wxss/http/query/swiper/perf-slow|fastslow、perf-idle、enter-query|feedback|storage|form、resume、sheet
```

汇总写在 `target/_regress/summary.txt`，每步一行：耗时、OK / FAIL / 看图、结论。
「看图」= gallery 与 HEAD 有差异，脚本逐张给出差异占比与包围盒，要人判断是不是有意改动。
2026-10-21 实测（负载 20~25、交换区已满）：构建之后的各步合计 **198s** —— 测试 73s、damage-check 16s、
gallery 9s、tabBar 20s、快照 19s、SDK 一致性 12s、交互 26s、H5 对比 23s。构建本身：改了引擎之后
`cargo build --release --all-targets` **19~22s**；换了编译参数 / 依赖时全量重编 262s。

从前一轮要几个小时，大头是 **thin LTO**：它给五十来个最终二进制（bin / example / 集成测试 / cdylib）
每个都把整张依赖图重新优化一遍。同一份源码背靠背：改了引擎之后编全部目标 thin LTO **2905s**、
单个二进制的 LTO 链接 4~11 分钟；关掉 LTO + 增量 19~22s。gallery 65 张两种编法**逐字节相同**、
跑完 65 个场景的耗时分不出差别（4.4~5.7s 对 5.0~5.3s）。所以 `Cargo.toml` 的 release 关了 LTO、开了增量，
发出去的库（`tools/build-mobile.sh`、`scripts/build-*`）用环境变量开回 thin LTO。
其余的时间花在等：别的会话占着 target 锁、内存吃紧时换页、`damage-check` 每张快照死等 9s（已改成等进程退出）。

逐条手跑：

```bash
. "$HOME/.cargo/env"

# 0) 清测试污染（必做，见下方警告）
rm -rf target/mini-storage

# 1) 编译
cargo build --release && cargo build --release --examples

# 2) 单元测试
cargo test --release   # lib 774 + bin 26 + 集成测试 72（22 个文件，tests/*.rs）

# 3) 增量重绘正确性：每个用例的「增量」与「整帧」必须逐字节一致
bash tools/damage-check.sh

# 4) 场景画廊：65 张，确定性渲染，与上次产物应逐像素一致
cargo run --release --example gallery

# 5) 底部 tabBar 点击：三个示例小程序 × 每个 tab，共 12 行
bash tools/tab-click-check.sh

# 6) 移动端 SDK 与桌面窗体的像素一致性（两条宿主路径不许分叉）
bash tools/sdk-parity.sh
bash tools/sdk-parity.sh sample/news-app target/fin2_news

# 7) 交叉编译（iOS / Android 目标能编）
bash tools/build-mobile.sh check

# 8) 逐页快照 + 与 HTML 参考实现对比
bash tools/snapshot-all.sh sample-app      target/fin2_sample --settle 0 --time 2
bash tools/snapshot-all.sh sample/news-app target/fin2_news   --settle 0 --time 2
./target/release/examples/compare --all --rust-from target/fin2_sample --out target/fin2_cmp
./target/release/examples/compare --all --app news-app --html dist-news \
    --rust-from target/fin2_news --out target/fin2_news_cmp
```

### 两个必须知道的坑

**1. 跑任何快照前先 `rm -rf target/mini-storage`。**
无头点击/输入会把数据落到 `target/mini-storage/<app>.json`，下次启动读回来，页面内容就和基线不同了。
曾让 sample 的购物车页从 1.51% 假崩到 10.05%。`tools/snapshot-all.sh` 与 `tools/tab-click-check.sh` 内部每页都会清一次。

**2. `sample-app` 的基线快照必须用 `--settle 0`。**
`pages/index/index` 有一个延时弹出的「新人专享礼包」浮层，`--settle ≥ 0.5` 就会弹出来，
与基线产生 93.9% 的**假**差异。要测这个浮层请单独跑一次 `--settle 1` 并肉眼看。

### 逐像素比对工具

```bash
python3 tools/pixdiff.py a.png b.png
# 输出：差异像素 1510/1076250 (0.140%)  包围盒 x[24,148] y[1333,1382]  最大通道差 153
```
包围盒是判断「真回归 or 动画相位噪声」的关键：差异集中在某个组件的矩形里通常是真改动，
散落全页多半是时钟/动画相位。

### 手工验证用的无头命令

```bash
./target/release/mini-app-window <app> [--route R] [--settle 秒] [--time 秒] [动作...] --snapshot 目录
```

动作按**书写顺序**执行，可重复：

| 动作 | 含义 |
|---|---|
| `--touch x,y[,按住ms]` | 完整触摸序列 touchstart→(长按)→touchend/tap。**测点击一律用这个** |
| `--click x,y` | 直接调 handle_click，**绕过指针层**，只用于隔离定位 |
| `--press x,y` | 按下保持（验证 `:active` / `hover-class`） |
| `--swipe x1,y1,x2,y2[,步数]` | 滑动手势 |
| `--swipe-hold 同上` | 停在终点不抬手（截手势进行中的一帧：橡皮筋、侧滑返回位移） |
| `--drag px×帧数` | 拖动并逐帧计时（滑动手感的可回归测量） |
| `--wheel x,y,dx,dy[,步数]` | 触控板双指滑动 |
| `--wheel-lines 同上` | 普通滚轮（行滚动） |
| `--type 文本` / `--key 按键` | 输入（先 `--click` 到输入框） |
| `--wait 秒` | 空转等待，期间照常出帧 |
| `--frames N` | 按刷新率跑 N 帧（局部重绘/动画类问题只有连续出帧才暴露） |
| `--eval JS` | 可重复，在 `--settle` 之后依次执行 |

> **`--click` 与 `--touch` 的区别曾经藏过一个真机 bug**：按下 tabBar 时提前 return，
> 触摸状态机没启动 → 抬手没有 tap → `handle_click` 永远不被调用。
> `--click` 全绿，真机上 tabBar 完全点不动。所以点击类回归**只认 `--touch`**。

### 诊断开关

| 环境变量 | 打印什么 |
|---|---|
| `MINI_SCROLL_LOG` | 手势归属、滚动状态、页面滚动上限 |
| `MINI_SCROLL_TREE` | 滚动容器树 |
| `MINI_FLEX_LOG` / `MINI_LAYOUT_LOG` | flex / 布局求解 |
| `MINI_IMG_LOG` / `MINI_NET_LOG` | 图片解码 / 网络 |
| `MINI_FONT_LOG` | 字体加载三段计时 |
| `MINI_FIXED_LOG` | fixed 覆盖层 |
| `MINI_CANVAS_LOG` | 画布每批指令的条数，以及每次把画布拷进页面时的位置、尺寸与 dpr（`type="2d"` 动画每帧一批，默认不打） |
| `MINI_MENU_BUTTON=0` | 桌面窗体不画右上角胶囊（对照「没有胶囊」的画面时用；SDK 那边由创建选项 `menuButton` 决定） |
| `MINI_SLIDER_LOG` | slider 派发给逻辑层的每一次 `changing` / `change`（id 与 `detail.value`）。拖动归属看 `MINI_SCROLL_LOG` 的「手势归属 → Slider」 |
| `MINI_TEXT_PROBE=<原文>` | 指定文本的度量细节 |
| `MINI_NO_DAMAGE` | 关闭局部重绘（强制整帧） |
| `MINI_FAKE_NOW=2024-03-15` | **把 JS 的 `Date` 钉在某一刻**（也可给 epoch 毫秒）。有页面用 `new Date()` 高亮当天（news-app 的签到日历），不钉住的话像素基线**跨天就失效**；`--time` 只固定 CSS 动画时钟，管不到 `Date`。六个回归脚本都默认 `2024-03-15`，想换就在命令前面覆盖 |
| `MINI_FPS` / `MINI_DRAW_LOG` | 帧率 / 绘制调用。`MINI_FPS` 每秒那行以后端标签开头（`📊 [后端 CPU] …`）；SDK（`MiniEngine`）也有同口径的一行，分开报 pump / 工作 / 等 surface |
| `MINI_DAMAGE_LOG` / `MINI_NO_DAMAGE`（SDK） | `MiniEngine` 每出一帧打一行重画了多少：`只合成` / `局部 宽x高@(x,y)` / `补条带` / `整帧·原因`（结构 / 数据 / 动画 / 媒体 / 滚动区）。整个 pump 超过 8ms 时另打一行 `⏱ [SDK] pump`，带重画之前那几段（换页留图、建页、事件回调、取页面数据、重建布局 + 比对，后者再分〔模板 / 建树 / 布局 / 换行 / 比对〕）。`MINI_NO_DAMAGE` 关掉局部重画、有变化就三层全画（引入局部重画之前的行为），是 `tests/sdk_damage_equivalence.rs` 逐帧逐字节比对的参照；SDK 的滚动手感用 `cargo run --release --example sdk_scroll_bench` 量（按宿主节奏 pump + 写像素，分帧种报耗时） |
| `MINI_BACKEND=auto\|cpu\|gpu` / `--backend` / `--backend-probe` | 渲染后端偏好与探测（GPU 默认编进来，只要 CPU 用 `--no-default-features --features desktop,audio,h264`；判据见「五之三、渲染后端基准」与 `tools/gpu-parity.sh`）。`snapshot-all` / `damage-check` / `sdk-parity` / `interaction-check` / `tab-click-check` 都默认 `cpu`：逐字节基线以 CPU 为准 |

## 四、能力矩阵：事件、WXML/WXSS、wx.\*

### 真正会派发给逻辑层的事件

| 事件 | 触发 | detail |
|---|---|---|
| `touchstart` / `touchmove` / `touchend` / `touchcancel` | 触摸状态机 | `touches` / `changedTouches` / `target` / `currentTarget` / `timeStamp` |
| `longpress` + `longtap` | 长按（两个名字都发，与微信一致） | 同上 |
| `tap` | 抬手且未构成滑动 | `{x, y}` |
| `change` | checkbox / switch 切换、radio 选中、slider 拖动结束、picker 选完 | `{value}`（在 `checkbox-group` 内时是选中值数组，按文档顺序） |
| `focus` / `input` / `blur` / `confirm` | 输入框 | `{value}`（**字符串不强转**） |
| `load` / `error` | `<image>` 有结论时，每个 `(组件, src)` 只发一次 | `{width, height}` / `{errMsg}` |
| 页面 `onPageScroll` | 滚动位置每帧变化 | `{scrollTop}` |
| 页面 `onReachBottom` | 滚到底部 | — |
| 页面 `onPullDownRefresh` | 下拉到位并松手（**不是**滚到顶就触发） | — |

绑定前缀六种全支持：`bind` / `catch` / `capture-bind` / `capture-catch` / `mut-bind` / `bind:`。
派发顺序：捕获外→内，冒泡内→外；`catch` 就地截断；`mut-bind` 只触发最内层。
组件内的绑定按 `owner`（`COMPONENT_OWNER_ATTR`）派发给组件实例，不会误派发到页面。

### 分项实测（本机 macOS，`examples/mem_report`，RSS 增量）

| 阶段 | 上游 fontdue（预展开全部字形） | 现在（`vendor/fontdue` 惰性展开 + mmap） |
|---|---|---|
| 系统主字体常规字面（Hiragino Sans GB.ttc，23MB 文件 / 29352 字形） | **+304 MB**，加载 ~350ms | **+1.4 MB**，加载 3ms |
| 同一字体集合里的粗体字面（首次画粗体时才解析） | **+279 MB** | **+1.3 MB** |
| 内置单字面 SourceHanSansSC-Regular.otf（16.5MB / 6.5 万字形） | +405 MB | +2.0 MB |
| 一个自定义字族（Songti.ttc，63.8MB 文件） | +154 MB，解析 ~300ms | ≈0，解析 1ms |
| 1200 个不同汉字的字形位图缓存 | +8.7~16 MB | +13.7 MB（按字节封顶 24MB，`MINI_GLYPH_CACHE_MB`） |
| 整个报告进程结束时 | 约 740 MB | **26.6 MB** |

真实页面（`examples/font_mem_pages`：Flutter 示例小程序 30 个页面挨个打开、各滚 6 屏，360×785 @3）：
3 个字面一共展开 1113 个字形，字体堆占用 = 几何 2.1MB + 表 2.1MB + 位图缓存 2.5MB ≈ **6.7MB**（`memory_report()` 末尾那段）。
一加 PLY110（`dumpsys meminfo`，Flutter 示例 `query-slow` 之后）：Native Heap 289 → 102MB、TOTAL PSS 374 → 194MB；
字体文件是 mmap 进来的文件页（`.ttf mmap` 一行，约 12MB PSS，干净页、可回收）。剩下的 Native Heap 不是字体（画布、图片、视频等）。

**原因与修法**：上游 fontdue 在 `Font::from_bytes` 时就把字体里**所有**字形的几何展开好
（`font_mem_probe`：29352 字形 → 305MB）。`vendor/fontdue`（改动见它的 `README.mini.md`）改成第一次用到某个字形才展开，
展开代码与上游逐行相同，所以度量与光栅化逐位一致（gallery 65 张、damage-check、sdk-parity、H5 对比全部不变；
`tests/font_lazy_e2e.rs` 把它和 crates.io 上的上游 0.9.3 放在一起，逐码位比 cmap、逐字形比度量与位图）。
字符 → 字形表也不在加载时建（每字面约 1MB），用到哪个字查哪个；轮廓线段按 1MB / 字面封顶（光栅化只在第一次画某个字号时要它）。
字体文件改成只读 mmap（`text/load.rs` `map_font_file`）：文件页按需进内存、可回收，同一个 TTC 的常规 / 粗体字面共用一份；
文件哈希也改成用到才算（不然 mmap 的每一页都会被读一遍）。探测粗体字面从前每个候选字面都要整个展开一遍
（Songti 5 个字面 ≈ 1.4s），现在只展开探测用的那一个字。

### 引擎缓冲：分项、条带外释放、后台释放

字体压下来之后，大头是一屏一屏的像素缓冲。先看分项再动手：`MiniEngine::memory_breakdown()`（`host/engine_memory.rs`）
逐项给「驻留 / 分配」，`MINI_MEM_LOG=1`（Android `setprop debug.mini.mem_log 1`）每次进后台打一行 `🧠`。
驻留量 Linux / Android 读 `/proc/self/pagemap`，只算「在内存里且只映射给本进程」的页（`mem_probe.rs`）——
mincore 会把只读过的零页也算驻留，覆盖层每帧整张扫一遍，从前显示 8.5MB，其实 0.6MB。macOS 仍是 mincore（偏高）。

| 项 | 做法 |
|---|---|
| 页面画布 | 已绘制条带以外的行 madvise 还给系统（读之前一定先清再画）；条带挪动超过 256 行才重做 |
| 覆盖层画布 | 全是 0 的行还掉（`row_spans` 一遍扫出不透明行与非零行） |
| 侧滑返回截图 | 只有最后一张原样留着，之前的按「整行重复 + 游程」无损压（`shot_pack.rs`，一屏 9.5MB → 几百 KB）；进后台最后一张也压，回前台解开 |
| 合成缓冲 / RGBA 读出缓冲 | 截图直接拿走合成缓冲（不再拷一份）；进后台两块都放掉，回前台整帧重新合成时按尺寸重新分配 |
| 渐变行缓存 | 6M → 2M 像素（≈8MB）封顶；进后台与 `trim_memory` 清掉 |
| `trim_memory` | 另清字形位图缓存、跑一遍 QuickJS GC |

## 五之三、渲染后端基准

**所有关于渲染后端（CPU / GPU）的性能结论只引用这一套基准的输出**，不引用随手跑的 `--drag`。
判据看最慢一帧与帧间隔峰值（steering 10），平均值不进表。

### 怎么跑

```bash
cargo build --release && cargo build --release --examples
cargo run --release --example backend_bench -- --backends cpu --runs 5 --mode both
#   [--backends cpu,gpu] [--scenes S1,R1,…] [--out target/_bench]
```

- 每个「场景 × 缩放 × 模式 × 后端」跑 5 次，每次是一个独立子进程，跑前会先 `rm -rf target/mini-storage`，并固定 `MINI_FAKE_NOW=2024-03-15`。表里取 5 次的中位数，最慢一帧另外报 min~max。只统计 drive 段，settle 和 eval 段不算。
- **防空转守卫**：滚动类场景实际滚动距离要 ≥ 请求距离的 90%；S2 的动画帧要 ≥ 90%；S4 的重画帧要 ≥ 30%；S5 的 Modal 要每帧都弹着；GPU 运行时每一帧的 backend 都必须是 gpu。守卫不过，这个场景就判失败（退出码 1）。
- 窗口模式要求显示器是 144Hz，不是的话打印「⚠️ 显示器 …Hz，不是 144Hz，窗口判据未测」，退出码 3。窗口模式的数字照样记录，但不能用来判定。
- 夹具生成在 `<out>/apps/`，首帧确认图在 `<out>/shots/`，每次运行的原始 JSON 在 `<out>/runs/`。

### 怎么读：最慢的帧慢在哪

每一行都按 JSON 逐帧分段（`logic` / `render_page` / `compose`）归过因，结论如下：

- **R1 每一帧都在重建整页布局**：p50 17.8ms，其中「模板 1.0 + 建树样式 4.0 + 布局 6.6 + 换行修正 2.2」ms，`MINI_LAYOUT_LOG` 每帧都会打一行「重建布局」。根因在 `renderer/wxml_renderer/layout.rs`：布局缓存把 `(scroll_offset, viewport_h)` 当作缓存键，可实际参与布局的只有 `viewport_h`。首页上有 CSS 动画，每一帧都要走损伤区重绘，这一趟会带着新的滚动偏移去问布局，结果被判成「视口变了」，于是整页重建并退回整带重画。**这和 GPU 无关**，是本轮 P3a 要修的第一项。
- **S1 的跨条带帧要 44~225ms**：p50 只有 0.22ms（纯合成），但每滚过约 208px 就有一帧整带重画，时间全落在 `render_page`。两张卡片之间的距离是 8.4ms 一帧的 26 倍，30 帧里有 1 帧掉得很深，手上就是每 0.2 秒顿一下。这也是 CPU 光栅瓶颈，P3a 的第二项会只补画新露出的条带。
- **S2 大面积动画 p50 16.6ms**：每帧都把子树离屏重画一遍，再逐像素做逆仿射，属于 P3 图层化的范围，本轮不做。GPU 合成器（P1）也帮不上，因为内容仍由 CPU 光栅。
- **S6 嵌套 scroll-view p50 1.7ms**：只重画 scroll-view 自己的盒子，帧成本低。偶发的 18ms 尖峰落在 `logic` 段（JS / 定时器），不是光栅。
- **合成本身很便宜**：合成 p99 在 0.4~2.2ms（无头 `cpu::compose`）。窗口模式的 softbuffer 上屏在 0.2~0.9ms。所以 GPU 合成器在桌面上能省下的上限，就是这 1~2ms 的合成和上屏；**最慢的那些帧都在光栅和布局里**。
- **单次长尾**：S2 / R1 3× / S3 3× 的 max 有 98~178ms，而同组的中位数只有 13~52ms，分段里也看不出集中在哪一段，推测是系统抢占。所以表里取中位数，并把 min~max 一起写出来。

### 跨时段比较要做 A/B

同一个二进制隔半小时再跑一遍，S1 2× 的 p50 能从 0.22ms 变成 0.93ms，机器的热状态会漂。所以「改动前后」的数字**必须在同一时段交替跑**：用 `MINI_BENCH_BIN=<改动前的二进制>` 跑一轮，再用改动后的二进制跑一轮，至少重复 2 轮。不要拿这一节上面的基线表和隔了很久的新数字直接比。

### P3a 第一项：滚动时不再重建布局（A/B，2 轮 × 3 次，CPU）

改动见 `renderer/wxml_renderer/layout.rs`：数据没变、只有滚动偏移变了的时候，布局树原样复用，但这一帧仍按整帧重画。重画范围与以前完全一样，所以像素逐字节不变。

| 场景 | 改动前 最慢一帧 / p99 / p50 | 改动后 最慢一帧 / p99 / p50 |
|---|---|---|
| S1 2× | 46.7~80.9 / 40 / 0.21 ms | 2.0~3.7 / 1.4~1.6 / 0.22 ms |
| S1 3× | 56~64 / 42 / 0.42 | 4.5~9.6 / 2.9~3.1 / 0.42 |
| R1 2× | 28.4~29.9 / 26 / 17.9 | 13.1~13.3 / 11 / 3.4 |
| R1 3× | 59~78 / 40~47 / 24.5 | 23~27 / 20~21 / 6.6 |
| S6 2× / 3× | 1.0~1.3 / 3.3~8.2 | 1.5~1.6 / 1.7~2.7（持平，scroll-view 滚动本来就不走页面偏移） |

S1 的改善最大，而这个场景根本没有动画：跨条带那一帧要整带重画，以前这一趟会顺带带着新偏移把 300 张卡片的布局整棵重建一遍（40~100ms），现在只剩重画（2~3ms）。R1 剩下的 p99 11ms 来自「CSS 动画帧 + 滚动偏移变了」时的整带重画，这要靠下一项「只补画新露出的条带 / 动画帧走局部重绘」来解决。

### GPU 后端的正确性判据：阈值 0

GPU 后端只做**合成**，内容仍由 CPU 光栅化。合成算术在着色器里用整数原样复刻：源纹理是 `Rgba8Uint`，`textureLoad` 不经过采样器；不开硬件混合；输出加 0.25 偏置，抵消 float→unorm 的舍入差异。Toast、Modal、picker、侧滑这类覆盖层帧走「直通」：整帧由 CPU 合成后上传。所以同一份图层，GPU 输出与 CPU **逐字节相同**，阈值定为 **0 个差异像素（所有帧，分层与直通都一样）**，不需要按驱动标定百分比。

判据是 `bash tools/gpu-parity.sh`（先 `cargo build --release && cargo build --release --examples`，gpu 已在默认 feature 里）。退出码：0 = 通过；1 = 不一致；3 = 没有可用 GPU（不算通过）；4 = 没编 gpu。它检查这些：

| 项 | 怎么比 | 结果（Apple M3 Pro · Metal） |
|---|---|---|
| 静态页 | sample-app 15 页 + news-app 6 页，CPU 与 GPU 各出一张快照，逐字节比较；GPU 运行同时开 `MINI_GPU_VERIFY` | 21/21 一致 |
| 增量重绘 | damage-check 的 5 个用例，各 `--frames 30`，**同一次运行里**逐帧把 GPU 读回与 CPU 合成对拍 | 5 × 32 帧全部一致 |
| 连续拖动 | R1 / news 首页 / S1 / S6 拖动，S5 Modal 空转，逐帧对拍（覆盖滚动、跨条带、环形镜像回绕、直通帧） | 270 / 287 / 399 / 216 / 94 帧全部一致 |
| 交互 | `MINI_BACKEND=gpu` 跑 interaction-check（picker、Modal、按压、长按），对照 CPU 基线 | 7/7 一致 |
| tabBar | `MINI_BACKEND=gpu` 跑 tab-click-check | 全部通过 |
| 防空转 | 每个 GPU 运行的日志都要有「渲染后端：GPU」；逐帧校验数 N ≥ 请求帧数的 90%；分层和直通两种模式都要出现过；注入 `tint`（R+1）必须报不一致 | 全过；tint 被检出 |
| 回退 | `init` / `selftest` / `lost@30`（S1 夹具）：日志里要有回退行，快照与 CPU 逐字节一致 | 3/3 |

带墙上时钟的场景只在同一次运行里逐帧对拍，不跨两次运行比 PNG。这类场景包括拖动后的惯性和回弹、showcase 页的 GIF 取帧、Loading 转圈。同一个二进制跑两次，它们本来就不一样（showcase 页那张 GIF 格偶发差 0.22%，包围盒 x[616,698]，正好落在动图上），跨运行比较测到的是时钟，不是 GPU。

单元测试（`cargo test --release`）有四项：50 组随机图层配置对拍；同一个合成器连续 200 步（整带写、矩形写、滚动、换画布、跳帧）对拍；tint 必须被检出；`lost@2` 必须报设备丢失。没有适配器时打印「GPU 未测」并跳过，决定性判据仍是 `gpu-parity.sh`。

窗口模式的回退（A1.5）：S1 夹具窗口 `--drag 8x300 --bench`，分别注入 `MINI_GPU_FAULT=lost@120` 和 `surface-lost@120`。两次都是第 120 帧当帧回退。回退前每一帧 `backend == "gpu"`，回退后每一帧 `backend == "cpu"`，300 个 drive 帧全部上屏，没有跳帧，进程退出码 0。日志分别是「设备丢失（Destroyed）」和「surface 无法恢复」。

体积（A1.7）：`mini-app-window` strip 后，不带 gpu 是 37.6MB，带 gpu 是 42.0MB，**增量 4.38MB（+11.6%）**，在 8MB 的软上限以内。
交叉编译：Android 三个 ABI（arm64-v8a / armeabi-v7a / x86_64）在 `--no-default-features --features bindgen,gpu` 下 `cargo check` 都能通过。
iOS 没能验证：本机只有 CommandLineTools，没有 iphoneos SDK，`ring` 的 build.rs 在走到本仓库代码之前就失败了。

**未验证**：真实上屏的色彩（A1.10）。离屏读回是逐字节一致的；屏上 surface 显式配成 `SurfaceColorSpace::Srgb`，与 softbuffer 的 CPU 路径是同一个色彩空间。但还没做两个后端窗口截图（`screencapture -l`）的像素对比。这一步需要屏幕录制权限，复现命令是 `screencapture -l <窗口号> a.png`，两个后端各截一张，再跑 `python3 tools/pixdiff.py a.png b.png`。

### CPU 与 GPU 对比（同一时段，5 次中位数，提交 `dc6c19b` + GPU 改动）

机器：Apple M3 Pro，内建 ProMotion 屏，**120Hz**，所以窗口判据未测（R12）。节拍按 `--hz 144`。GPU 窗口模式用 Fifo 交换链，帧间隔实际跟着显示器的 8.33ms 走。复现命令：`cargo run --release --example backend_bench -- --backends cpu,gpu --runs 5 --mode both`。

| 场景 | 模式 | CPU 最慢 / p99 / p50（ms） | GPU 最慢 / p99 / p50（ms） | GPU 完成 p99 | 结论 |
|---|---|---|---|---|---|
| S1 列表滚动 2× | 窗口 | 8.80 / 6.95 / 3.06 | **3.42 / 2.45 / 0.37** | — | GPU 快：上屏不再拷 100 万像素，p50 降到 1/8 |
| S6 嵌套滚动 2× | 窗口 | 4.76 / 3.55 / 3.27 | **1.27 / 1.20 / 1.00** | — | GPU 快，p99 降到 1/3 |
| S5 Modal 2× | 窗口 | 8.00 / 7.64 / 3.47 | **2.99 / 2.93 / 1.69** | — | GPU 快（直通帧也只剩一次上传） |
| S3 阴影大图 2× | 窗口 | 9.19 / 7.64 / 2.96 | **7.07 / 5.62 / 0.32** | — | 跨条带那帧是光栅，持平；平时的帧 GPU 快 |
| R1 首页 2× | 窗口 | 17.80 / 13.61 / 6.10 | **13.24 / 12.11 / 3.90** | — | 剩下的是动画帧整带重画（光栅），GPU 帮不上 |
| S2 大面积动画 2× | 窗口 | 50.76 / 40.10 / 19.49 | 20.81 / 18.00 / 15.53 | — | 每帧离屏重画子树（光栅），p50 两边都在 15~20ms，要靠图层化（P3） |
| S4 整屏重绘 2× | 窗口 | 14.44 / 12.14 / 3.05 | 13.12 / 10.51 / 0.64 | — | 光栅主导，持平 |
| S1 2× | 无头 | 3.20 / 1.79 / 0.22 | 6.01 / 3.41 / 1.09 | 1.53 | 无头 GPU 要等 `poll(Wait)` 做完，CPU 合成本身只有 0.5ms：GPU 更慢 |
| S6 2× | 无头 | 1.94 / 1.64 / 0.63 | 16.30 / 5.98 / 2.06 | 2.37 | 同上 |
| R1 2× | 无头 | 37.33 / 22.05 / 3.90 | 18.99 / 15.95 / 5.13 | 2.15 | 光栅主导（两边的最慢帧都是动画帧整带重画） |

怎么读这张表：

- **GPU 快在真实上屏**。窗口模式下，CPU 的 softbuffer 每帧要把整个视口转换并拷进窗口缓冲（含 macOS 合成器那一侧）。GPU 只上传变了的行，合成和上屏由 GPU 做，主线程每帧只剩约 0.4ms 的编码和提交。S1、S6、S5 的 p50 和 p99 都降到 CPU 的 1/3 到 1/8。
- **无头模式下 GPU 更慢，这是测量口径造成的，不是退步**。无头基准里每帧都 `poll(Wait)` 等 GPU 做完（为了量「GPU 完成」时间），而 CPU 在无头下只合成进内存、不上屏，本来就只要 0.2~1ms。无头数字用来看「GPU 完成」时间（p99 1.5~3.9ms，都低于 120Hz 一帧的一半），不用来比快慢。
- **光栅主导的场景（S2、S4、R1 的动画帧、跨条带帧）两边差不多**。内容仍由 CPU 光栅化，GPU 合成器省不掉光栅。这几项要靠 P3 图层化：动画子树缓存、只补画新露出的条带。
- **帧间隔峰值不能按 144Hz 判**。GPU 窗口模式由 Fifo 按显示器（120Hz）出帧，帧间隔中位数是 8.33ms；S5 / S6 的峰值里有 1~2 次 16~25ms，是 Fifo 偶尔错过一个 vsync。在 144Hz 显示器上复测前，这一项只陈述数据，不作为判据。

### GPU 窗口模式的掉帧：查到了什么、改了什么（120Hz 屏，真开窗）

背景：开窗手点开关时，`MINI_FPS` 里 GPU 一行显示「上屏 15.9 / 39 / 85ms」，看上去像是 GPU 上屏很慢。查下来有三件事：

1. **「上屏」把等 vsync 算进去了，数字本身有误导。** Fifo 的 acquire 按设计会阻塞到下一个 vsync，所以 GPU 的每一帧都会显示「上屏 7~8ms」，真正的上屏开销（约 0.4ms）看不出来。现在 `MINI_FPS` 的「最慢一帧」和「上屏」都扣掉了 acquire 等待，等待时间单独显示，格式是 `上屏 0.4[等 vsync 7.9]`。CPU 那一行格式不变。判断有没有掉帧，看「帧间隔」：它是墙上时钟，什么都没扣。
2. **上屏顺序：先准备，再 acquire。** 原来是先 acquire，拿到 drawable 再同步纹理。直通帧（Toast / Modal 弹着）要先由 CPU 合成整帧、再上传 4MB，这 1~10ms 全压在「拿到 drawable → 下一个 vsync」那一个周期里。现在先做完上传和 uniform，再去等 drawable。用每 300ms 弹一次 Toast 的场景 A/B，5 轮：掉帧 0/1/2/3/3 → 0/0/1/1/1，合计 9 → 3。
3. **剩下的掉帧不在合成器里，在 CPU 光栅。** 用「每 300ms setData + 弹 Toast」的场景 A/B，3 轮：

   | 场景（每 300ms 一次） | CPU | GPU 改前 | GPU 改后 |
   |---|---|---|---|
   | setData + Toast（360 帧） | 掉 10/10/10 帧，峰值 40.9~43.0ms | 掉 15/10/10，峰值 38~69ms | 掉 11/10/10，峰值 37.8~40.3ms |
   | 只弹 Toast（360 帧） | 0/0/0，峰值 8.5~8.9ms | 合计 9（5 轮），峰值最高 124ms | 合计 3（5 轮），峰值 ≤ 16.6ms |
   | 列表拖动 S1（300 帧） | 0/0/0 | 0~1 | 0~1 |

   setData 场景里 CPU 和 GPU 掉的帧数一样，都在 10 帧左右，掉的正是 setData 那一帧，`render_page` 约 37ms。这 37ms 两个后端走的是同一份 CPU 代码，换 GPU 也解决不了。

   **归因：慢在重建布局，不在光栅。** 无头复现同一个 setData（`items[0].title`，300 张卡片），打开 `MINI_LAYOUT_LOG=1`：

   ```
   ⏱  重建布局：模板 22.0ms  建树+样式 5.1ms  布局一遍 11.9ms  换行修正 0.5ms
   🩹 setData 增量重绘 542x41 @(160,59)  覆盖层复用
   ```

   重绘已经收窄到改动的那一行标题（542×41），光栅只占零头。贵的是前面那段：只改一个字段，也要把 300 项的 `wx:for` 模板整页重新展开、重新建树、重新排一遍。（6 次采样，模板 22~41ms，建树 5~8ms，布局 12~23ms，测的时候 load average 约 57，数字偏高。）Skyline 对 setData 是按路径 patch 改到的节点，不重排整页。所以真正要做的是「按路径的增量模板 + 局部重排」，属于 `setData` 增量失效的后续工作，与 GPU 后端无关。

**试过、没有收益、已撤回的两个方案**（都是 3 轮 A/B 的结论）：

- 直通帧纹理双缓冲（两张轮换写）：Toast 场景掉帧没有减少（合计 3 对 0）。
- Immediate 呈现 + 自己的节拍器：setData 场景 31 对 36，Toast 场景 1 对 2，差别在噪声以内。而且 Immediate 会让 GPU 帧和显示器脱钩，不值得换。

**测量注意**：这几组只在机器空闲时测。实测其他会话在编译时（load average 30），同一个二进制的峰值会从 38ms 跳到 150ms，Toast 场景的单次峰值也会冒到 70~124ms。
