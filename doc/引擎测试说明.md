# mini-render 引擎测试说明

**对齐目标**：微信小程序 **Skyline** 渲染引擎。所有「期望」列写的都是微信的行为，不是我们自己的约定。

**本文档的用法**：
1. 改动引擎之后，按「第一节 一条命令跑完回归」跑一遍，六项判据全绿才算没回归；
2. 新增能力时，按「第五节 逐项测试清单」的编号追加条目 + 补自动化测试；
3. 发现新的差距时，写进「第六节 已知差距」，不要留在聊天记录里。

## 一、一条命令跑完回归

```bash
. "$HOME/.cargo/env"

# 0) 清测试污染（必做，见下方警告）
rm -rf target/mini-storage

# 1) 编译
cargo build --release && cargo build --release --examples

# 2) 单元测试
cargo test --release   # lib 415 + bin 53

# 3) 增量重绘正确性：每个用例的「增量」与「整帧」必须逐字节一致
bash tools/damage-check.sh

# 4) 场景画廊：65 张，确定性渲染，与上次产物应逐像素一致
cargo run --release --example gallery

# 5) 底部 tabBar 点击：三个示例小程序 × 每个 tab，共 12 行
bash tools/tab-click-check.sh

# 6) 逐页快照 + 与 HTML 参考实现对比
bash tools/snapshot-all.sh sample-app      target/fin2_sample --settle 0 --time 2
bash tools/snapshot-all.sh sample/news-app target/fin2_news   --settle 0 --time 2
./target/release/examples/compare --all --rust-from target/fin2_sample --out target/fin2_cmp
./target/release/examples/compare --all --app news-app --html dist-news \
    --rust-from target/fin2_news --out target/fin2_news_cmp
```

### 判据

| 项 | 判据 | 当前值 |
|---|---|---|
| 单元测试 | 全绿 | lib **415** + bin **53** |
| damage-check | 每个用例「增量 == 整帧」逐字节一致 | 全部一致 |
| 画廊 | 与改动前逐像素一致（除有意改动的场景） | 65 张 |
| 画廊例外 | `35_gif_frame4.png` 按**墙上时钟**取 GIF 帧，连续两次跑就会不一致（实测差异约 6.8%）。看到只有它变、且包围盒落在动图那块，按噪声处理；其余任何一张变了都要当真 | — |
| tabBar 点击 | 12 行全部 OK | 12/12 |
| sample-app 双端差异 | 不高于基线 | **4.55%**（15 页） |
| news-app 双端差异 | 不高于基线 | **6.33%**（6 页） |

### 两个必须知道的坑

**1. 跑任何快照前先 `rm -rf target/mini-storage`。**
无头点击/输入会把数据落到 `target/mini-storage/<app>.json`，下次启动读回来，页面内容就和基线不同了。
曾让 sample 的购物车页从 1.51% 假崩到 10.05%。`tools/snapshot-all.sh` 与 `tools/tab-click-check.sh` 内部每页都会清一次。

**2. `sample-app` 的基线快照必须用 `--settle 0`。**
`pages/index/index` 有一个延时弹出的「新人专享礼包」浮层，`--settle ≥ 0.5` 就会弹出来，
与基线产生 93.9% 的**假**差异。要测这个浮层请单独跑一次 `--settle 1` 并肉眼看。

### 逐像素比对工具

```bash
python3 tools/pixdiff.py a.png b.png
# 输出：差异像素 1510/1076250 (0.140%)  包围盒 x[24,148] y[1333,1382]  最大通道差 153
```
包围盒是判断「真回归 or 动画相位噪声」的关键：差异集中在某个组件的矩形里通常是真改动，
散落全页多半是时钟/动画相位。

### 手工验证用的无头命令

```bash
./target/release/mini-app-window <app> [--route R] [--settle 秒] [--time 秒] [动作...] --snapshot 目录
```

动作按**书写顺序**执行，可重复：

| 动作 | 含义 |
|---|---|
| `--touch x,y[,按住ms]` | 完整触摸序列 touchstart→(长按)→touchend/tap。**测点击一律用这个** |
| `--click x,y` | 直接调 handle_click，**绕过指针层**，只用于隔离定位 |
| `--press x,y` | 按下保持（验证 `:active` / `hover-class`） |
| `--swipe x1,y1,x2,y2[,步数]` | 滑动手势 |
| `--swipe-hold 同上` | 停在终点不抬手（截手势进行中的一帧：橡皮筋、侧滑返回位移） |
| `--drag px×帧数` | 拖动并逐帧计时（滑动手感的可回归测量） |
| `--wheel x,y,dx,dy[,步数]` | 触控板双指滑动 |
| `--wheel-lines 同上` | 普通滚轮（行滚动） |
| `--type 文本` / `--key 按键` | 输入（先 `--click` 到输入框） |
| `--wait 秒` | 空转等待，期间照常出帧 |
| `--frames N` | 按刷新率跑 N 帧（局部重绘/动画类问题只有连续出帧才暴露） |
| `--eval JS` | 可重复，在 `--settle` 之后依次执行 |

> **`--click` 与 `--touch` 的区别曾经藏过一个真机 bug**：按下 tabBar 时提前 return，
> 触摸状态机没启动 → 抬手没有 tap → `handle_click` 永远不被调用。
> `--click` 全绿，真机上 tabBar 完全点不动。所以点击类回归**只认 `--touch`**。

## 四、能力矩阵：事件、WXML/WXSS、wx.\*

### 真正会派发给逻辑层的事件

| 事件 | 触发 | detail |
|---|---|---|
| `touchstart` / `touchmove` / `touchend` / `touchcancel` | 触摸状态机 | `touches` / `changedTouches` / `target` / `currentTarget` / `timeStamp` |
| `longpress` + `longtap` | 长按（两个名字都发，与微信一致） | 同上 |
| `tap` | 抬手且未构成滑动 | `{x, y}` |
| `change` | checkbox / switch 切换、radio 选中、slider 拖动结束、picker 选完 | `{value}`（在 `checkbox-group` 内时是选中值数组，按文档顺序） |
| `focus` / `input` / `blur` / `confirm` | 输入框 | `{value}`（**字符串不强转**） |
| `load` / `error` | `<image>` 有结论时，每个 `(组件, src)` 只发一次 | `{width, height}` / `{errMsg}` |
| 页面 `onPageScroll` | 滚动位置每帧变化 | `{scrollTop}` |
| 页面 `onReachBottom` | 滚到底部 | — |
| 页面 `onPullDownRefresh` | 下拉到位并松手（**不是**滚到顶就触发） | — |

绑定前缀六种全支持：`bind` / `catch` / `capture-bind` / `capture-catch` / `mut-bind` / `bind:`。
派发顺序：捕获外→内，冒泡内→外；`catch` 就地截断；`mut-bind` 只触发最内层。
组件内的绑定按 `owner`（`COMPONENT_OWNER_ATTR`）派发给组件实例，不会误派发到页面。

### WXML

支持：`wx:for`、`wx:if` / `wx:elif` / `wx:else`、`wx:for-item` / `wx:for-index`、对象遍历、`block` 透传、
表达式（成员访问、下标、函数调用、三元）、`class` / `style` 绑定数组与对象、自定义组件（`usingComponents`）。

### WXSS

支持：复合选择器（tag / id / class / 属性 / 伪类）、后代与子代 `>` 组合器、选择器分组、特异性层叠、
`:first-child` / `:last-child` / `:only-child` / `:nth-child(An+B)` / `:nth-last-child(An+B)` / `:active`、
`@import`、`@keyframes`（含 `-webkit-` / `-moz-` 前缀）、CSS 变量 `var(--x, 兜底)`、
rpx、渐变、box-shadow、transform、transition/animation。

`:hover` / `:focus` / `:focus-within` / `:visited` / `:target` **明确永不匹配**（手机上没有 hover；
focus 由宿主输入态处理）。这是有意为之，有测试守着。

### wx.\* API

| 分组 | 已实现 |
|---|---|
| 网络 | `request`（含 `abort`、GET query 编码、4xx 走 success）、`downloadFile` |
| 存储 | `setStorageSync` / `getStorageSync` / `removeStorageSync` / `clearStorageSync` / `getStorageInfoSync` 及四个异步版 |
| 界面 | `showToast` / `hideToast` / `showLoading` / `hideLoading` / `showModal` / `startPullDownRefresh` / `stopPullDownRefresh` / `createAnimation` |
| 画布 | `createCanvasContext`（指令队列 → 原生绘制） |
| 设备 | `getSystemInfoSync` / `getWindowInfo` / `getDeviceInfo` / `getAppBaseInfo` / `getSystemInfo` / `getLaunchOptionsSync` / `getEnterOptionsSync` |
| 路由 | `navigateTo` / `navigateBack` / `switchTab` / `redirectTo` / `reLaunch` |
| 监听 | `onError` / `onUnhandledRejection` / `onPageNotFound` / `onThemeChange` / `onAppShow` / `onAppHide` 及对应 `off*` |
| 兼容 | `createPage` / `createComponent` / `createApp`（uni-app / Taro 产物） |

**未实现的 API 一律保持 `undefined`，不给 no-op 函数。**
框架层普遍用 `typeof wx.X === 'function'` 做能力探测（uni-app、Taro 都是），
给个假函数会让框架以为能力存在，进去之后拿不到回调，反而更难查。这条有测试守着。

`console` 必须齐全（`log/warn/error/info/debug/dir/trace/table/group/groupCollapsed/groupEnd/assert/count/time/timeEnd`）：
uni-app 运行时会对 `['log','warn','error','info','debug']` 逐个 `console[t].bind(console)`，少一个整包挂掉。

## 五之二、内存

### 怎么量

```bash
# 分项：按加载阶段量常驻内存（同一进程内逐段对比，噪声最小）
cargo run --release --example mem_report

# 字体后端的内存基线：预展开解析 vs 惰性解析
cargo run --release --example font_mem_probe

# 进程峰值（macOS/Linux）
/usr/bin/time -l ./target/release/mini-app-window sample-app --route pages/index/index \
    --settle 0 --time 2 --snapshot target/_mem

# 运行期一行摘要（可接监控/日志）
mini_render::memory_report()
```

### 分项实测（本机 macOS，375×667 @2x）

| 阶段 | 增量 |
|---|---|
| 系统主字体常规字面（Hiragino Sans GB.ttc，23MB 文件 / 29352 字形） | **+304 MB** |
| 同一字体集合里的粗体字面（首次画粗体时才解析） | **+279 MB** |
| 一个自定义字族（Songti.ttc，63.8MB 文件） | **+154 MB** |
| 1200 个不同汉字的字形位图缓存 | +8.7 MB |
| 一块 750×4000 的页面画布 | ~12 MB |

**结论：内存的 98% 花在字体上。** 原因是 fontdue 在 `Font::from_bytes` 时就把字体里
**所有**字形的几何全部展开好（`font_mem_probe` 实测：29352 字形 → 305MB；
把 `FontSettings.scale` 从 40 降到 12 只降到 245MB，降到 200 反而涨到 438MB）。
对照组：`ttf-parser` 这类**惰性**解析器 `Face::parse` 之后几乎不额外占内存，
总量就是文件本身的 23MB。

### 已经做的封顶与回收

| 项 | 上限 | 覆盖 |
|---|---|---|
| 解码后的图片（RGBA 原图尺寸，一张 1200×1200 就 5.5MB） | 64MB，LRU 逐出（`MINI_IMAGE_CACHE_MB`） | `image_cache.rs` 7 个单测 |
| 动图帧（帧数 × 单帧 RGBA） | 上一项的一半 | 同上 |
| 字形位图缓存 | 24MB，到顶整表清空（`MINI_GLYPH_CACHE_MB`） | `memory_tests.rs` |
| 自定义 `font-family` 的字体文件 | 2 个，LRU 逐出（`MINI_FONT_CACHE_MAX`） | `memory_tests.rs` |
| 系统主字体 | 进程级单例，不重复加载 | `system_font_is_a_process_wide_singleton` |
| 粗体字面 | 懒加载：只有真的要画粗体才解析 | 画廊 / 快照回归 0 变化 |

宿主接口：

```rust
mini_render::trim_memory();     // iOS didReceiveMemoryWarning / Android onTrimMemory / 鸿蒙 onMemoryLevel
mini_render::memory_report();   // 一行摘要
```

`trim_memory()` 放掉「可重建」的东西（解码图、动图帧、自定义字体），
**不动系统主字体** —— 放掉它下一帧就要重新解析 300MB，等于在内存最紧张的时候制造尖峰。
正在使用中的资源不会被打断（调用方手上的 `Arc` 仍然有效，当前帧照常画完）。

> 这几项都是**防止无上限增长**，不是把当前峰值压下来：上面几个被测页面的图片数据
> 本来就没到 64MB，所以峰值不变（sample index 654→655MB，news home 653→653MB）。
> 真正的峰值大头是字体。

### 下一步（未做，需要决策）

把字体后端从 fontdue 换成惰性解析 + 独立光栅化（`ab_glyph` / `swash` / `cosmic-text`）。
按实测推算：每个字面 305MB → 约 23MB，一个「主字体 + 粗体 + 一个自定义字族」的页面
从 ~740MB 降到 ~70MB。

**代价**：换光栅化器会让**每个字形的抗锯齿覆盖率**发生变化，画廊 65 张、
两个 app 的 21 页快照、以及双端对比的百分比都要重新定基线；
字宽（`advance_width`）两边都来自 `hmtx`，理论上一致，但要逐页核对断行有没有位移。
这件事应该单独开一轮做，并且以「双端对比百分比不变差」为验收标准。
