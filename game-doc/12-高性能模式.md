# 12 小游戏高性能模式（iOS：游戏 JS 跑在 WKWebView 里）

对标微信 iOS 的「高性能模式」（[官方文档](https://developers.weixin.qq.com/minigame/dev/guide/game-engine/unity-webgl-transform/Design/iOSOptimization.html)）。
官方的说法：普通模式下 iOS 的 JS / WASM 没有 JIT，计算重的游戏帧率低、长时间运行发烫；高性能模式 CPU 算力明显提升；
`game.json` 写 `"iOSHighPerformance": true` 开启，去掉即回退；业务代码不用改；vconsole 里 `game start` 的 `render` 字段是 `h5`；
内存上限更紧（低端机 1G、中高端 1.5G）；代价是要处理跨域（Cookie、`Content-Encoding`、资源 `isTrusted`）。
官方没说实现方式，从 `render: h5`、内存上限与跨域问题推断是 WKWebView（WebContent 进程里的 JavaScriptCore 带 JIT）。

## 1. 怎么选模式

| 来源 | 规则 |
|---|---|
| 启动参数 `-gameMode web` / `native` | 最优先（对照测量用） |
| 宿主（`MiniGameViewController(mode:)`、Flutter 选项 `highPerformance`） | 其次 |
| `game.json` 的 `iOSHighPerformance` / `iOSHighPerformance+` | 宿主给 `.auto` 时按它（与微信一致） |
| 包里有 `openDataContext` / `plugins` | 回落普通模式，日志一行（高性能模式还不支持这两样） |

`MiniGameMode.resolve`（sdk/ios/Sources/MiniRender/MiniGameViewController.swift）实现上表；两种视图都实现 `MiniGameHosting`，
宿主处理 hostCall（支付、广告、登录）的代码不用分模式。

## 2. 分工

```
WKWebView（WebContent 进程：JSC + JIT、WebKit 的 WebGL / Canvas 2D / WebAudio）
  /__wg.html → boot.js（启动数据 + 过桥层 wg-env.js）
             → /__wg/seg/*.js：基础库（js/prelude 里与平台无关的 24 段，game/web/boot.rs 的 SEGMENTS）+ DOM 层（js/web_game/*.js）
             → /__wg/m/<键>.js：包里每个 .js 一个 <script>（CommonJS 注册）→ /__wg/entry.js（执行 game.js）
        │  同步：prompt('__wg', {"n","a"})        异步：webkit.messageHandlers.wg.postMessage
        ▼
MiniWebGameView.swift（只传话）── mr_wg_* ──► src/game/web（Rust）
        ▲  evaluateJavaScript(mr_wg_take_js)       storage / wxfile / 网络 / FileSystemManager / 系统信息 / 胶囊：
        │  宿主事件 mr_wg_take_event（同 QuickJS 模式） 与 QuickJS 模式同一份实现，存档互通
```

- **与 QuickJS 模式共用的**：基础库（wx.* 的参数校验、errMsg、回调形状、Promise 化）、系统信息与胶囊的算法（engine_options、chrome.rs）、
  storage 文件（`<数据目录>/game/<appId>/storage.json`）、wxfile、网络（net.rs 的线程池，没有跨域问题）、FileSystemManager（wxfs）、
  hostCall 的文件翻译（app_host.rs）、宿主侧的键盘 / 视频 / 传感器 / 胶囊（Swift）。
- **换成 DOM 的**：画布（第一个 `wx.createCanvas()` 上屏、铺满）、图片、字体（字族名仍由 Rust 按 name 表取）、rAF（同批同时间戳、
  `setPreferredFramesPerSecond` 跳帧）、触摸（identifier 从 0 起分配）、InnerAudioContext（外壳仍是 audio.js，原生入口换成 WebAudio）、
  WebAudio、WebSocket（外壳仍是 socket.js）、Worker、WXWebAssembly、系统覆盖层（Toast / Loading / Modal / ActionSheet 画成 DOM）。
- **模块包装**：`function(module, exports, require) { return (function(GameGlobal, window, self, globalThis) {<源码>…}).call(this, __wgG…) }`。
  `__wgG` 是全局的代理：weapp-adapter 往 `window` 上挂 `location`（真赋值会跳页）、`document` / `navigator`（只读）时落进影子表，
  其余原样读写真全局。代理的目标是空对象（目标是 window 时 Proxy 不变式让 `document` 写不进影子表）。
- **浏览器原生构造器先留一份**（`__wgNative`）：适配层常把 `window.Image` / `XMLHttpRequest` / `WebSocket` 换成自己基于 wx.* 的实现，
  过桥层再用全局名字就绕回去无限递归（萌宠跑酷在 Chrome 里就这么栈溢出过）。

## 3. 微信文档里的坑，这里怎么处理

| 文档 QA | 处理 |
|---|---|
| 跨域：资源 `isTrusted`、拿不到 `Content-Encoding` | 远程图片 / 音频 / 字体经 `/__wg/proxy` 由原生取回（同源）；wx.request / downloadFile 走原生网络，不受跨域限制 |
| 服务端 Cookie 读不到 | wx.request 走原生，Cookie 由原生网络层处理 |
| 内存上限 | WebContent 进程被系统杀掉时（`webViewWebContentProcessDidTerminate`）发 `restart` 宿主事件，宿主重开这一局 |
| 启动发烫（JIT 编译） | 与微信相同的性质；包内大脚本按 `<script>` 逐个加载，WebKit 自己做分层编译 |
| 判别是否开启 | 日志 `运行模式：高性能（WKWebView）`；页面里 `__wgMode === 'h5'` |

## 4. 不支持 / 取舍

- 开放数据域、引擎插件：回落普通模式。
- `performance.now()` 精度是 WebKit 的（1ms 量级）；帧统计的 pump 是 rAF 回调的 JS 耗时，不含 WebKit 的提交与合成。
- 页面跳转一律拦下（只许待在 `wxgame://app`）。
- 审核：App Store 审核指南 4.7 允许 App 提供 HTML5 / JavaScript 写的小程序与小游戏（必须跑在 WebKit 里，开发者对内容负责，
  并遵守 4.7.1~4.7.5：隐私、给出内容索引、年龄分级，以及**未经苹果许可不向这些内容暴露原生平台 API**）。高性能模式与普通模式在
  「下发 JS」这件事上适用同一条；WKWebView 是公开 API。

## 5. 测试

- Rust 单测：`cargo test --release --lib game::web`（资源路径不跳出包根、模块包装行号、storage 落盘与跨重启、转屏派发、hostCall、文件系统）。
- e2e（headless Chrome 扮 WKWebView，devserver 扮宿主）：`cargo test --release --test game_e2e web`，tests/game_cases/web.rs / web2.rs：
  console / onError / 行号、日志限流、适配层全局代理、系统信息、storage 跨重启、rAF 语义与跳帧、触摸、图片来源与 onerror、
  覆盖层（Toast / Modal / ActionSheet、遮罩拦触摸）、前后台、转屏、hostCall、文件系统与 toTempFilePath、网络、WebSocket、
  Worker（真线程、结构化克隆、onError）、WASM、分包、音频、three.js / PixiJS / Phaser（像素与点击）、10 个示例游戏冷启动。
  找不到 Chrome 时跳过（`MINI_CHROME=<路径>`）；`MINI_CHROME_FLAGS` 追加启动参数。
- 手工：`cargo run --release --example web_game_check -- <包> [秒] [--query …] [--shot a.png] [--open]`（`--open` 起服务给 Chrome 开发者工具调）。
- 真机：`IOS_ARGS="-gameMode web" bash tools/ios-game-sweep.sh 40 <游戏…>`，与不带参数的普通模式同一张表比。

## 6. 真机数字（iPhone 16 Pro Max，2026-10-31，每个游戏 40 秒自动玩，`tools/ios-game-sweep.sh`）

| 游戏 | 普通模式 fps / 掉帧 / JS（pump）中位 | 高性能模式 fps / 掉帧 / JS 中位 |
|---|---|---|
| 3D 跑酷 | 60 / 0 / 10.7ms | 60 / 3 / 2.0ms |
| 保龄球 | 60 / 1 / 16.3ms | 60 / 2 / 1.0ms |
| 萌宠小岛 | 59 / 23 / 8~16ms | 前 24 秒 58~60，之后稳在 38 / 571 / 2.0ms |
| farm001（Cocos） | 60 / 0 / 16.6ms | 42 / 132 / 3.0ms |

结论：JS 的耗时降到 1/5~1/15（JIT 起作用，CPU 更闲、更不烫 —— 与微信说的收益同一类）；
但重画面的两个游戏在高性能模式下掉到 40fps 左右，而 JS 只用 2~3ms：瓶颈在 WebKit 的渲染管线（WebGL 在 GPU 进程里执行、
再经合成器上屏；同一时段 backboardd 的合成线程占 36%、GPU 进程 GL 队列 19%），普通模式是 ANGLE 直接画进 CAMetalLayer。
这正是微信又做了「高性能+」的原因（官方：保留游戏独立进程、把渲染挪回微信进程）。所以现在的默认与微信一致：
只有 game.json 写了 `iOSHighPerformance` 的游戏走高性能模式，其余照旧；下一步是「高性能+」：JS 留在 WKWebView、
WebGL 命令按帧打包交回 App 进程，用现有的 ANGLE 直接上屏（game-webgl.js 已经是按 op 编号过桥的形状）。
