# 05 测试计划

## 0. 原则

- **每个判据可判定**：说得出期望值、说得出怎么验证（steering 10）。「能跑」「看起来对」不算。
- **四类参照**：① 微信真机取证（API 行为、事件形状）；② CPU 后端帧基线（逐字节）；③ Chrome 参考实现（像素，有阈值）；④ 小程序既有基线（零回归）。
- **先定向速测，全量放后台**（steering 30）：迭代时只跑相关的 `cargo test --release --lib game_` / `--test game_e2e <过滤词>` 与单个夹具；每期收尾 `regress-async.sh` 全量一次。
- **防空转**：每一类自动化检查都带守卫，证明它真的测到了（例如「GPU 运行日志必须出现渲染后端：GPU」「触摸用例必须收到 ≥1 次回调」「音频用例欠载计数器必须被读到」）。
- **时间相关的场景不比跨运行像素**（steering 30 ②）：凡是墙上时钟驱动的，要么固定帧时钟，要么改用日志断言。

### 2.2 取证探针 `g-probe`

目的：把「微信里到底是什么样」变成一份机器可比的参考答案。探针跑完把结果 `console.log` 一行 JSON（`PROBE_RESULT:{…}`），也写进 `wxfile://usr/probe.json`。

探针内容（每项一个键）：
1. 全局：`typeof` 下列名字——`window, document, self, globalThis, GameGlobal, performance, TextEncoder, TextDecoder, atob, btoa, WebAssembly, WXWebAssembly, SharedArrayBuffer, requestAnimationFrame, setImmediate, queueMicrotask, structuredClone, fetch, XMLHttpRequest, Image, Audio`。
2. `wx` 上全部键的列表（排序）与每个 `typeof`；`wx.canIUse` 对 03 列出的每个 API 的结果。
3. `wx.getSystemInfoSync()` 全量（隐私字段替换成类型名）。
4. 画布：主画布默认 `width/height`；离屏默认尺寸；`getContext('2d')` 两次是否同一对象；拿过 2d 后 `getContext('webgl')`；`width=5000` 后读回值；`fillStyle` 设 `'red'`/`'#F00'`/`'rgba(255,0,0,.5)'`/非法值后读回；`font` 读回；清屏后 `getImageData` 一个像素的值（透明还是黑）；`measureText('Hello')` 的全部字段名。
5. rAF：连续 10 帧回调参数、相对 `wx.getPerformance().now()` 的差；`setPreferredFramesPerSecond(0/61/30)` 是否抛错、之后的间隔。
6. 定时器：`setTimeout(fn, 0)` 嵌套 10 层的实际间隔；`setInterval(fn, 0)` 一秒内的次数。
7. 触摸：提示用户双指按下、交错抬起，记录全部事件的完整对象（`identifier` 取值规律、`touches/changedTouches`、坐标字段是否相等、`force`）。
8. Image：加载成功 / 失败时 `onload/onerror` 的参数；`width/height` 在 `onload` 前后的值；`src` 设相同值是否再次 `onload`。
9. 音频：`InnerAudioContext` 默认属性值；连续创建 40 个同时播放的表现（报错还是抢占）；`onHide` 后是否自动暂停、`onShow` 后是否恢复。
10. 生命周期：冷启动 `getLaunchOptionsSync()`；切后台再回来的 `onShow` 参数。
11. 原生按钮：按下按钮区域时游戏的 `onTouchStart` 是否收到。
12. 错误文案：参数类型错误、storage 超限、文件超限的 `errMsg`。
13. Worker 内可用的 `wx` 键列表。

比对：`tools/game-probe-diff.py <取证.json> <引擎.json>` 逐键比较；允许差异的键放 `game-doc/取证/allowlist.json`，每条写理由（例如 `brand/model` 天然不同）。**白名单之外任何一处差异 = 失败**。

### 2.3 确定性

| 来源 | 固定方法 |
|---|---|
| 帧时刻 / rAF 参数 / `performance.now` | 无头 `--hz H --frames N`：帧 n 的时刻 = `n × 1000/H`（02 §4.3） |
| `Date` | `MINI_FAKE_NOW=2024-03-15`（与现有回归一致） |
| `Math.random` | `MINI_RANDOM_SEED=<n>`（新开关，替换为确定性 PRNG） |
| 定时器 | 跟帧时钟 |
| 存储 | 每次运行前清 `target/mini-storage` 与 `target/sdk-parity/mini-storage`（steering 30 的坑），游戏实例的 `wxfile` 数据目录用 `target/game-data/<夹具>` 并在脚本里清 |
| 网络 | `tests/sample_harness/demo_server.rs` 起本地服务，固定响应；不依赖外网 |
| 图片解码完成时刻 | 无头模式下解码线程池同步完成（`--sync-decode`，仅测试），保证第 k 帧 `onload` 必定已触发 |
| 音频 | 无头不开设备；离线渲染路径（`MINI_AUDIO_OFFLINE=1`）按帧数推进 |
| 后端 | 逐字节基线一律 `MINI_BACKEND=cpu`（与现有脚本一致） |

### 2.4 Chrome 参考实现

`tools/game-compare.py`：headless Chrome 打开 `tools/game-ref/index.html`，它用一层 **wx 垫片**（`wx.createCanvas → HTMLCanvasElement`、`wx.createImage → Image`、rAF 由脚本逐帧驱动、`performance.now` 同 §2.3、`MINI_RANDOM_SEED` 同算法）跑同一份 `game.js`，截第 N 帧画布像素；引擎侧用 `--frames N --snapshot`。
- 窗宽问题沿用 steering 30 的做法：Chrome headless 有最小窗口宽度，用 iframe 外壳固定 375/393 宽。
- 垫片只覆盖 2D 夹具用到的 API；它是像素参照，不是 API 行为参照（API 行为以 §2.2 取证为准）。

## 4. 像素判据

### 4.1 帧基线（CPU，逐字节）

`tools/game-check.sh [夹具…]`：对每个夹具按 `game-doc` 约定的帧号（每个夹具在 README 里写死，如 `g-square: 1,30,60,120`）出 PNG，与 `target/baseline_game_<夹具>/` md5 比较；不一致时调 `pixdiff.py` 给差异占比与包围盒。
退出码与 `regress.sh` 约定一致：0 通过、1 失败、3 需看图。基线由 G2 起在每期收尾前生成，生成那一刻的 HEAD 写进基线目录的 `meta.txt`。

### 4.2 GPU 与 CPU：阈值 0

游戏层的缩放在两端用同一个整数定点算法（02 §5.4），所以延续现有判据：**所有帧 0 个差异像素**。新增用例接进 `tools/gpu-parity.sh` 的一个独立段落，复用它的退出码约定（3 = 没有可用 GPU，不算通过）。

### 4.3 小程序零回归

每期收尾的全量回归里，小程序的 gallery、快照、damage-check、sdk-parity、interaction-check、tab-click-check、H5 对比（sample **4.57%**、news **6.46%**）都不许变（除非那一期有意改了小程序行为，并在提交说明里给出逐页数字）。

### 4.4 Chrome 参考的阈值怎么定

阈值不能拍脑袋（steering 10）。方法（与 GPU 设计 P3 A3.5 同一口径）：
1. 固定 Chrome 版本（记录版本号）。
2. 每个夹具的每个比较帧跑 3 次，确认两边各自自稳定（3 次 md5 相同）。
3. 初次实测差异占比 `d`，阈值 = `max(d) × 1.5`，向上取整到 0.01%；文字夹具单独一档（抗锯齿差异大）。
4. 包围盒必须落在预期区域内（例如 `g-ctx2d` 每格的格子矩形）。
5. 阈值写进 `doc/引擎测试说明.md`，之后只许降不许升；升必须给出原因并经用户同意。

### 4.5 WebGL CTS 子集（G8 定稿）

候选：`conformance/{attribs, buffers, canvas, context, extensions(按可用), glsl/misc, glsl/functions, limits, misc, programs, rendering, renderbuffers, state, textures(非视频), uniforms}`。不跑依赖 DOM / video / 跨域的用例，逐条列在 `design-webgl.md`。

## 5. 性能与流畅度

### 5.1 定义

- **rAF 间隔**：相邻两次 rAF 回调参数之差。
- **屏上重复**：SurfaceFlinger `--latency` 中相邻两次上屏隔了超过一个**目标间隔**（60fps 时 16.7ms）的次数 / 总帧数（沿用 `android-jank.sh` 的算法，但「周期」用目标间隔而不是显示器周期，因为 60fps 在 120Hz 上本来就隔一个 vsync）。
- **引擎慢帧**：`pump_ex` 耗时 > 8ms 的帧（与现有 🩹/⏱ 同一道线）。60fps 预算 16.7ms，8ms 留出 JS 回调与合成余量。
- **JS 帧时间**：本帧所有 rAF 回调总耗时（`MINI_RAF_LOG`）。

不看平均帧率（steering 10）。

### 5.2 门槛（暂定，G2 首次实测后由用户确认定死）

| 场景（夹具） | 设备 | 后端 | rAF 间隔峰值 | 屏上重复 | 引擎 >8ms 帧 |
|---|---|---|---|---|---|
| `g-square` 空载 | 一加 PLY110 | CPU / GPU | ≤ 18.0ms | ≤ 0.5% | 0 |
| `g-bench-sprites?n=500` 逻辑尺寸 | 一加 PLY110 | CPU / GPU | ≤ 20.0ms | ≤ 1.0% | ≤ 1% |
| `g-bench-sprites?n=500` ×dpr | 一加 PLY110 | CPU / GPU | 记录（D-6 依据） | 记录 | 记录 |
| `g-bench-mixed` 逻辑尺寸 | 一加 PLY110 | CPU / GPU | ≤ 20.0ms | ≤ 1.0% | ≤ 1% |
| `g-square` | iPhone（ProMotion） | GPU | ≤ 17.5ms | ≤ 0.5% | 0 |
| `g-bench-sprites?n=500` | 低端 Android（≤4GB，CPU 后端） | CPU | 记录 | 记录 | 记录 |
| `g-touch-draw` 拖动 10s | 一加 PLY110 | auto | ≤ 18.0ms | ≤ 1.0% | 0 |
| 小程序 `query-slow` / `query-fastslow` | 一加 PLY110 | 现状 | — | 不比清单回退 | — |

每个数字同时给 CPU 与 GPU 两列，GPU 还要说明快在哪（steering 10）。

### 5.3 `examples/game_bench`

仿 `examples/backend_bench`：夹具现场生成、`--backends cpu,gpu --runs 5`、取 5 次中位数、守卫（每次运行必须产生 ≥ 请求帧数 90% 的 rAF；GPU 运行日志必须有后端标签）。场景：`sprites(n=100/500/1000/2000)`、`paths`、`text`、`image-scale`、`clear-only`、`getImageData-1px`、`bridge-1MB`、`gc-churn`。输出 JSON + Markdown 表进 `target/_game_bench/`。

### 5.4 音频延迟测法

真机：夹具在 `touchstart` 回调里 `play()` 一个 1ms 的满幅方波，同时在画布上闪白一帧；用高速摄像（240fps）+ 麦克风录像，对齐画面闪白与声音波形起点，差值即「触摸→出声」端到端延迟（含显示延迟）；另用引擎内时间戳（`play()` 调用时刻 vs 音频回调首次写入该 Voice 样本的时刻）给出引擎内部延迟。两者都记录，门槛用引擎内部延迟（可自动化）。

### 5.5 启动

`g-hello` 冷启动：宿主 `create` 调用 → `game.js` 第一行执行 ≤ 300ms；→ 第一帧上屏 ≤ 600ms（一加 PLY110，release 包）。日志打点 `⏱ 游戏启动`。

### 5.6 真机测量流程

- Android：`tools/android-jank.sh` 新增场景 `game-idle`、`game-square`、`game-sprites`、`game-touch`（`MINI_APP=native` 与 Flutter 都支持；用 `GAME=<夹具>` 选包；坐标按 1080 宽换算沿用脚本现有逻辑）；判据见 §5.1，周期按目标间隔。量之前看前台窗口与 `lastUpdateTime`，被打断的结果重跑（steering 30）。
- iOS：`tools/ios-debug.sh` 加 `--game <夹具>`；帧间隔用引擎 `MINI_RAF_LOG` + `CADisplayLink` 时间戳；屏上重复用 Instruments「Animation Hitches」手工记录（暂无自动化，**写明未自动化**）。
- 每次真机结论都写清设备、系统版本、刷新率、后端、APK 构建时刻、引擎库 md5（APK 里的库必须等于 jniLibs 那份）。

| Unity WebGL 小游戏 | 依赖 `WXWebAssembly`（G10）+ WebGL2 | 同上 + GT-WASM6；iOS 解释器路径的性能单独记录 |

导出物由用户提供或由我们用各引擎官方工具链生成（需要本机装对应编辑器，**未核实**是否可得）；放 `sample-game/compat/`，体积大的不入库（`.gitignore`，脚本按需下载到 `target/`）。

## 10. 执行节奏

| 时机 | 跑什么 |
|---|---|
| 改一个函数 | 对应 L1 过滤词，几秒 |
| 改一个功能点 | L1 + `--test game_e2e <过滤词>` + 一个夹具的 `game-check.sh <夹具>` |
| 改合成 / GPU | + `gpu-parity.sh` 游戏段 |
| 改帧调度 / 宿主 | + 真机 `android-jank.sh game-* `（一个场景几十秒）+ 小程序 `query-slow` |
| 每期收尾 | `regress-async.sh G<n>-收尾`（全量，后台）+ 该期全部真机项 + `game-probe-diff` |
| 发布前 | 全部 + soak + 兼容 + 真机矩阵 |

## 11. 清理与产物

- 所有游戏测试产物写 `target/_game_*` 或 `target/game-data/`；基线写 `target/baseline_game_*`（白名单）。**不写** `doc/`、`sample/`、`sample-game/`、仓库根目录。
- 每轮回归结束 `bash tools/clean-target.sh`；编过移动端库之后 `--targets`。新写的脚本收尾调 `python3 tools/prune-target.py --quiet`（steering 30 存储预算）。
- 临时探针 `examples/tmp_*` 用完删源文件。
- 取证 JSON 入库（`game-doc/取证/`），它是参考答案，不是产物。

## 12. 验收报告格式

每期一份 `game-doc/验收/G<n>.md`：验收项编号 → 结果（通过 / 失败 / 未验证）→ 数字 → 复现命令 → 日志位置。
「未验证」必须写原因（没设备、没权限、工具链不可得），不能省略。数字给出设备、构建、后端、日期。
