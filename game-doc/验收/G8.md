# G8 验收记录（2026-10-28，分支 `feat/mini-game`）

设计与决策见 `game-doc/design-webgl.md`（D-2 = A：ANGLE 的 WebGL 兼容上下文；Android 加载不到 ANGLE 时退到系统 GLES + 引擎自己校验）。

复现：
- 用例：`cargo test --release --test game_e2e -- wg e1_three`（先 `bash tools/fetch-angle.sh`、`bash tools/fetch-engines.sh`）；
- CTS：`bash tools/webgl-cts/fetch.sh && python3 tools/webgl-cts/run.py`（报告 `target/_cts/report.md`）；
- 对照 Chrome：`bash tools/webgl-chrome-compare.sh`；
- 真机：`bash tools/android-game-jank.sh g-webgl 8`（`--es query toast=1` 测覆盖层叠加）。

## 已做

| 项 | 结果 | 证据 |
|---|---|---|
| G8.1 ANGLE 接入 | 通过（macOS） | 运行时加载 libEGL / libGLESv2（comfy-angle 0.1.1，取自 Electron 的 ANGLE，sha256 写死）；不链接任何 GL 库 |
| G8.2 上下文与上屏 | 通过 | WebGL 兼容上下文、pbuffer 当默认帧缓冲；Android 主画布直接 `eglSwapBuffers` 到 SurfaceView（window.rs）；覆盖层黑白双底求 alpha 后 GPU 叠加 |
| G8.3 WebGL1 | 通过 | WG1~WG3、WG5、WG8；CTS 子集 |
| G8.4 texImage 来源 | 通过 | WG2：Uint8Array（FLIP_Y）、2D 画布、ImageData；Image；PBO 偏移（WebGL2）；尺寸自己核（GL 不知道 JS 缓冲多长） |
| G8.5 丢失与兜底 | 通过 | WG4；`MINI_GPU_FAULT=lost@N`；SwiftShader 兜底与无头基线；`MINI_WEBGL=off` → null（WG7） |
| G8.6 WebGL2 | 通过 | WG6：VAO、实例化、uniform 块、3D 纹理、getBufferSubData（GLES3 没有，按 MapBufferRange 读） |
| G8.7 离屏 WebGL / drawImage(webglCanvas) | 通过 | WG8 |
| G8.9 WebGPU `wx.getGPU` | 形状（W 级） | `requestAdapter()` resolve null，引擎回退 WebGL（PC1） |
| G8.10 iOS 纹理路线 | 没做 | 依赖 G2.8 的 iOS 小游戏视图，iOS 还没有 |
| G8.11 `wxBindCanvasTexture` | 通过（拷贝） | WG8；微信是零拷贝共享，这里是调用那一刻拷一份 |
| G8.8 调用开销 | 记录 | 每个 GL 调用一次 `__game_gl` 原生调用；真机 e-pixi / e-phaser 60fps（下表），没做命令缓冲批量提交 |

## 判据

| 编号 | 结果 | 说明 |
|---|---|---|
| A8.1 CTS 子集 | **通过：适用页 169/175（96.6%）**，子项 16871 过 / 19 失败 | KhronosGroup/WebGL 3a65272e 的 buffers、state、programs、uniforms、attribs、renderbuffers、misc、typedarrays、rendering、context 十个目录共 179 页，4 页不适用（下）。macOS ANGLE + SwiftShader 无头 |
| A8.2 与 Chrome 对照 | **通过** | three.js r160 同一场景、同一份 scene.js：差异像素 2 / 250125（0.001%），包围盒 x[178,185] y[462,463]，最大通道差 1（阈值 0.1%） |
| A8.3 CPU 合成也能 WebGL | 通过 | 游戏实例没有 wgpu 合成，WebGL 只看 EGL；无头走 SwiftShader（WG1 断言后端是 swiftshader） |
| A8.4 丢失与恢复 | 通过 | WG4：getError 报一次 CONTEXT_LOST_WEBGL、丢失期间 create* 给无效对象、preventDefault 后恢复、旧对象作废 |
| A8.5 体积 | 通过 | arm64 符号统计：glow 59KB + khronos-egl 12KB + game::webgl 206KB ≈ 0.28MB（< 8MB） |
| A8.6 顿挫 | 通过 | 见真机数字 |

CTS 不适用的 4 页（不计入）：两页要 iframe（小游戏没有）；两页依赖「每块 DOM 画布都会被合成、合成后隐式清屏」——小游戏里只有主画布上屏，离屏 WebGL 画布从不合成，绘图缓冲保留。

CTS 未通过的 6 页：

| 页 | 原因 |
|---|---|
| state/gl-object-get-calls | 几个罕见 pname 的报错码与 Chromium 不同（INVALID_ENUM / INVALID_OPERATION 的取舍） |
| uniforms/gl-uniform-unused-array-elements-get-truncated | 着色器数组是 MAX_FRAGMENT_UNIFORM_VECTORS 的两倍，SwiftShader 下链接失败（驱动相关） |
| renderbuffers/framebuffer-object-attachment | 部分「不完整帧缓冲上画」的组合仍按 GL 画了（WebGL1 额外规则只做了渲染缓冲那几条） |
| rendering/blending | 浮点帧缓冲上的混合没按 EXT_float_blend 拦 |
| context/context-lost | 丢失后第二轮的 CONTEXT_LOST_WEBGL 报告次数 |
| context/premultiplyalpha-test | toDataURL('image/jpeg') 压黑底的那几组 |

## 待取证 / 取舍

- 微信 `getParameter(VERSION / RENDERER)` 的串：现在照 Chromium 报 `WebGL 1.0 (OpenGL ES 2.0 Chromium)` / `WebKit WebGL`；
- 离屏 WebGL 画布的 preserveDrawingBuffer：这里不清（从不合成），微信的行为待取证；
- Android 打包 ANGLE：要 gn + Chromium 依赖链自编，本机放不下；现在走系统驱动 + 引擎校验（越界绘制、texImage / readPixels 尺寸、资源清零），着色器不做 WebGL 的 GLSL 限制检查；
- WebGPU 没有映射到 wgpu。
