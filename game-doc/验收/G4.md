## 性能（一加 PLY110，CPU 后端，`g-bench-sprites?n=500` 逻辑尺寸）
| 改动 | 桌面 pump 中位 | 真机引擎工作中位 / p99 | 引擎 >8ms | 屏上重复 | rAF 峰值 |
|---|---|---|---|---|---|
| 逐像素 put | 0.81ms | 9.2 / 11.6ms | 504 / 707 | 0.2% | 16.59ms |
| 不透明段整段拷贝（与逐像素逐字节相同） | 0.50ms | 8.2 / 10.7ms | 413 / 761 | 0 | 16.59ms |

05 §5.2 的门槛：rAF 峰值 ≤ 20ms **达到**、屏上重复 ≤ 1% **达到**、引擎 >8ms ≤ 1% **没达到**（54%）。
rAF 回调本身 6.2ms/帧（夹具自报），simpleperf：QuickJS 解释执行 ~19%、libc（memcpy / malloc，原生调用的参数数组）~22%、
精灵拷贝 ~14%、上屏拷贝 ~7%。剩下的大头在 JS 引擎与调用开销，要等决策 D-3（换 JS 引擎）或把 drawImage 的调用参数改成定长。

## 踩到的坑
- 设过图案填充之后，每次 drawImage 都走了整画布蒙版（`fx.trivial(false)` 把填充样式算进去了），一次 0.26ms；
  drawImage 只该看合成模式与阴影（`trivial_for_image`）。改完一万次 drawImage 从 2.6s 降到 7ms。
- Image 对象没人引用了，解码结果也不会马上放：要等 GC 跑过、FinalizationRegistry 回调之后。预算测试必须先 GC。

## 与浏览器已知的差别（记下，不假装一致）
- 旋转 / 斜切后的图片边缘没有抗锯齿；大幅缩小不做 mip（双线性只看 4 个邻域）。
- 合成模式 / 阴影下的 drawImage 走图案蒙版，采样是最近邻；阴影按目标矩形的形状，不按图的 alpha。
- `fillText(…, maxWidth)` 超宽时缩字号（浏览器是横向压缩字形）；strokeText 仍是用描边色填充。
- 以画布为源的图案在设 fillStyle 时取像素（规范是 createPattern 时快照）。
