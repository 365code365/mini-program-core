# 11 兼容性审查（第三轮：对照「百分百兼容微信小游戏运行标准」）

## 0. 结论

**按 01~09 的方案做完，达不到百分百兼容。** 我把方案与微信官方 API 总览（382 个 `wx.*`、51 个对象 / 444 个方法，
逐项见 10）和小游戏运行环境逐层对照，找出 **13 处阻断性偏差**（§2）。其中 5 处会让一整类游戏直接跑不起来：

| # | 偏差 | 跑不起来的游戏 |
|---|---|---|
| B-1 | 原方案不提供 `WXWebAssembly` | Unity、Emscripten（C++ / Cocos 原生物理）导出的全部游戏 |
| B-3 | 原方案在 CPU 合成后端上 `getContext('webgl')` 返回 `null` | 被机型分级判成 CPU 的设备上，所有 WebGL 游戏（主流引擎默认 WebGL） |
| B-6 | 原方案不做开放数据域 | 带好友排行榜的游戏：`getOpenDataContext()` 一调用就出错 |
| B-7 | 原方案只对 `game.json.plugins` 打一行「不支持」 | 用了 Cocos「引擎插件」的游戏：引擎代码不在包里，启动即白屏 |
| B-2 | JS 引擎是 QuickJS，微信是 JSC（iOS）/ V8（Android） | 依赖 `Intl`、`Error.captureStackTrace`、栈格式、JIT 级性能的游戏 |

本章逐条给出：官方标准是什么、原方案哪里不对、怎么改、改到哪一期、用什么用例证明。改动已同步进 02~06 与 10。

**「百分百」的边界**也要先说清楚，避免给出做不到的承诺（§1.2）：依赖微信后台的能力（关系链数据、米大师支付、
帧同步服务、广告投放）引擎只能做到**接口形状与错误语义百分百一致**；数据与结算必须由宿主后端提供，否则返回与微信
「无权限」同形的失败。这不是方案缺陷，是任何非微信宿主都绕不开的事实。

## 1. 什么叫「百分百兼容」

### 1.1 五层标准

| 层 | 内容 | 判据 | 是否能 100% |
|---|---|---|---|
| C1 包与加载 | `game.json` 全字段、分包 / 独立分包、引擎插件、`.br` 压缩文件、资源格式 | 合法的微信小游戏包都能被识别、加载、执行 | 能 |
| C2 JS 运行环境 | 语言特性、全局对象、引擎特有行为（栈、`Intl`、错误类型） | 微信真机上能跑的 JS 在引擎上结果相同 | 选 V8/JSC 时能（D-3） |
| C3 API 表面 | 382 个 `wx.*`、444 个对象方法、全局函数 | **每一个都存在**，`typeof`、同步 / 异步 / Promise 形态一致 | 能（自动化门禁 GT-API） |
| C4 API 行为 | 参数校验、回调时机、返回值、事件序列、errMsg | 与真机取证逐字段一致 | 等级 E 的能；H 在宿主接入后能；W 只到形状 |
| C5 渲染、输入、性能 | 2D / WebGL / WebGPU 像素、帧节拍、输入延迟、音频 | 05 的像素与流畅度判据 | 能（性能另有 B-1、B-2 的风险） |

### 1.2 等级（与 10 的「等级」列一致）

- **E**：引擎自己能做，必须与微信行为一致。
- **H**：系统或宿主能力（蓝牙、定位、相机、登录…）。引擎给完整形状；宿主接入后行为一致；没接入时与微信「不支持 / 无权限」同形失败。
- **W**：依赖微信后台。引擎给完整形状和错误语义；宿主后端可选提供数据。
- 统计（10）：E 147、E+H 3、H 192、W 40。

## 2. 阻断性偏差与修正

### B-1 `WXWebAssembly`

- **官方标准**：小游戏提供 `WXWebAssembly`（不是标准的 `WebAssembly`），`instantiate(path, imports)` 的第一个参数只接受代码包内的 `.wasm` / `.wasm.br` 路径（社区与官方文档一致）；Worker 里也可用；Unity 小游戏方案、Emscripten 适配（官方「通用适配」里的 WXSocketLib 等）都依赖它。
- **原方案**：03 §9、06 §6 写「不提供，Unity 不在支持范围」。**与百分百兼容冲突。**
- **修正（新增 G10，决策 D-11）**：
  1. `WXWebAssembly.{instantiate, validate, Module, Instance, Memory, Table, Global, CompileError, LinkError, RuntimeError}`，按官方签名，只认包内路径，`.br` 自动解压（复用 G4 的 brotli）。
  2. 执行引擎：iOS 不允许 App 自己 JIT，只能用解释器 → **wasmi**（纯 Rust、可在 iOS 跑）；Android 与桌面可选 **Wasmtime（Cranelift JIT）**，性能高一个数量级以上。两者同一套导入导出绑定，`MINI_WASM_ENGINE=interp|jit` 可强制。
  3. 与 JS 的边界：导入函数调回 JS、`Memory.buffer` 映射成 `ArrayBuffer`（`memory.grow` 后旧 buffer detached，与规范一致）、`Table` 存函数引用。
  4. 体积：wasmi 约 1MB 量级、Wasmtime 约 5~10MB 量级（**未核实**，G0.3 探针实测；超 8MB 停下来问用户）。
- **性能风险（如实写）**：iOS 上解释执行 Unity 游戏，CPU 密集场景可能比微信慢数倍（微信 iOS 的 wasm 执行方式**未核实**）。百分百兼容指「能正确跑」；「跑得一样快」在 iOS 上不能承诺，以 G10 的实测为准。
- **用例**：GT-WASM1~6（§4）。

### B-2 JS 引擎语义

- **官方标准**：小游戏逻辑在 iOS 上跑在 JavaScriptCore，在 Android 上跑在 V8（多方资料一致，官方 iOS 高性能模式另说）。游戏和引擎在这两个环境里调过，依赖它们的行为。
- **原方案**：QuickJS；D-3 写「G9 按数据定」。
- **QuickJS 与 V8 / JSC 的已知差异**（逐项要用例覆盖）：

| 项 | V8 / JSC | QuickJS（未改造） | 影响 |
|---|---|---|---|
| `Intl`（`toLocaleString`、`Intl.NumberFormat`、`DateTimeFormat`） | 有 | **没有**（`toLocaleString` 退化成 `toString`） | 金币 `1,234,567` 显示成 `1234567`；用 `Intl` 的库直接抛错 |
| `Error.captureStackTrace` / `Error.stackTraceLimit` | V8 有 | 没有 | 一些库（如 Node 风格的错误工具）调用即抛 `TypeError` |
| `error.stack` 格式 | V8：`at fn (file:line:col)`；JSC：`fn@file:line:col` | 自有格式 | 解析栈做上报的 SDK 拿不到行号 |
| JIT 性能 | 有 JIT（iOS 第三方 App 的 JSC 是否有 JIT **未核实**） | 解释器 | 重逻辑游戏慢数倍 |
| `SharedArrayBuffer` / `Atomics` | 视环境 | 编译选项决定 | Worker 共享内存 |
| 正则 `v` / `d` 标志、`Array.prototype.findLast` 等新语法 | 随版本 | 随 QuickJS 版本 | 新语法的打包产物 |
| `Date.parse` 非标准格式 | 宽松（各不相同） | 较严格 | `new Date('2024-03-15 10:00')` 在 iOS JSC 上本来就是 NaN，游戏已规避；V8 上可解析 |

- **修正（D-3 升级为开工前决策）**：
  - **推荐 D-3 方案 B**：抽一层 `JsEngine` 接口，Android 用 **V8**、iOS 用系统 **JavaScriptCore.framework**（与微信同类引擎，行为差异最小），桌面与无头测试保留 QuickJS 并补齐上表的缺项（补 `Intl` 子集：数字分组、日期 `zh-CN` / `en-US`；补 `Error.captureStackTrace` 空实现）。
  - 代价：XL（桥、原生类绑定、GC 句柄、二进制桥都要两份实现）；Android 包体增加 V8（约 7~10MB 量级，**未核实**）。
  - 如果不选 B（保持 QuickJS），必须在验收标准里写明「C2 层不是 100%」，并列出上表每一项的处理。
- **用例**：GT-JS1~5（§4）。

### B-3 WebGL 不能跟着合成后端走

- **官方标准**：小游戏里 `getContext('webgl')` / `'webgl2'` 总是可用（只要设备有 GPU 驱动，所有在售手机都有）。
- **原方案**：02 §10 把「CPU 后端」与「没有 WebGL」绑在一起。但我们的 CPU / GPU 指的是**合成器**（steering 10 的双后端），机型分级把不少中低端 Android 判成 CPU（`compositor::select`：API < 29、内存 < 3.5e9 字节、黑名单）。这些设备在微信里能跑 WebGL 游戏，在我们这里拿到 `null`。
- **修正**：
  1. WebGL 的可用性只取决于「ANGLE 能不能在这台设备上建 WebGL 兼容上下文」，**与合成后端无关**。
  2. 主画布是 WebGL 时，上屏路径是 EGL / Metal 直接 present，合成器不参与；覆盖层在 GL 里叠加（02 §10 已有）。CPU 合成后端只服务 2D 游戏与覆盖层。
  3. ANGLE 建不了上下文的情况（驱动缺失、模拟器、无头 CI）：用 **SwiftShader**（ANGLE 自带的软件 Vulkan 后端）兜底，保证 `getContext` 不返回 `null`。D-2b 从「不做」改成「必须做」。
  4. steering 10 的「CPU 后端是参考实现」仍然成立：它约束的是合成；WebGL 的像素参照改用「ANGLE + SwiftShader」（确定性的软件实现，可做逐字节基线），硬件 GPU 与它按阈值比较。
- **用例**：GT-WG3 改为「合成后端强制 CPU 时 `getContext('webgl')` 仍返回上下文」；新增 GT-WG7、WG8（§4）。

### B-4 `wxBindCanvasTexture`

- **官方标准**：`WebGLRenderingContext.wxBindCanvasTexture`，把一个 Canvas 的内容作为纹理绑定到 WebGL 上下文（官方 API 列表里的微信扩展）。引擎用它把 2D 画布（文字、UI）贴进 3D 场景，避免 `texImage2D(canvas)` 的读回。
- **原方案**：没有。
- **修正（G8.4）**：2D 画布的后备缓冲在原生侧，绑定时直接上传成 GL 纹理（脏区增量上传，复用游戏层的脏区记账）；签名与返回值以取证为准。
- **用例**：GT-WG9。

### B-5 WebGPU `wx.getGPU`

- **官方标准**：`wx.getGPU()` 返回 WebGPU 的 `GPU` 对象（等价于 `navigator.gpu`）。
- **原方案**：没有。
- **修正（新增 G8.9）**：引擎本来就依赖 wgpu（`=30.0.1`），WebGPU 的 JS 绑定可以直接映射到 wgpu（Deno、Firefox 都这么做）。可用性：设备支持 Vulkan / Metal 时返回对象，否则 `getGPU()` 的结果与微信在不支持设备上一致（取证：返回 `undefined` 还是抛错）。
- **用例**：GT-GPU1~3。

### B-6 开放数据域

- **官方标准**：`game.json.openDataContext` 指定目录；`wx.getOpenDataContext()` 返回 `OpenDataContext{canvas, postMessage}`；开放数据域是**独立的 JS 环境**，只能调关系链 API 与有限的渲染 API，主域能把 `sharedCanvas` 画到自己的画布上、但读不到它的像素（`getImageData`、`toDataURL` 被禁止）。
- **原方案**：D-5「不做」。**与百分百兼容冲突**：排行榜是小游戏的标配，`getOpenDataContext` 不存在或形状不对，游戏启动就抛错。
- **修正（G9.7 从「可选」改为「必做」）**：
  1. 第二个 JS 运行时（同一引擎线程，独立 Context，只装开放数据域的 prelude），入口是 `openDataContext/index.js`。
  2. `sharedCanvas`：开放数据域里 `wx.getSharedCanvas()`，主域里 `openDataContext.canvas`；主域 `drawImage(sharedCanvas)` 允许，`getImageData` / `toDataURL` / `toTempFilePath` 在**被画过 sharedCanvas 的画布**上也要按微信规则限制（取证：微信的污染规则，类似浏览器的 tainted canvas）。
  3. 关系链 API（`getFriendCloudStorage` 等 W 级）：宿主点名后由宿主后端提供数据；没点名时返回与微信无授权时同形的 fail。
  4. 两域之间只能经 `postMessage` / `wx.onMessage` 通信，消息结构化克隆。
- **用例**：GT-OD1~6。

### B-7 引擎插件与 `requirePlugin`

- **官方标准**：`game.json.plugins` 声明插件（`provider`、`version`、`path`、`contexts`）；最常见的是 Cocos 的「引擎插件」：引擎代码不打进游戏包，由微信按版本下载并缓存，游戏用 `requirePlugin('cocos')` 之类拿到。
- **原方案**：02 §1「`plugins` 非空时打一行插件不支持」。**用了引擎插件的游戏会白屏。**
- **修正（新增 G6.7，决策 D-12）**：
  1. 插件解析：创建选项 `pluginDir`，目录结构 `<pluginDir>/<provider>/<version>/`；宿主（或商店服务）负责下载插件包。
  2. `requirePlugin(name)` 与 `game.json.plugins[name].path` 的本地兜底：插件包缺失时，如果游戏包里带了 `path` 指向的本地副本就用它（Cocos 的「引擎分离」允许本地兜底），否则抛与微信一致的错误。
  3. 插件代码在独立的模块作用域里执行，`contexts` 决定它在主域 / 开放数据域是否可用。
- **用例**：GT-PL1~4。

### B-8 PC 端能力

- **官方标准**：`requestPointerLock` / `exitPointerLock` / `isPointerLocked`、`setCursor`、`setWindowSize`、`getGamepads` / `onGamepadConnected`、`desktopDeviceOrientation`、`resizable` 与 `displayMode`。
- **原方案**：只有键鼠与滚轮。
- **修正（G3.7）**：桌面窗体（winit）与 macOS SDK 实现指针锁定（`CursorGrabMode::Locked`）、光标、窗口尺寸；手柄用 `gilrs`（桌面）/ Android `InputDevice`、iOS `GCController`（H 级，SDK 采集）。
- **用例**：GT-T12~T15。

### B-9 小游戏视频 `wx.createVideo`

- **官方标准**：`wx.createVideo({x, y, width, height, src, poster, autoplay, loop, muted, underGameView, objectFit…})` 返回 `Video` 对象，可以放在游戏画面下层（配合 WebGL `alpha:true`）。
- **原方案**：「计划外」。
- **修正（G7.7）**：复用已有的同层视频（Android `VideoHost` MediaPlayer、桌面 openh264）；`underGameView:true` 时视频层在游戏层下面，游戏层按 alpha 合成；方法与事件按 10 的 `Video` 一行补齐。
- **用例**：GT-U4。

### B-10 长尾 API（71 项「本轮补入」）

`createPath2D`、`wx.encode/decode`、旧版全局 socket（`onSocketOpen/Message/Error/Close`）、离线模式
（`onOfflineModeStateChange`、`enableOfflineModeDebug`）、`onKeyboardConfirm/Complete`、`getGameLogManager`、
`getScenePerformanceManager`、`createPageManager`、Handoff、聊天工具、米大师新接口、广告新接口、游戏圈、关系链等，
全部列在 10，等级与期次已定。其中引擎能做的（E）有：`createPath2D`、`encode/decode`、旧版 socket、离线模式状态（恒为在线，
调试开关只记录）、键盘的两个事件、`getGameLogManager`（写宿主日志）、`getScenePerformanceManager`（本地统计）。

### B-11 `console` 缓冲泄漏（源码已核实）

- 事实：`console.js` 的每个方法都会 `__console_buffer.push(…)`（`src/js/prelude/console.js:1、22、27、32、37`），**整个仓库里没有任何代码读取或清空它**。
- 影响：长时间运行的游戏每打一行日志就永久多占一份字符串；每帧打几行，一小时就是几十万条。小程序页面生命周期短，问题不明显；游戏会持续涨内存，最终触发系统杀进程。
- 修正：游戏 profile 的 console 不写 `__console_buffer`（G1.12 一起做）；小程序侧同样有这个问题，改它属于小程序行为变化，**单独提交、征求同意**（D-10 一并处理）。
- 用例：S8「`console.log` 100 万次后 JS 堆增长 ≤ 1MB」。

### B-12 全局配置与运行时元数据

- 部分适配层会读运行时注入的全局（例如 `__wxConfig`：包含 `game.json` 内容、`envVersion`、平台信息）。是否存在、有哪些字段，**未核实**。
- 修正：探针加一项列出全部非标准全局（`Object.getOwnPropertyNames(GameGlobal)` 减去 ECMAScript 标准全局），取证后逐个对齐（G1）。

### B-13 文件与资源格式

| 类 | 需要确认的格式 | 现状 | 处置 |
|---|---|---|---|
| 图片 | png、jpg、gif、webp；svg 是否支持（**未核实**） | `image` crate 开了哪些格式未核实 | G4.1 按取证补齐；svg 若微信支持则接现有的 svg 渲染 |
| 音频 | mp3、aac、m4a、wav；ogg 在 iOS / Android 上是否支持（**未核实**） | symphonia 未开 vorbis | D-4b 按取证 |
| 字体 | ttf、otf；woff / woff2（**未核实**） | fontdue 只认 ttf / otf | 取证后决定是否加 woff2 解码 |
| 压缩 | `.br`（wasm、`readCompressedFile`） | 无 | G4.6 / G10 |
| 视频 | mp4（h264）；hevc 视设备 | openh264 / MediaPlayer | 沿用 |

## 6. 仍然不能承诺的

1. **W 级数据**：没有宿主后端时，关系链、米大师、帧同步、广告只能返回与微信无授权时同形的失败。
2. **iOS 上 wasm 的性能**：解释执行，CPU 密集的 Unity 游戏可能明显慢于微信（微信 iOS 的 wasm 执行方式未核实）。
3. **微信自有界面**：游戏圈、客服会话、视频号等是微信的页面，只能交给宿主实现自己的版本，外观与微信不同。
4. **基础库版本差异**：微信每月更新基础库，行为会变。我们对齐的是取证那一刻的版本（`GAME_SDK_VERSION`）；之后的变化靠 API5 的定期重抓与重新取证跟进。

## 7. 第四轮核对（开工前最后一遍）

逐层再过一遍 §1 的五层，只剩网络身份这一类没写到（游戏服务端常用它做来源校验，不对齐就是「本地能玩、连服务器失败」）：

| # | 官方 / 真机行为 | 方案原状 | 处置 | 期 | 用例 |
|---|---|---|---|---|---|
| N-1 | `wx.request`、`downloadFile`、`Image`、`InnerAudioContext` 发出的请求带 `Referer: https://servicewechat.com/{appid}/{version}/page-frame.html`（官方 `Image.referrerPolicy` 文档写明格式；`version` 开发版为 0），`referrerPolicy:'no-referrer'` 时不带 | 没有 | 引擎按创建选项 `appId` / `appVersion` 拼出，各 API 的 `referrerPolicy` 生效；小游戏里路径是否仍是 `page-frame.html` 以取证为准 | G4 | N7：本地服务回显请求头，Referer 与取证一致；`no-referrer` 时缺省 |
| N-2 | 请求的 `User-Agent` 含微信标识（具体串**未核实**） | 用 ureq 默认 UA | 创建选项 `userAgent`（宿主给），默认值按取证格式；`header` 里显式传 UA 时是否允许覆盖以取证为准 | G4 | N8 |
| N-3 | 合法域名、TLS 版本、证书校验 | 06 §5 已有 `allowedDomains`；rustls 默认 | 补：不允许 IP 直连与非 443 端口是否与微信一致以取证为准（开发版不校验） | G4 | N9 |

除此之外五层均已覆盖，可以开工。开工时尚未拍板的决策按「推荐」执行，并在实现处注明（D-1 用方案 B；D-3 先落 `JsEngine` 抽象与 QuickJS，V8 / JSC 等用户确认后再接）；
需要用户执行的取证（G0.2）不阻塞 G0 其余步骤，取证缺失项按默认实现并标「取证缺失」。
