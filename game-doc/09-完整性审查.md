## 2. 新发现的生产隐患（源码已核实）

### 2.1 FFI 没有 panic 防护

- 事实：`src/ffi_*.rs` 里没有任何 `catch_unwind`（grep 0 处）；`with_app!` 宏只判空指针（`src/ffi_app.rs:122`）。
  Rust 1.81 起，panic 穿过 `extern "C"` 边界会直接 **abort 整个宿主进程**。
- 为什么对小游戏更严重：小游戏跑的是第三方代码，会把各种畸形参数送进原生路径（负尺寸画布、NaN 坐标、超大 TypedArray、损坏的图片 / 音频）；任何一处 `unwrap` / 下标越界都会让宿主 App 闪退。
- 连带问题：引擎大量 `self.runtime.lock().unwrap()`。就算捕获了 panic，Mutex 已经中毒，之后每次调用都会再 panic。
- 处置（新增 04 G1.9）：
  1. 游戏实例的每个 FFI / JNI 入口包 `std::panic::catch_unwind(AssertUnwindSafe(..))`；捕获后把实例标记为 **poisoned**：`last_error` 写 panic 信息与位置，之后所有调用直接返回失败值，宿主收到一次 `error` 事件（`{kind:'panic'}`），由宿主决定重建。
  2. 不尝试在 panic 之后继续运行同一实例（状态可能不一致）。
  3. 原生侧对 JS 传入的数值一律先校验（NaN、无穷、负数、超上限）再用，校验失败转成 JS 异常（`TypeError` / `RangeError`），不 panic。
  4. 小程序实例的 FFI 是否也加防护：属于小程序行为变化（异常从「闪退」变成「实例失效」），**单独提交、单独征求同意**，不混在游戏改动里。
- 用例：08 §5「panic 防护」；注入开关 `MINI_GAME_FAULT=panic@pump|panic@touch|panic@canvas`（只在游戏实例上生效）。

### 2.2 数据目录按「包目录名」区分

- 事实：`wxfile` 根目录是 `<data_dir>/wxfile/<包目录名>`（`src/wxfile.rs:16-21`），storage 是 `<data_dir>/mini-storage/<包目录名>.json`（`src/storage_file.rs:19-26`）。
- 风险：两个不同的游戏只要解包目录同名（例如都叫 `game`、`dist`），就会**共享存档与文件**；游戏换了解包目录名，存档就「丢了」。
- 处置（新增 04 G1.10）：游戏实例的命名空间用创建选项 `appId`（必填；缺省时回落目录名并打警告）；数据目录 `<data_dir>/game/<appId>/{storage.json, wxfile/}`。小程序的现有路径**不动**（改了会让已上线用户的数据丢失，需要迁移方案，计划外）。
- 用例：新增 FS6「两个 appId 不同、目录名相同的游戏数据互不可见；同一 appId 换目录名后数据仍在」。

### 2.3 默认系统信息是「开发者工具」

- 事实：`device.js` 默认 `platform: 'devtools'`、`SDKVersion: '3.0.0'`、`benchmarkLevel: 1`（`src/js/prelude/device.js:22-48`），宿主用 `systemInfo` 选项覆盖。
- 风险：游戏引擎普遍按 `platform` 分支（`'devtools'` 时走调试逻辑、加载本地资源、打开调试面板），并用 `SDKVersion` 比版本决定走哪套 API。宿主忘了覆盖就会走错分支，而且现象很隐蔽。
- 处置（新增 03 §1 要点、04 G1.11）：
  - 游戏实例的 `platform` 由引擎按编译目标给出真实值（`android` / `ios` / `mac` / `windows`），宿主不能覆盖成 `devtools`（只有无头测试可以）。
  - `SDKVersion` 报一个**与已实现 API 集合匹配**的基础库版本号，写成常量 `GAME_SDK_VERSION` 并在注释里列出依据（决策 D-9）；`wx.canIUse` 的结果必须与这个版本号一致（G0.2 取证后定）。
  - `benchmarkLevel` 由 `DeviceInfo` 计算（04 G6.6），不再是常数 1。
- 用例：R9「游戏实例 `platform` 不是 `devtools`；`SDKVersion` 等于常量；`canIUse` 与 03 的阶段状态一致」。

### 2.4 `console` 输出洪水

- 事实：`console.*` 先进 JS 数组 `__print_buffer`，SDK 每帧 `JSON.stringify(__print_buffer.splice(0))` 取走（`src/host/engine_events.rs:151-159`）。
- 风险：游戏常在每帧里打日志（调试遗留），一帧几千行时，这一步会在引擎线程上序列化几百 KB，直接造成掉帧；宿主侧 logcat 也会因为日志量大而整段静默（避坑清单记录过 ColorOS 的这一现象）。
- 处置（新增 02 §3.3）：游戏实例每帧最多取 500 行、单行截断到 4KB，超出部分只计数，下一帧打一行 `…丢弃 N 行日志`；`MINI_GAME_LOG_ALL=1` 关闭限制（调试用）。
- 用例：S6「一帧 `console.log` 10 000 次：该帧 pump 增量 ≤ 3ms（M3 Pro），宿主收到 500 行 + 一行丢弃计数」。
