Rust · 自绘 · 无 WebView

小程序源码进，
像素出。

一个用 Rust 从零实现的小程序渲染引擎。给它一份微信小程序源码 （WXML / WXSS / JS / app.json）和一块可写的像素缓冲，它把界面画出来、把交互跑起来。 中间没有浏览器内核、没有系统控件、没有第三方图形库。

  • 不基于 WebView
  • 不映射系统原生控件
  • 不依赖 Skia

为什么自绘

WebView 的痛点不在能不能渲染，
而在你控制不了

内核版本随系统走、同一份 CSS 在不同 Android 上排版不同、首屏要等内核起来、 滚动与手势的手感由内核决定、想插一层原生能力就要架桥。 自绘把这些变成自己的代码：布局与绘制各端只有一份，帧调度、手势仲裁、内存上限全在手里。

与常见跨端渲染方案的对比
方案它的做法本引擎
小程序 WebView 渲染层 WXML → DOM，交给浏览器内核排版绘制 不用 DOM 与浏览器内核
React Native / Weex JS 描述 → 映射成系统原生控件 不映射 系统控件，不受各端控件差异摆布
Flutter Dart + Skia 自绘 思路最近 但这里是 Rust + 自研光栅器，无 Skia
Electron / Tauri 打包或复用一个浏览器 不打包 浏览器，产物 34MB 级
微信 Skyline 原生渲染 + 自绘组件 对齐目标 语义、手感、事件模型都按它对

代价也很实：CSS 覆盖面要自己一条一条补，性能靠 CPU 省着花。各端剩余差异只来自系统字体 —— 要彻底消掉就把字体一起打包（assets/ 里放了 Noto Sans SC）。

渲染管线

一帧是怎么画出来的

八步，每步都能单独打开诊断日志。逻辑层与渲染层之间只有数据快照这一条通道 （setData → Arc<Value>）—— 没有 DOM、没有虚拟节点 diff、没有 GC 压力。

  1. 01

    解析

    WXML → 节点树，WXSS → 样式表。手写解析器；CSS 选择器引擎在解析期就编译好，含标签 / 类 / #id / * / 属性 / 后代 / 子代与特异性排序。

  2. 02

    逻辑层

    跑 App / Page / Component，setData 产出数据快照。QuickJS 运行时：CommonJS 模块、Promise / async、定时器、微任务每帧 pump。

  3. 03

    模板求值

    {{ }} 表达式 + wx:if / wx:for 展开成渲染节点树。class / style 绑定到数组或对象时按 CSS 语义拼接。

  4. 04

    样式计算

    命中的 CSS 加内联 style 合成计算样式。带继承语义（color / font-size / line-height …），简写与细项按固定档位排序落地。

  5. 05

    布局

    taffy 求解 Flexbox 盒模型。文本节点挂自定义度量函数，换行与 min/max-content 由真实字形宽度决定；布局后有第二遍 reflow 收拾算完才知道的溢出。

  6. 06

    绘制

    自研 2D 光栅器：扫描线 + even-odd 填充、4× 超采样抗锯齿、圆角三次贝塞尔逼近、多字体回退、Apple sbix 彩色 emoji、两级图片过滤、渐变、掩膜化 box-shadow、裁剪栈。

  7. 06′

    动画

    @keyframes / transition / wx.createAnimation 在绘制期按全局时钟求值。transform / opacity / 颜色只影响绘制不触发重排 → 动画帧成本≈静态帧。

  8. 07

    分层合成

    正常流 → tabBar → position:fixed 覆盖层，层叠顺序与浏览器一致（全屏遮罩能压暗 tabBar）。覆盖层用视口坐标、独立画布、按需重绘。

  9. 08

    上屏

    贴到窗口、交给宿主 View、或直接存 PNG。桌面走 softbuffer，移动端把 RGBA 交给宿主，无头模式 save_png —— 同一份代码，五个平台。

小程序目录解析逻辑层布局光栅化合成RGBA 缓冲

产物是一个普通的 Rust 库（cdylib / staticlib / rlib）。 落地条件只有一条：给我一块可写的像素缓冲 —— 所以 Android、iOS、Windows、macOS、Linux 跑同一份代码，没有屏幕的 CI 里也能直接出 PNG。

稳态帧稳得住

144Hz 屏（节拍 6.94ms）上商城首页的帧间隔从 6.9~25ms 抖动 收到 6.7~7.2ms；最慢一帧从 17.9ms 降到 11.4ms。

只重绘变化的那一块

首页秒杀倒计时的失效范围是 45×33 像素，不是整屏。拿不准就退回整帧 —— 少画一块留下脏像素，比多画一次严重得多。

滚动不重绘

页面画布是整页高的、用内容坐标，滚动只是取不同切片上屏，每帧 2~3ms。只有滚出已绘制条带那一刻才补画一次。

双端一致性

同一份源码：一边原生渲染，一边编译成 HTML 用 Chrome 截图，逐像素比。剩余差异集中在粗体字形与亚像素文本位置。

关键取舍

为什么这么写

每一条背后都有踩过的坑，反面教材都记在踩坑记录里。

文本度量驱动布局，不估算宽度

度量上下文挂到 taffy 叶子上，真实字形参与布局，「定宽容器内换行」与「收缩容器被内容撑开」两种语义同时成立。

曾给每个文本盒 +4px「保险余量」，结果所有按内容定宽的徽标都比浏览器宽一圈。

动画只重绘不重排

@keyframes 里改 width / height 这类会引发重排的属性不生效，改 transform / opacity / 颜色都生效。换来的是动画帧和静态帧一样便宜。

滚动手感按 iOS / 微信那套做

橡皮筋衰减 1 - 1/(x·0.55/d + 1)；回弹是带初速度的临界阻尼弹簧，不是固定时长缓动；惯性撞边界不当场停死，把动量交给弹簧。

手势归属不在按下时决定

等第一次明显位移（4px）按主方向锁定，再按「到边界仍在推」交棒给外层。横向卡片列表里竖着划该滚页面，纵向列表里横着划谁也不动。

宿主层沉进 lib，两端共用

页面栈、覆盖层、触摸状态机、手势仲裁、picker 面板、像素合成都在 src/host/，只有帧调度各自实现。逐像素脚本 + 输入行为测试双重守着。

不引入 GPU，不做元素级位图缓存

定位就是「给我一块像素缓冲我就能画」。抗锯齿也没换成子采样 —— 实测与 Chrome 的差异反而从 4.7% 涨到 5.3%。

全部八条与 12 类踩坑记录见 踩坑记录 与 架构与实现原理。

上手

30 秒跑起来

桌面只要 Rust 工具链。集成进 App 只用一个 View。

# 需要 Rust（https://rustup.rs）
cargo build --release

# 交互式选一个示例小程序
./target/release/mini-launcher

# 或直接指定
./target/release/mini-app-window sample-app
./target/release/mini-app-window sample/tea-app --route pages/index/index
# 没有窗口也能出图（CI / 回归用）
./target/release/mini-app-window sample-app --route pages/index/index \
    --settle 0 --time 2 --snapshot target/shot

# 动作参数按书写顺序执行，可重复
#   --touch x,y   --swipe x1,y1,x2,y2   --drag px×帧数
#   --type 文本    --key enter          --wheel
#   --wait 秒      --frames N
// 1) 编库 → jniLibs，再 publishToMavenLocal
//    bash tools/build-mobile.sh android
//    cd sdk/android && ./gradlew publishToMavenLocal

val mini = MiniProgramView(this)
setContentView(mini)
mini.open(File(filesDir, "my-mini-app"))   // 解包后的小程序目录

override fun onBackPressed() {
    if (!mini.goBack()) super.onBackPressed()   // 页面栈空了才退出
}
override fun onResume() { super.onResume(); mini.onHostResume() }
override fun onPause()  { super.onPause();  mini.onHostPause() }
// 1) 编库 → sdk/ios/MiniRender.xcframework（设备 + 模拟器）
//    bash tools/build-mobile.sh ios

let mini = MiniProgramView(frame: view.bounds)
view.addSubview(mini)
mini.open(appDir: unpackedDir)

if !mini.goBack() { navigationController?.popViewController(animated: true) }

View 内部已经包好的

  • 专用渲染线程（引擎不是线程安全的）
  • 尺寸与 dpr 换算
  • 触摸三段，含历史点 / coalescedTouches，不抽稀
  • 按需出帧，静止不耗电
  • 沙盒目录、生命周期与内存告警

只有两件事必须你决定

  1. 小程序包从哪来 —— 下载 / 校验 / 解包到沙盒。引擎按目录读，不解析 .wxapkg、不做签名校验。
  2. 原生层组件谁承载 —— <web-view> / <map> 在微信里是原生组件层。引擎算位置与参数，控件由你用 WKWebView / android.webkit.WebView / ArkUI Web() 放上去。

能力边界

能做什么，明确不做什么

「明确不做」不是没排期，是取舍。

已实现

  • 24 个组件标签：容器 / 文本媒体 / 表单三类，含 swiper、scroll-view、picker-view
  • 事件：六种绑定前缀与完整捕获-冒泡链；触摸序列按微信语义产出（slop 取消 tap、350ms longpress、被滚动接管补 touchcancel）
  • 模板：wx:if / wx:for / block、表达式引擎、class / style 绑定、自定义组件（样式隔离 + 独立数据作用域）
  • 样式：选择器与特异性层叠、继承、@import、CSS 变量、rpx、calc()、渐变、阴影、transform / transition / @keyframes
  • 39 个 wx.*：request（含 abort）、storage 全套且跨启动持久化、Toast / Loading / Modal、五个路由 API、设备信息全套
  • 生命周期：三级共 28 个钩子（App 7 / Page 13 / Component 5 + pageLifetimes 3）
  • 交互：惯性滚动与临界阻尼回弹、手势仲裁、侧滑返回、下拉刷新、picker 面板、局部重绘
  • 媒体：Canvas 2D 完整上下文、<video>（MP4 解复用 + H.264 软解 + 音频）

明确不做

GPU 渲染纯 CPU 才能在无 GPU 环境（CI、嵌入式）里出图
解析 .wxapkg / 签名校验分包、灰度、完整性属于宿主的事，引擎按目录读
把 <web-view> / <map> 编进引擎微信里它们是原生组件层，位置由引擎算、控件由宿主放
远程字体 wx.loadFontFace字体来自系统。API 存在并回调 success，但不真的下载
迁就偏离微信语义的写法对齐目标只有 Skyline 一个

还缺的 13 条

wx:key 的复用语义、template / slot / wxs、scroll-view 的滚动事件、<video> 的播放事件、wx.login 等云能力、移动端 SDK 的左边缘侧滑返回 —— 每条都写了影响。

适合

  • 自家 App 想内嵌小程序容器，又不想背 WebView 的版本差异与首屏成本
  • 要求渲染结果可控且可复现：同一套字体下各端输出逐像素相同
  • 无屏环境批量出图：营销长图、服务端渲染卡片、UI 回归基线
  • 想把一份小程序源码同时输出成 H5（内置编译器）

不适合

  • 需要完整 Web 生态（任意 CSS、第三方 H5 SDK、<iframe>）—— 那就该用 WebView
  • 重度 3D / 大量滤镜 —— 纯 CPU 光栅撑不住
  • 期望零适配跑通任意线上小程序 —— 还有 13 条已知差距
  • 内存极紧的设备 —— 字体后端换完之前峰值偏高

最大的已知短板：内存

实测峰值 600MB~1GB，其中 98% 是字体 —— fontdue 加载时把字体里全部 29352 个字形几何预展开 （一个 CJK 字面约 300MB）。缓存已按字节封顶（图片 64MB / 字形 24MB，LRU）， 也有 trim_memory() 给宿主在内存告警时调用。真正压峰值要换惰性字体后端， 预计每字面 300MB → 约 23MB —— 这会改变每个字形的抗锯齿，需要单独一轮重定基线。
