Rust · self-rendered · aligned with Skyline

Mini-program source in,
pixels out.

A mini-program rendering engine written from scratch in Rust. Hand it a WeChat mini-program source tree (WXML / WXSS / JS / app.json) and a writable pixel buffer, and it draws the UI and runs the interactions. In between there is no browser engine, no platform widgets, no third-party 2D graphics library — the CPU draws every pixel, and an optional GPU backend only composites the layers, byte-identical to the CPU. All 503 official wx.* APIs are there, and Skyline's own components — grid-view, gesture handlers, draggable-sheet, worklet animations — run on the same pipeline.

Why self-render

The pain with WebView is not whether it can render,
it is that you do not control it

The engine version follows the OS, the same CSS lays out differently across Android builds, first paint waits for the engine to boot, scroll and gesture feel are decided by the engine, and every native capability needs a bridge. Self-rendering turns all of that into your own code: one copy of layout and paint for every platform, with frame scheduling, gesture arbitration and memory ceilings in your hands.

Comparison with common cross-platform rendering approaches
ApproachHow it worksThis engine
Mini-program WebView render layer WXML → DOM, handed to a browser engine for layout and paint No DOM, no browser engine
React Native / Weex JS description → mapped onto platform widgets No mapping to platform widgets, not at the mercy of their differences
Flutter Dart + Skia, self-rendered Closest but this is Rust + an in-house rasterizer, no Skia — and it ships as a Flutter plugin too
Electron / Tauri Ship or reuse a browser No bundled browser; about 40 MB on arm64, GPU compositor included
WeChat Skyline Native rendering with self-drawn components Alignment target semantics, feel, event model, API surface and component set all follow it

The price is real too: CSS coverage has to be filled in one property at a time, and performance is spent CPU cycle by CPU cycle. The only remaining cross-platform difference comes from system fonts — to remove even that, bundle a font with the app (assets/SourceHanSansSC-Regular.otf is there for exactly that). With glyphs expanded on first use it costs about 2MB, close to the system font's 1.4MB.

Done inside the engine

  • Routing checked against app.json, success after the new page's onShow, two-way EventChannel, route events, enableAlertBeforeUnload
  • createTCPSocket / createUDPSocket, getLocalIPAddress, createWorker in an isolated module scope
  • A WebAudio node graph with native decodeAudioData, createMediaQueryObserver, createOffscreenCanvas, createBufferURL
  • Batch storage and getStorageInfo, OS-backed getRandomValues, getVideoInfo parsed from the MP4, legacy canvas clip / setLineDash / measureText

Handed to the host, through one channel

  • Name an API in hostApis (Flutter, Android, iOS, C ABI) and the call is yours; leave it out and it fails immediately with an errMsg saying the host can take over
  • chooseImage / chooseMedia / chooseVideo / chooseMessageFile and saving to the album ship with the Android SDK and the Flutter plugin; the desktop window opens the system file dialog
  • Files returned as file:// are imported into wxfile://tmp/; MapContext and the other context objects forward each method with their id; host events reach wx.onXxx through mr_app_dispatch_event

Animation and touch, Skyline style

  • this.animate / clearAnimation, including scroll-driven timelines
  • wx.worklet: shared and derived values, timing / spring / decay / sequence / repeat / delay, Easing, and applyAnimatedStyle writing node styles
  • Gesture handlers report state, delta and velocity through on-gesture-event; while a page-container is open, going back closes it first
  • touchmove / touchend / touchcancel stay locked to the node that got touchstart, as in WeChat and the DOM, even when the finger leaves it

Degradations are written down, not hidden: worklets run on the logic thread; gesture handlers are single-finger (scale stays 1, force-press never fires); movable-view has no pinch zoom; editor is plain text; Workers share the page's QuickJS; sticky-header / sticky-section do not stick and list-view / nested-scroll-* are plain containers; WebAudio plays its sources but effect nodes do not change the sound; custom wx.router transitions are not applied; snapshot.takeSnapshot fails. Each is listed in the engine test guide (Chinese).

Render pipeline

How one frame gets drawn

Eight stages, each with its own diagnostic switch. Between the logic layer and the render layer there is exactly one channel — the data snapshot (setData → Arc<Value>). No DOM, no virtual-node diffing, no GC pressure.

app directoryparselogic layerlayoutrasterizecomposeRGBA buffer
  1. 01

    Parse

    WXML → node tree, WXSS → stylesheet. Hand-written parsers; the CSS selector engine is compiled at parse time and covers tag / class / #id / * / attribute / descendant / child with specificity ordering.

  2. 02

    Logic layer

    Runs App / Page / Component; setData produces a data snapshot. QuickJS runtime: CommonJS modules, Promise / async, timers, microtasks pumped every frame.

  3. 03

    Template eval

    {{ }} expressions plus wx:if / wx:for expanded into a render tree. class / style bound to arrays or objects are joined per CSS semantics.

  4. 04

    Style resolution

    Matched CSS plus inline style composed into a computed style, with inheritance semantics. Selector matching allocates nothing and the cascade borrows declarations instead of copying them — on a phone that is what took a full rebuild after setData from about 7 ms to about 3.5 ms.

  5. 05

    Layout

    taffy solves the flexbox box model. Text nodes carry a custom measure function, so wrapping and min/max-content come from real glyph widths; line counts are memoized per font, so text that did not change is never measured twice.

  6. 06

    Paint

    In-house 2D rasterizer: scanline + even-odd fill, 4× supersampled anti-aliasing, rounded corners via cubic Bézier, multi-font fallback, Apple sbix color emoji, two-tier image filtering, gradients, masked box-shadow, clip stack.

  7. 06′

    Animation

    @keyframes / transition / wx.createAnimation are evaluated at paint time against the vsync clock. transform / opacity / colors affect painting only and never trigger reflow → an animated frame costs about the same as a static one.

  8. 07

    Composition

    Normal flow → tabBar → position:fixed overlay, stacked like the browser. After setData only the changed region repaints: a list that grows at the bottom repaints from its first change downward, a fixed button appearing repaints only the overlay.

  9. 08

    Present

    Blit to a window, hand to a host view, or save a PNG. The desktop window and Android composite on the GPU once the self-test passes (wgpu takes the layers as textures) and fall back to the CPU otherwise; the native iOS view hands its CAMetalLayer to the same compositor (Metal); headless and the Flutter iOS texture composite on the CPU — one codebase, five platforms plus Flutter.

The artifact is an ordinary Rust library (cdylib / staticlib / rlib) and it asks for one thing: a writable pixel buffer — so Android, iOS, Windows, macOS and Linux run the same code, and a CI box with no screen can emit PNGs directly.

What the mobile hosts get

  • On Android the engine draws into its own SurfaceView; the system compositor takes it directly, no Flutter frame in between
  • GPU compositing on Vulkan once the start-up self-test is byte-identical; CPU fallback on any failure or lost device
  • Engine-drawn navigation bar and capsule button, 300 ms route transitions, left-edge swipe back
  • Drags resampled by touch timestamps; animations sampled at the vsync, not when drawing happened
  • Same-layer <video> and <map> on Android: the host decodes or draws the frame, the engine paints it into the page, so it scrolls with the page and sheets, modals and the tabBar cover it as in WeChat (iOS still lays them over the page)
  • System pickers for chooseImage / chooseMedia / chooseVideo / chooseMessageFile and saving to the album, built into the Android SDK and the Flutter plugin
  • Idle costs nothing: frames only on demand; in the background GPU textures, image caches and the compose buffer are released and screenshots packed

Dual backend

Two backends, one picture

The CPU rasterizer draws every pixel and stays the single reference, so a CI box with no GPU produces the same image as a phone. The GPU backend (wgpu: Metal / Vulkan / DX12 / GLES) only composites the page, tabBar and fixed layers as textures, with integer shaders that replicate the CPU's blending arithmetic.

⊕ =
  • 34 / 34 scenes byte-identical in tools/gpu-parity.sh, including a device loss injected mid-run
  • A start-up self-test must match the CPU byte for byte before the GPU is used; any failure falls back to the CPU on the same frame, with a log line saying why
  • Automatic on the desktop window, Android and the native iOS view; headless and the Flutter iOS texture use the CPU. Force either with --backend / MINI_BACKEND
  • Overlays (Toast, Modal, action sheet, picker) upload only the rows they cover; scrolling just presents another slice of the page texture

Steady frames hold

On a 144 Hz screen (6.94 ms budget) the shop home's frame interval went from 6.9–25 ms jitter down to 6.7–7.2 ms; the slowest frame from 17.9 ms to 11.4 ms.

Only the changed region repaints

The home page's flash-sale countdown invalidates 45×33 pixels, not the screen. A growing list repaints from its first change down; a fixed button appearing repaints only the overlay. When in doubt it falls back to a full frame — stale pixels are far worse than one extra paint.

Scrolling does not repaint

The page canvas is full-page height in content coordinates, so scrolling just presents a different slice, 2–3 ms per frame. Only the strip you scroll into gets painted, a little before it shows.

Key trade-offs

Why it is written this way

Every one of these has a mistake behind it; the counter-examples are all written up in the gotchas doc.

Text measurement drives layout; widths are never estimated

The measure context is attached to taffy leaves so real glyphs participate in layout, letting "wrap at the container width" and "a shrinking container pushed out by its content" hold at the same time.

A +4px "safety margin" per text box once made every content-sized badge a ring wider than the browser's.

Animation repaints, never reflows

Changing width / height in @keyframes has no effect; transform / opacity / colors do. What you buy is an animated frame being as cheap as a static one.

Scroll feel follows iOS / WeChat

Rubber-band damping 1 - 1/(x·0.55/d + 1); bounce-back is a critically damped spring with initial velocity, not a fixed-duration easing; inertia hitting a boundary does not stop dead, it hands its momentum to the spring.

Gesture ownership is not decided on touch-down

It waits for the first meaningful movement (4px), locks to the dominant axis, then hands off to the outer scroller on "still pushing at the boundary". Swiping vertically inside a horizontal card list scrolls the page; swiping horizontally inside a vertical list moves nothing.

The host layer lives in the lib, shared by every host

Page stack, route transitions, overlays, touch state machine, gesture arbitration, picker sheet and pixel composition all live in src/host/; only frame scheduling is per-platform. A per-pixel script plus input-behaviour tests guard it from both sides.

The CPU draws, the GPU only composites

The CPU rasterizer is the single pixel reference, so CI and embedded boxes with no GPU produce the same image. The GPU backend (desktop window, Android and the native iOS view) only composites the page / tabBar / fixed layers as textures, byte-identical to the CPU for the same frame, and falls back to the CPU on any failure. No vello / Skia: their own anti-aliasing would make that unverifiable.

All eight, and every "what went wrong" story behind them, are in the gotchas log and architecture & implementation (Chinese).

Getting started

Run it in 30 seconds

Desktop needs only the Rust toolchain. In an app it is one View — or one Flutter widget.

# needs Rust (https://rustup.rs)
cargo build --release

# pick a sample mini-program interactively
./target/release/mini-launcher

# or name one directly
./target/release/mini-app-window sample-app
./target/release/mini-app-window sample/tea-app --route pages/index/index
# images without a window (CI / regression)
./target/release/mini-app-window sample-app --route pages/index/index \
    --settle 0 --time 2 --snapshot target/shot

# action flags run in the order written, and repeat
#   --touch x,y   --swipe x1,y1,x2,y2   --drag px×frames
#   --type text    --key enter          --wheel
#   --wait seconds --frames N
// pubspec.yaml: mini_render: { path: <repo>/sdk/flutter }
// build the engine first: bash tools/build-mobile.sh android   (or ios)

final c = MiniProgramController(
  appDir: unpackedDir,                        // the unpacked mini-program (has app.json)
  hostApis: {'login': (args) async => {'code': await myLogin()}},  // chooseImage & co. are built in
  nativeComponents: const ['video', 'map'],   // hosted by your own widgets
  sameLayerViews: const ['map'],              // Android: painted into the page, scrolls with it
);
Navigator.push(context, MaterialPageRoute(
  builder: (_) => MiniProgramScaffold(        // nav bar + back + capsule + engine view
    controller: c,
    onMenu: () => showMyShareSheet(),          // the capsule's "•••"
    onExit: () => Navigator.pop(context),      // the capsule's "⊙"
  ),
));
// 1) build the libs → jniLibs, then publishToMavenLocal
//    bash tools/build-mobile.sh android
//    cd sdk/android && ./gradlew publishToMavenLocal

val mini = MiniProgramView(this)
mini.hostApis["login"] = MiniHostApi { call, reply -> reply.success(JSONObject().put("code", myCode())) }
mini.sameLayerViews["map"] = { MyMapView() }   // a MiniSameLayerView, painted into the page
setContentView(mini)
mini.open(File(filesDir, "my-mini-app"))   // the unpacked mini-program directory

override fun onBackPressed() {
    if (!mini.goBack()) super.onBackPressed()   // exit only once the page stack is empty
}
override fun onResume() { super.onResume(); mini.onHostResume() }
override fun onPause()  { super.onPause();  mini.onHostPause() }
// 1) build the lib → sdk/ios/MiniRender.xcframework (device + simulator)
//    bash tools/build-mobile.sh ios

let mini = MiniProgramView(frame: view.bounds)
mini.hostApis["login"] = { call, reply in reply.success(["code": myCode()]) }
view.addSubview(mini)
mini.open(appDir: unpackedDir)              // renders into its own CAMetalLayer (GPU, CPU fallback)

if !mini.goBack() { navigationController?.popViewController(animated: true) }

Already handled inside the View

  • A dedicated render thread (the engine is not thread-safe)
  • Size, dpr and safe-area conversion, system bars on Android
  • All three touch phases with timestamps, including historical points / coalescedTouches, nothing dropped
  • On-demand frames; idle costs no battery
  • Sandbox directory, lifecycles and memory warnings
  • GPU surface attach / detach, warm-up and CPU fallback

Only two things are yours to decide

  1. Where the package comes from — download / verify / unpack into the sandbox. The engine reads a directory; it does not parse .wxapkg and does no signature checking.
  2. Who hosts native components — <map>, <camera>, <web-view> live in WeChat's native component layer. Hand the engine a frame (sameLayerViews, Android) and it paints it into the page; or let the engine report position and parameters and place WKWebView / android.webkit.WebView / ArkUI Web() yourself. Tags nobody claims draw a labelled placeholder.

Deliberately not

Drawing content on the GPU (vello / Skia style)The GPU backend that exists only composites layers the CPU already drew. Content is always drawn by the CPU, so it stays the single pixel reference and places with no GPU (CI, embedded) produce the same image. Drawing on the GPU would mean a second rasterizer next to the CPU one; not done in this round
Parsing .wxapkg / signature checks.wxapkg is WeChat's private compiled format and the signature is WeChat's key system; subpackages, staged rollout and integrity belong to the host, and the engine reads a source directory
Compiling <web-view> / <map> into the engineSkyline itself does not render web-view (its component table says "not planned"; such a page falls back to the WebView renderer), and map is a same-layer native component in Skyline: the host draws the map, the engine paints that frame into the page (or reports the position so the host can lay its widget over it)
Accommodating code that deviates from WeChat semanticsSkyline is the only alignment target. This is a principle, not a feature that can be implemented

Still open

Each with its impact written down in the test guide: wx:key in incremental invalidation and WXS event handlers; custom components in the H5 export; scrollbars, Skyline's sticky sections and nested scrolling; dragging video progress and picture-in-picture; multi-finger gestures (pinch on movable-view and the scale handler); worklets off the logic thread and swiper worklet callbacks; type="webgl" canvases; bare text placed directly in a <view> does not wrap; inherited color overriding progress / slider / icon defaults; per-element CSS variables and grid-template; textarea auto-height and IME composition; same-layer components on iOS.

Good fit

  • You want to embed a mini-program container in your own app — native or Flutter — without inheriting WebView version drift and first-paint cost
  • You need rendering that is controllable and reproducible: with the same fonts, every platform outputs pixel-identical results
  • Batch image generation with no screen: marketing long-images, server-rendered cards, UI regression baselines
  • You want one mini-program source tree to also ship as H5 (built-in compiler)

Poor fit

  • You need the full web platform (arbitrary CSS, third-party H5 SDKs, <iframe>) — use a WebView
  • Heavy 3D or lots of filters — content is rasterized on the CPU (the GPU only composites), which will not hold up
  • You expect any production mini-program to run with zero adaptation — there are still known gaps
  • Very tight memory budgets — fonts are no longer the problem, but decoded images (capped at 64MB) and a CPU page canvas about one screen tall still count

Memory: no longer the biggest weakness

Fonts used to be about 98% of the peak: fontdue expanded every glyph's geometry at load time. A vendored fontdue now expands a glyph the first time it is drawn and memory-maps the font file; metrics and bitmaps are bit-identical to upstream, so no baseline moved. The buffer round then keeps only the painted strip of the page and drops or packs full-screen buffers in the background.

Stack

Few dependencies, all on current stable

src/ is 410 .rs files / ~88k lines (49 of them test modules), plus 33 integration-test files; any file over 500 lines gets split. Outside the FFI boundary, unsafe appears in 12 audited spots — pixel slices viewed as bytes, surfaces created from a native window pointer, two Android system calls (logcat, CPU affinity) and one zeroed canvas allocation — each with a SAFETY note; there is no static mut.
